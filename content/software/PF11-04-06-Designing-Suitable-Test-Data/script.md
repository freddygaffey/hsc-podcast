QUESTION: Can't I just run my program with some normal inputs and see if it works?

NARRATOR: That's exactly the trap, and it's the most common testing mistake. Normal data passing tells you almost nothing — the bugs hide in the cases you didn't think of. Take a discount calculator: test it with a hundred dollars at ten percent off, you get ninety, looks perfect. But feed it a hundred and fifty percent off and it pays the customer fifty dollars; feed it a negative price and it sails through. Normal data passed; the program is broken. That's in Listing 1. So the dot-point: "Determine sets of suitable test data," including "boundary values; path coverage; faulty and abnormal data." Outcome S-E-eleven-oh-six. Designing test data means deliberately choosing inputs that probe where bugs live — not just the happy path.

NARRATOR: Objectives up front. By the end you'll be able to: name and apply the three syllabus types of test data; use equivalence partitioning to cut the test count without losing coverage; design a test set for a given function, including boundary and abnormal cases; and explain why normal data alone is insufficient. Here's the hook for the three types the syllabus names: B-P-F — Boundary, Path coverage, Faulty-abnormal, laid out in the reference in Listing 2. And every test, whatever its type, does the same thing: compare the actual output to the expected output. Let's take the trio.

NARRATOR: First, boundary values — the highest-value test data there is. A boundary value is an input sitting exactly on the edge of a range, plus the values just either side of that edge. Wherever your code has a cut-off — a pass mark, a range limit, a threshold — you test the value on the boundary and the values immediately above and below it, because boundaries are precisely where off-by-one errors live. Take a grade function where fifty and above is a pass, graded D, and below fifty is an F. The boundary is fifty, so you test forty-nine, fifty, and the surrounding values: forty-nine should be F, fifty should be D. You test every grade cut-off that way — seventy for a C, ninety for an A — plus the outer limits zero and a hundred, and just outside the valid range, minus one and a hundred and one. Listing 3 is that full boundary test set. This is the boundary value from the desk-checking episode and the range constraints from the data-dictionary episode, now formalised as a testing strategy.

QUESTION: Here's one to actually attempt. Pause the player. A function accepts an age that must be between eighteen and sixty-five inclusive. What boundary values would you test? Work it out, then play.

NARRATOR: You'd test the two boundaries and the values just either side of each: seventeen and eighteen at the lower edge, and sixty-five and sixty-six at the upper edge — and ideally the boundaries themselves, eighteen and sixty-five, confirmed valid. So seventeen should be rejected, eighteen accepted, sixty-five accepted, sixty-six rejected. The mark is testing the value on each limit and the value one step outside it — that's where an accidental "greater than" instead of "greater than or equal to" would show up. Four well-chosen boundary values catch more bugs than a hundred random valid ages.

NARRATOR: Second, path coverage. This means choosing test data that exercises every path through the code — every branch of every decision, and the loops running zero, one, and many times. If your code has an if-elif-else with four branches, you need at least four test cases, one to drive execution down each branch; a branch never executed is a branch never tested. So for the grade function with its five grade branches plus the invalid branch, path coverage means at least one input that lands in each. Listing 4 shows a small function with three branches — negative, zero, positive — and a test set with one input per branch, so every path runs. The key idea: count the paths, then make sure your test data covers all of them.

NARRATOR: Third, faulty and abnormal data — deliberately bad input, to check the program handles it gracefully instead of crashing or producing nonsense. Wrong type — a word where a number was expected. Out of range — an age of two hundred. Empty input — a blank string. Negative where only positive makes sense. Garbage. Good test data includes these, because real users and real systems send bad input all the time, and a robust program rejects it cleanly. Listing 5 tests a parse-age function with an empty string, non-numeric text, a negative, a decimal, the wrong type, and an out-of-range value — and checks each is rejected, not crashed on. Faulty-and-abnormal data is how you test the validation you learned to specify back in the data-dictionary episode.

NARRATOR: Now a strategy that ties boundary and path testing together and saves you from testing forever: equivalence partitioning. The idea is that inputs fall into groups — partitions — where every value in a group is treated the same way by the program, so testing one representative from each group is as good as testing them all. For an age categoriser with Child, Teenager, Adult, and Senior groups, you don't test every age zero to a hundred; you test one age from each group — say seven, sixteen, thirty-five, seventy — plus the boundaries between the groups. Partition the inputs, pick one from each, and add the boundaries. That's in Listing 4 too. Equivalence partitioning cuts the test count dramatically without losing coverage, and it pairs naturally with boundary testing — the partitions tell you the groups, the boundaries tell you the edges between them.

NARRATOR: Now the exam-style questions. Pen down, and when I say pause, attempt it before the model answer.

QUESTION: Question one. Name the three types of test data the syllabus requires, and what each is for.

NARRATOR: Boundary values — inputs on the edge of a range and just either side, to catch off-by-one errors at cut-offs. Path coverage — inputs chosen so that every branch and path through the code is executed at least once. Faulty and abnormal data — invalid input such as wrong types, out-of-range, or empty values, to check the program handles bad input gracefully. The hook is B-P-F, and the "for" clause on each — edges, every path, bad input handled — is what lifts a recall answer to full marks.

QUESTION: Question two. Design suitable test data for a function that assigns a letter grade, where a mark of fifty or more is a pass. Include boundary and abnormal cases. Pause the player, write your test set, then play.

NARRATOR: Boundary cases around the pass mark: forty-nine should be a fail, fifty should be a pass — testing the cut-off and the value just below it. Boundaries at the other grade thresholds and the outer limits: seventy, ninety, zero, and a hundred. And abnormal cases outside the valid range: minus one and a hundred and one, which should both be rejected as invalid, plus perhaps a non-numeric input. For each, state the input and the expected output. The marks are for including boundary values right at and just below the cut-offs, and for abnormal data outside the valid range — not just a few normal marks in the middle.

QUESTION: Question three. Explain equivalence partitioning and why it is useful.

NARRATOR: Equivalence partitioning divides the possible inputs into groups, or partitions, where every value in a group is processed in the same way by the program, then tests one representative value from each partition rather than every possible value. It's useful because it dramatically reduces the number of test cases needed while still covering every distinct behaviour — testing one child's age represents all child ages — and it pairs with boundary testing, which then checks the edges between the partitions. The mark is defining the partition as a group treated identically, and the benefit as full behavioural coverage with far fewer tests.

QUESTION: Question four. A discount function works correctly for normal inputs but a tester is worried. Give two pieces of test data that might reveal a bug, and what each checks.

NARRATOR: One: a discount percentage above one hundred, such as a hundred and fifty percent — an abnormal value that checks whether the function wrongly produces a negative price, effectively paying the customer. Two: a negative price — a faulty value that checks whether the function rejects impossible input rather than processing it. Both are faulty-or-abnormal data probing beyond the normal range, and both reveal missing input validation. The mark is choosing genuinely boundary or abnormal inputs and stating what each one checks — not just more normal data.

QUESTION: Question five. Why is testing a program only with normal, typical data insufficient?

NARRATOR: Because normal data exercises only the common, expected case, and most bugs occur in the cases the programmer didn't anticipate — at the boundaries of ranges, in rarely-taken branches, and when invalid input arrives. A program can pass every normal test and still fail on a boundary value, an unhandled branch, or bad input, which is exactly where real failures happen. Thorough testing therefore needs boundary, path-coverage, and faulty-and-abnormal data as well as normal data. The mark-earning point: normal data leaves the edges, the untaken paths, and the error cases untested, and that's where bugs live.
