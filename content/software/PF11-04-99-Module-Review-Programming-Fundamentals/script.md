NARRATOR: Chapter One — software development. The lifecycle, the tools, the management.

QUESTION: The eight development steps — the acronym, and the order-locking sentence?

NARRATOR: R-S-D-D-I-T-I-M: Requirements, Specifications, Design, Development, Integration, Testing, Installation, Maintenance — "Real Software Demands Discipline: Integrate, Test, Install, Maintain." And the headline: the lifecycle is iterative, not linear. Then the tools — Git's three places are W-S-R, Write, Stage, Record; the benefits of online collaboration tools are CRAB, Collaboration, Review, Accountability, Backup. Documentation is R-D-C, Read-me, Docstring, Comment, and a comment explains why, not what. And the management models: Waterfall falls once, Agile loops — compared on R-F-D-C, Requirements, Feedback, Documentation, Change, with no universal winner.

QUESTION: Chapter Two — designing algorithms. The three control structures, and the analysis routine?

NARRATOR: The control structures are S-S-I: Sequence, Selection, Iteration — and the data a loop stores is A-E-F: Accumulator, Extreme, Flag. You write algorithms as pseudocode or flowcharts, where the diamond decides and a data flow diagram shows where the data goes while a flowchart shows what the program does in order. You analyse them with I-O-P: Inputs, Outputs, Purpose — desk is solo, peer is social — and at scale the full method is Read, I-O-P, Map, Trace, Check, ending in the connections, which are a call or a data hand-off. You decompose with structure charts — top-down splits, bottom-up builds, aiming for high cohesion and low coupling — and the two strategies, divide-and-conquer, split-solve-combine, and backtracking, try-fail-undo-retry. The module boxes are subprograms: a function returns, a procedure performs. And the wide-angle view, the four paradigms: I-O-L-F, Imperative, Object-oriented, Logic, Functional.

QUESTION: Big retrieval. Pause the player and write down what S-S-I, A-E-F, I-O-P, and I-O-L-F each stand for. Go.

NARRATOR: S-S-I — Sequence, Selection, Iteration. A-E-F — Accumulator, Extreme, Flag. I-O-P — Inputs, Outputs, Purpose. I-O-L-F — Imperative, Object-oriented, Logic, Functional. Four hooks, the spine of Chapter Two. If you missed one, that's your revision target — it's on the master sheet.

QUESTION: Chapter Three — data. Number systems, types, dictionaries, structures?

NARRATOR: Number systems: base-two binary, base-ten decimal, base-sixteen hexadecimal; each hex digit is exactly four bits; and two's complement for negatives is flip the bits, add one, with the leftmost bit as the sign. The standard data types fall into four families — Words, Numbers, Truth, Time — and the key line is an integer is exact, a float is approximate. A data dictionary describes each field as F-T-C-R, Field name, Type, Constraints, Relationship — constraints answer four questions, how long, how big, what shape, must it be there — and relationships are one-to-one, one-to-many, many-to-many. And the four data structures are A-R-T-S: Arrays, Records, Trees, Sequential files — where an array indexes by number and a record names by field.

QUESTION: Chapter Four — building it in Python. The Python-specific gotchas, and the four testing-and-quality hooks?

NARRATOR: In Python, the indent is the block, and the range function stops one before its stop. A list is your array, a dictionary your hash table, a list with append-and-pop your stack. Functions take parameters three ways, P-D-K, Positional, Default, Keyword. You import the module, or import the name, never the star — and seed it to repeat it for testable randomness. You debug with the trio Breakpoint, Step, Watch. You design test data as B-P-F, Boundary, Path coverage, Faulty-and-abnormal. You classify errors as S-L-R, Syntax, Logic, Runtime — syntax won't run, runtime crashes, logic is silently wrong. And you evaluate the finished solution as F-P-R-D, Functionality, Performance, Readability, Documentation. That's the whole module on a few breaths.

NARRATOR: Two real stories worth carrying into the exam, because a marker remembers an answer anchored in one. First, the Year Two Thousand problem: for decades, software stored the year as just two digits to save space, so nineteen-ninety-nine was nine-nine — and the fear was that the year two thousand, stored as oh-oh, would read as nineteen hundred. A data-representation choice — the data-types and number-systems content of Chapter Three — that triggered a worldwide remediation effort. Second, Mariner One, nineteen-sixty-two: a NASA probe destroyed seconds after launch, traced to a tiny transcription error in the guidance software — a single missing symbol in a formula — that made the rocket steer erratically. The classic cautionary tale for the error types and test data of Chapter Four: a microscopic bug, catastrophic cost, and exactly what careful testing exists to catch.

NARRATOR: Now the traps, gathered in one place — the predictable mistakes across the whole module. From Chapter One: calling the lifecycle linear instead of iterative; crowning a universal winner in Waterfall-versus-Agile; a comment that restates what instead of why. From Chapter Two: confusing sequence with selection; the infinite loop from a never-changing exit condition; the do-everything module with low cohesion; printing inside a function instead of returning; missing a data dependency between subprograms. From Chapter Three: forgetting two's complement is flip and add one, not just flip; writing the eight-bit range as plus-or-minus one-twenty-eight instead of negative one-twenty-eight to positive one-twenty-seven; storing money in a float; storing a number you'll do maths on as a string. From Chapter Four: the range off-by-one; the silent logic error — code that runs is not proof it's correct; testing only normal data; and vague praise with no evidence when you evaluate. Name a trap before you make it, and you don't make it.

NARRATOR: Let's close in full exam mode — integrated questions spanning multiple chapters, the way real HSC questions do. Pen down, pause where I say, then the model answer.

QUESTION: Question one, integrated. A team is building software with stable, well-understood requirements. Name a suitable project management model and justify it, then name two modelling tools they'd use to design the algorithm.

NARRATOR: Waterfall, justified because the requirements are stable and well-understood — Waterfall's sequential, plan-up-front approach suits low-change projects; Waterfall falls once. For designing the algorithm, two modelling tools: a structure chart, showing the module hierarchy and data flow, and pseudocode or a flowchart for the detailed logic. Full marks: name Waterfall, tie the justification to requirement stability, and name two genuine modelling tools.

QUESTION: Question two, spanning data and code. Explain why storing a monetary amount in a floating-point variable is a poor choice, and what you'd do instead.

NARRATOR: A floating-point number is stored approximately in binary, so many decimal values like nought point one can't be represented exactly, and these errors accumulate across financial calculations, producing incorrect totals. Instead, store the amount as an integer number of the smallest unit — cents — so all arithmetic is exact, and divide only for display. The marks: the float's inexactness and its cause, the consequence for money, and the integer-cents fix. That's Chapter Three's data-types content with real stakes.

QUESTION: Question three, the end-to-end one. Pause the player. Briefly outline how you would design, code, test, and evaluate a simple program that finds the highest score in a list. Work it out, then play.

NARRATOR: Design: write an algorithm in pseudocode that stores a running maximum — the Extreme of A-E-F — initialised to the first score, then iterates the rest, updating the maximum when it finds a larger value. Code: implement it in Python as a function with a loop and a selection, returning the maximum. Test: feed it B-P-F data — a normal list, a single-element list and an empty list as boundaries, and decide what an empty list should return as the faulty case. Evaluate: across F-P-R-D — functionally correct against the tests, efficient in one pass, readable with a descriptive name, and documented with a docstring. Full marks: name a concrete technique at each of the four stages — design, code, test, evaluate — using the module's vocabulary.

QUESTION: Question four. Classify each as a syntax, runtime, or logic error: a missing colon after an if-statement; reading the tenth element of a five-element list; and a loop that runs one time too few because of an off-by-one.

NARRATOR: The missing colon is a syntax error — it breaks the grammar, so the program won't run. Reading the tenth element of a five-element list is a runtime error — an index error — the code runs until it hits that line, then crashes. The off-by-one loop is a logic error — it runs to completion without crashing but produces the wrong result, silently. The hook is S-L-R, and the giveaway for each — won't run, crashes, runs-but-wrong — is the classification. The logic error being silent is the key point.

QUESTION: Question five, the synthesis. A program is functionally correct — it passes all its tests. Is that enough to call it a high-quality solution? Justify your answer.

NARRATOR: No. Functional correctness is only one of the four aspects a solution is evaluated against — F-P-R-D. A program that passes all its tests may still perform poorly on large inputs, be unreadable and therefore hard to maintain, or lack documentation so others can't use or extend it. A high-quality solution must be evaluated across all four — functionality, performance, readability, and documentation — with evidence for each, not just functionality. The mark-earning point: correctness is necessary but not sufficient; quality is judged on all four aspects. That's the whole module's final lesson, and a perfect note to end on.
