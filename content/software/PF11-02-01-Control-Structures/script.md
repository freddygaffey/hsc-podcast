NARRATOR: First, sequence. Sequence is the simplest — it's just doing things in order, one step after another, each step exactly once, no decisions and no repetition. The textbook image is a recipe: get the ingredients, mix them, bake for thirty minutes, cool and serve. The defining characteristics, and these are the words markers like to hear: linear execution, every step runs exactly once; predictable order, the steps always happen in the same order; no branching and no looping. Take the make-sandwich algorithm — get two slices of bread, spread butter on one, add the filling, place the second slice on top, cut in half. Five steps, always the same five, always that order. Trace it and you get the identical result every single time. That predictability is the whole point of sequence.

QUESTION: That sounds almost too obvious to be worth a mark. Why would the exam ever test sequence on its own?

NARRATOR: Fair — and you're right that pure sequence is rarely the whole question. But it shows up as part of a larger trace, and there's a classic trap: students confuse a sequence with a selection. If two things always both happen, that's sequence. If one of two things happens depending on a condition, that's selection. People see two output lines and call it a decision when there was never a condition. Naming the structure correctly is the mark, so don't fumble the easy one.

NARRATOR: Which brings us to the second building block: selection. Selection lets the algorithm make a decision based on a condition. It's the fork in the road — you check a condition, and you choose a path. The syllabus term is selection; in code you know it as the if statement. There's a family of selection shapes worth being able to name. The simplest is a single if-then: do something only if the condition is true, otherwise skip it and carry on. The condition is checked, and the body is optional. Then binary selection — if-then-else — where you choose between two actions and exactly one of them always runs; the two branches are mutually exclusive. Then multiple selection — if-then, else-if, else-if, and a final else — for choosing among several options, where the first matching condition wins and the rest are skipped. There's also nested selection, decisions inside decisions, for layered logic; and in some languages a case or switch structure that picks among many values of one variable.

NARRATOR: Let me make multiple selection concrete with our running example, the grade calculator, because the grade boundaries are a perfect illustration and they come back later in the course. Suppose we have a score and we want a letter. If the score is greater than or equal to ninety, the grade is A. Else if it's greater than or equal to eighty, B. Else if greater than or equal to seventy, C. Else if greater than or equal to fifty, D. Otherwise, F. The full version is in Listing 1 as real Python and in Listing 2 as exam-style pseudocode. Now here's the thing that earns marks: the order matters, and "first match wins" matters. Trace a score of eighty-five. Is it greater than or equal to ninety? No. Greater than or equal to eighty? Yes — output B, and stop. We never even check the seventy or fifty conditions, because once a branch matches, the rest of the chain is skipped. Say that explicitly in an answer — "the first true condition executes and the remaining branches are not evaluated" — and you've shown you understand how the structure actually behaves, not just what it outputs.

NARRATOR: Now the third and richest building block: iteration. Iteration is repetition — repeating an action multiple times. The syllabus term is iteration; informally, a loop. And here is where the real exam vocabulary lives, because there are distinct kinds of loop and you're expected to tell them apart. There are three you must know, and they split on one question: when do you check the condition? Here's the hook — For counts, While checks first, Repeat checks last. Let me unpack that.

NARRATOR: A for loop is the counted loop. You use it when you know in advance how many times to repeat — count from one to ten, process every element of an array, do this exactly N times. The loop variable is managed for you and termination is guaranteed: it will always stop after the set number of iterations. "Counted" and "guaranteed termination" are the phrases to use.

NARRATOR: A while loop is the pre-test loop. It checks its condition before each iteration — pre-test, test-first. The crucial consequence, and this is a favourite exam point: a while loop may run zero times. If the condition is false the very first time you check it, the body never executes at all. Use a while loop when you don't know the number of repetitions ahead of time — keep reading lines until end of file, keep going while the user hasn't typed quit.

NARRATOR: A repeat-until loop is the post-test loop. It executes the body first and checks the condition afterwards — post-test, test-last. The consequence, the mirror image of the while loop: a repeat-until always runs at least once, because the body happens before the first check. That makes it perfect for input validation — ask for the input, then check whether it was valid, and loop back if not. You always want to ask at least once, so post-test fits. Listing 3 shows the same input-validation task written both ways — as a pre-test while loop and as a post-test repeat-until — so you can see the difference in shape side by side.

QUESTION: So how would the HSC actually word the difference between a while loop and a repeat-until?

NARRATOR: Usually as "distinguish between a pre-test and a post-test loop," and they want the behavioural consequence, not just the names. A weak answer says: "a while loop checks at the top and a repeat-until checks at the bottom." True, but it's just restating the definition. The strong answer adds the effect: "A pre-test loop, such as a while loop, evaluates its condition before the body, so it may execute zero times; a post-test loop, such as repeat-until, evaluates its condition after the body, so it always executes at least once." That second version names the structures, states where the test happens, and gives the consequence. Hear the difference? The mark is in the consequence — zero times versus at least once. There's even a one-liner to lock it: while may run never; repeat runs once for sure.

NARRATOR: There's also nested iteration — a loop inside a loop — which you'll meet for grids and tables, where the inner loop completes fully for each single pass of the outer loop. Total iterations are outer times inner. Worth knowing it exists; we'll use it properly when we hit two-dimensional data in Chapter Four.

NARRATOR: Now the trap that costs the most marks in iteration, and it's a logic error, not a syntax one: a loop whose exit condition never changes. If the variable the condition depends on is never updated inside the loop, the condition stays true forever and you have an infinite loop. The classic is a while loop that's meant to count down but forgets to decrease the counter — the counter sits at five, the condition "counter greater than zero" stays true, and it runs until the program is killed. The fix is a rule you can state in an exam: every loop must make progress toward its exit condition on every pass — the body must change the variable the condition depends on. Listing 4 shows the broken countdown and the corrected one, where the counter actually decreases each pass. Say it in an answer like this — "the loop body fails to modify the control variable, so the termination condition is never met, producing an infinite loop" — and that's the marker's exact language.

There's sequence — set things up, then compute, then decide, in order. There's iteration — loop over every score, adding it to a running total. And there's selection — once we have the average, choose the letter with the grade chain. NARRATOR: That running total I just mentioned is the bridge to the last part of the dot-point, the part students skip: identifying data that should be stored. An algorithm isn't just control flow — it's control flow over data, and part of designing it well is deciding what you need to remember as you go. Three patterns cover almost everything you'll see at this level, and the hook is A-E-F — Accumulator, Extreme, Flag. First, the accumulator — a running total or running product you build up across a loop, like that total we added each score to. Second, the running extreme — a stored "best so far," like the highest score seen, which you update whenever you find something larger. Third, the flag — a boolean that records whether something has happened yet, like a "found it" flag in a search, or a "did anyone pass" flag. Accumulator, Extreme, Flag — A-E-F. Listing 5 shows all three at once: a summary that stores a running total, a running maximum, and a passed-flag while looping over scores a single time.

One: the three control structures, the key features of standard algorithms, are sequence, selection, and iteration — S-S-I. Two: sequence is linear, every step once, no decisions; selection chooses a path on a condition, and in a multiple-selection chain the first true branch wins and the rest are skipped. QUESTION: Question one, recall. Name the three control structures used in standard algorithms.

NARRATOR: Sequence, selection, and iteration. If you want the marker to be sure, add one clause each: sequence executes steps in order, selection chooses between paths based on a condition, and iteration repeats steps. That's the S-S-I hook unpacked.

QUESTION: Question two. Identify the control structure being used and explain its effect: an algorithm that, while a counter is less than the length of a list, adds the current element to a total and increases the counter by one. Pause the player, write your answer, then play.

NARRATOR: This is iteration, specifically a pre-test while loop. Its effect: the body repeats as long as the counter is less than the list length, accumulating each element into a running total; because it's pre-test, it checks the condition before each pass and would execute zero times for an empty list. A full-mark answer names the structure — iteration, pre-test while loop — describes the effect — accumulates a total across the elements — and notes the pre-test consequence — zero iterations on an empty list. That last clause is the difference between a solid answer and a top one.

QUESTION: Question three, distinguish — three marks. Distinguish between a pre-test loop and a post-test loop.

NARRATOR: A pre-test loop evaluates its condition before executing the body, so if the condition is initially false the body runs zero times — a while loop is the example. A post-test loop executes the body first and evaluates its condition afterwards, so the body always runs at least once — a repeat-until loop is the example. The distinguishing consequence is the number of guaranteed executions: zero or more for pre-test, one or more for post-test. Three marks: one for each loop's test position, one for the consequence. Lead with the consequence and you can't be marked down for vagueness.

QUESTION: Question four, application. An algorithm reads numbers from the user until they enter a negative number, and reports how many positive numbers were entered and their average. Identify the control structures required and the data that must be stored.

NARRATOR: Control structures: iteration — a loop that continues until a negative value is entered, which is naturally a pre-test while loop or a post-test repeat-until since we read at least once; and selection — a check of whether each entered number is negative to decide whether to stop, and to make sure we don't count the terminating negative. Data to store: a running total of the positive numbers, initialised to zero — that's an accumulator; a count of how many were entered, initialised to zero — a counter; and the current input value. The average is the total divided by the count at the end, with a guard for the count being zero so you don't divide by zero on no input. A strong answer names sequence, selection, and iteration explicitly, names each stored variable with its role and initial value, and flags the divide-by-zero edge case. That edge case is a boundary value — and naming it is exactly the test-data thinking we cash in two episodes from now.

QUESTION: Question five, the trap. A student writes a loop that should print the numbers five down to one but it never stops. Explain the likely cause and how to fix it.

NARRATOR: The likely cause is a logic error: the loop's exit condition depends on a counter that the body never changes — the counter stays at five, the condition "counter greater than zero" remains true forever, so the loop never terminates. This is an infinite loop. The fix is to make the loop progress toward its exit condition on every pass — decrease the counter by one inside the body so it eventually reaches zero and the condition becomes false. The mark-earning phrasing: "the control variable is not modified within the loop body, so the termination condition is never satisfied; updating it each iteration restores guaranteed termination." Name it a logic error, not a syntax error — the code runs fine, it just runs forever, and that distinction comes back when we classify error types in Chapter Four.
