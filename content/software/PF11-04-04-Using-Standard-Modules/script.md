NARRATOR: Exactly. Python ships with a huge standard library — pre-written, tested modules that do common jobs so you don't reinvent them. This is the bottom-up design idea from the structure-charts episode made real: build on proven components instead of from scratch. We'll focus on the two the syllabus and the textbook centre on: the math module and the random module. You've used modules without thinking — print and the others are built in — but now we import deliberately, and there's exam-worthy nuance in how you import and how random interacts with the purity idea from last episode.

NARRATOR: Objectives up front. By the end you'll be able to: import a module three ways and say which to prefer; use the key functions of the math and random modules; explain why the randint function differs from the range function; and explain why a function using random is hard to test and how to fix it. Let me start with importing, because there are three styles and the exam can ask you to compare them.

NARRATOR: Style one: import the whole module by name — then you call its functions through the module, writing the word math, a dot, then the function name, like math then dot then square-root. Style two: import a specific name from the module — then you call that name directly, without the prefix. Style three: import everything from the module with a star — which dumps every name the module defines into your namespace. The hook: import the module, or import the name — never import the star. Why never the star? Because it pollutes your namespace: you no longer know where a name came from, and two modules can define the same name and silently clash. Preferring "import the module" keeps it obvious that the square-root function came from the math module. The three styles and the warning are in Listing 1.

NARRATOR: Now the math module — mathematics beyond the basic operators. The functions worth knowing: square root; power, raising a number to an exponent; and the rounding trio — floor rounds down, ceiling rounds up, and truncate chops the decimal toward zero. There are trigonometric functions, which work in radians, so you convert degrees to radians first; and logarithm functions. And the constants: pi, and Euler's number e. Listing 2 puts these to work in real formulas — the distance between two points, and compound interest, which uses the power function for the exponent. Compound interest: a thousand dollars at five percent, compounded monthly for three years, comes to one thousand, one hundred and sixty-one dollars and forty-seven cents — computed with the math module's power function, not by hand.

NARRATOR: Then the random module — pseudo-random numbers for games, simulations, and test data. The key functions: the random function gives a float from zero up to, but not including, one; the randint function gives a whole number between two bounds; the choice function picks one item from a list; shuffle reorders a list in place; and sample draws several distinct items without repeating. And here is the gotcha the exam loves, connecting straight back to the range function from the control-structures episode. The randint function is inclusive of both ends — randint of one and six can return one, two, three, four, five, or six, including six. But the range function, and the related randrange, exclude their upper bound — range of one to six stops at five. So randint one-to-six is a fair six-sided die; range one-to-six is not. Last episode: range stops one before the stop. This episode: randint includes both ends. Don't mix them up. Listing 3 demonstrates the random functions.

QUESTION: Here's one to actually attempt. Pause the player. If you want to simulate rolling a normal six-sided die, do you use the randint function or the range-based randrange — and with what bounds? Work it out, then play.

NARRATOR: Use the randint function, with bounds one and six — randint of one and six — because randint is inclusive of both ends, so it can return any value from one through six, exactly like a die. If you used randrange with one and six, you'd get one through five only, missing the six, because randrange excludes its upper bound. To use randrange you'd have to write one and seven. The inclusive-versus-exclusive boundary is the whole point — and it's the same boundary-value vigilance from desk checking, now between two similar functions.

NARRATOR: Now the design issue, which ties to last episode's purity idea and is the brief's trap. A pure function depends only on its inputs and gives the same output every time. A function that calls random inside it is impure — it's non-deterministic, returning a different value each call even with the same inputs. That makes it hard to test, because you can't assert what it returns. There are two fixes, both in Listing 4. One: seed the random generator — the seed function makes the sequence reproducible, so the same seed produces the same numbers, which is how you test code that uses randomness. Seed it to repeat it. Two, the cleaner design: inject the randomness — generate the random value outside and pass it in as a parameter, leaving the core function pure and trivially testable. The trap to avoid: burying a random call deep inside a function so the whole thing becomes untestable. Pull the randomness to the edge.

NARRATOR: A worked example that pulls it together: a password generator, in Listing 5 — it builds a string by repeatedly using the choice function to pick random characters. Useful, and a nice demonstration. But here's a real security caveat that earns marks and matters: the random module is a pseudo-random generator, not cryptographically secure — its output is predictable if someone knows the seed or enough history. So for anything security-sensitive — real passwords, tokens, keys — you do not use random; you use Python's secrets module, which is designed to be unpredictable. The random module is for games, simulations, and test data; the secrets module is for security. That distinction is exactly the kind of safe-implementation thinking behind S-E-eleven-oh-seven, and it's the first taste of secure software we'll cover deeply in Year Twelve.

QUESTION: Question one. Write Python that uses a standard module to calculate the square root of a number and the area of a circle of radius five. Pause the player, write it, then play.

NARRATOR: Import the math module. The square root of a number is the math module's square-root function applied to it. The area of a circle is the math module's constant pi, times the radius squared — using either the power function or radius times radius — so pi times five squared, about seventy-eight point five four. The marks: importing math, using its square-root function and its pi constant correctly, and the area formula. Using the module rather than hand-coding a square root is the point of the question.

QUESTION: Question two. Distinguish between "import math" and "from math import star", and state which is preferred and why.

NARRATOR: "import math" brings in the module under its name, so its functions are called with the math prefix in front of each function name, making it clear where each name comes from. "from math import star" imports every name from math directly into the current namespace, with no prefix. The first is preferred because it avoids namespace pollution and name clashes — with the star import, you can't tell which module a name came from, and two modules defining the same name will silently conflict. The mark is the contrast plus the clear preference for the prefixed import on namespace-safety grounds.

QUESTION: Question three. Explain why the randint function and the range function behave differently at their upper bound.

NARRATOR: The randint function is inclusive of both its bounds — randint of one and six can return six. The range function, like randrange, is exclusive of its upper bound — range of one to six produces one through five and never six. So to cover one through six you write randint of one and six, but range of one to seven. The mark is stating that randint includes the upper bound while range excludes it, with the consequence for the values produced.

QUESTION: Question four. A function generates a random dice roll internally and returns it. Explain why this is difficult to test, and give one way to make it testable.

NARRATOR: It's difficult to test because the function is impure and non-deterministic — it uses randomness internally, so it returns a different value on each call even with the same inputs, and you cannot assert a specific expected result. One way to make it testable is to seed the random generator before calling it, so the sequence of random numbers is reproducible and the output becomes predictable for the test. An even cleaner way is to inject the randomness — generate the random number outside the function and pass it in as a parameter — which makes the core function pure and directly testable. The marks: identify non-determinism as the problem, and give seeding or injection as the fix.

QUESTION: Question five. Why should the random module not be used to generate passwords, and what should be used instead?

NARRATOR: The random module is a pseudo-random number generator: its output is deterministic given its internal state, so it is predictable to an attacker who can guess or recover the seed or observe enough output — which makes it unsuitable for anything security-sensitive. For passwords, tokens, and keys you should use Python's secrets module, which is designed to produce cryptographically secure, unpredictable values. The mark is identifying random as predictable and not cryptographically secure, and naming the secrets module as the secure alternative.
