NARRATOR: Three episodes back we started with objects and classes. The one-line version: an object bundles data and behaviour into a single unit. The data is the attributes, the nouns, the state. The behaviour is the methods, the verbs, the actions. A class is the blueprint, written once, holding no actual data, and an instance is a concrete object built from that blueprint, holding its own real values. One class, many instances. And we learned that calling a method on an object is really sending it a message: the sender asks, the receiver acts on its own data and replies. The language performs that in five steps, and we gave you a mnemonic to hold them: L-B-P-E-R. That stands for Lookup the method, Bind the receiver to self, Pass the parameters, Execute, Return. Lookup, Bind, Pass, Execute, Return. Keep that one — it's the answer to any message-passing question.

NARRATOR: Two episodes back we did encapsulation. Encapsulation is two halves, and you need both: bundle the data with the methods that control it, and restrict direct access to that data from outside. The bundling alone just describes an object — it's the restricting that makes it encapsulation. We separated the public interface, the approved methods outside code is allowed to call, from the internal state, the wiring nobody outside should touch. The interface is the buttons, the state is the wiring. And we asked: why bother hiding state at all? Four reasons, and the mnemonic is I-C-F-S: Integrity, Consistency, Flexibility, Security. Integrity, Consistency, Flexibility, Security. Write that down the second an exam asks why we encapsulate.

NARRATOR: And then last episode we finished the four behaviours of OOP. We've been calling them A-PIE the whole module — Abstraction, Polymorphism, Inheritance, Encapsulation. Have a slice of A-PIE. Last time we taught the A, the P and the I, since the E was done under encapsulation. Abstraction hides the complexity; encapsulation hides the data — cousins, different targets. Generalisation is the modelling act, spotting shared traits and capturing them in a general class. Inheritance is the implementation act, a subclass reusing a parent's attributes and methods, and we coined "generalise to model, inherit to reuse" for the distinction the exam loves to test. And polymorphism is one interface, many behaviours — one loop, each object running its own version of the same method — with Python doing it by duck typing: if it quacks, it'll do. No shared parent required.

NARRATOR: Start with the core idea, and let's make it a single clean sentence, because this is the sentence you write down first in any compare question. Here it is. In procedural programming, the data and the functions live apart. In object-oriented programming, the data walks around with its methods. Say it again, because at speed a single mention slips past: procedural — data and functions live apart; OOP — data walks with its methods. That's the whole comparison compressed into one line, and it's the line I want you to be able to produce instantly.

NARRATOR: Let me unpack both sides. Procedural programming organises a solution as a sequence of functions that operate on data, and the data is separate — it's sitting in variables, sometimes global, sometimes passed in as parameters, and the functions reach out and act on it. The design technique that goes with it is top-down decomposition: you take the big problem and break it into smaller and smaller functions until each one is simple. You did exactly this in Programming Fundamentals — that procedural code you wrote in Year 11 is the "before" picture for today. Functions on one side, data on the other, parameters carrying the data across to the functions.

NARRATOR: Object-oriented programming organises the solution around objects, and each object carries its own data and the methods that work on that data, together, in one unit. The data isn't passed in from outside every time — it lives inside the object as its state, and the methods reach into their own object to do their work. That's the bundling we called encapsulation two episodes ago. So OOP is encapsulation applied as an organising principle for the whole program: instead of functions over here and data over there, you have self-contained objects that hold their data and expose methods.

NARRATOR: Now, the most concrete way to feel the difference is to write the exact same thing both ways, and I've done that for you. In the appendix, Listing 1 shows a simple rectangle, written first procedurally and then object-oriented, side by side. In the procedural version there are three free-standing functions — one to calculate area, one to calculate perimeter, one to display the rectangle's information — and the length and the width are just two separate variables that get passed into every function as parameters. The data sits outside; the functions take it in. In the object-oriented version, there's one rectangle class. The length and the width live inside it as attributes, set when you create the rectangle, and the same three operations — area, perimeter, display — become methods on the object that reach into their own length and width. You don't pass the dimensions around any more; the object already holds them. Same behaviour, same arithmetic, two completely different ways of organising it. Listing 1 is the picture to carry in your head for the rest of this episode.

QUESTION: Looking at those two versions of the rectangle — which one is better?

NARRATOR: That's the trap, and I want you to feel it bite. The honest answer is: for a single rectangle that you compute once and throw away, neither is better, and the procedural one is arguably simpler — fewer moving parts, nothing to set up. The point of showing them side by side is not to crown a winner. It's to show that the same problem genuinely has two valid shapes, and which shape is better depends entirely on the problem around it. A weak exam answer says "OOP is better because it's more organised." A strong answer says "it depends on the scale and nature of the problem, and here's how I'd decide." Hold that thought — we're building to it.

NARRATOR: Let's get the trade-offs straight, because a compare question wants structure, not a vibe. There are six dimensions the syllabus material lines them up along, and I'll give you a memory hook in a moment. The first is organisation. Procedural organises code as functions operating on data; OOP organises code as objects bundling data and methods. Second, data handling. In procedural, data is global or passed as parameters — it's out in the open. In OOP, data is encapsulated inside objects — it's protected and local to the object that owns it. Third, the problem approach. Procedural is top-down decomposition: split the task into functions. OOP tends to be more about identifying the objects and how they interact. Fourth, code reuse. Procedural reuses through libraries of functions. OOP reuses through inheritance and composition — remember inheritance, the "is-a" relationship from last episode. Fifth, modularity. Procedural modularity is separate functions; OOP modularity is classes with clear interfaces — that public interface idea from encapsulation. And sixth, state management. Procedural keeps state in external or global variables; OOP keeps state inside the object, managed internally.

NARRATOR: Six dimensions is a lot to hold, so anchor them on the single sentence you already know. Every one of those six is just a consequence of "data and functions live apart" versus "data walks with its methods." Organisation, data handling, reuse, modularity, state — they all flow from that one split. So if you can produce the sentence, you can reconstruct the table. That's your memory hook: don't memorise six rows, memorise the one sentence and derive the rows. The full comparison is laid out as a reference in Listing 2 in the appendix if you want to read the dimensions lined up.

NARRATOR: Now the part that earns the top band: when does each one actually fit? Let's do procedural first, because this is the side students neglect, and neglecting it is exactly what caps an answer at a middle band.

NARRATOR: Procedural is the better choice for simple, self-contained problems. Three clear cases. First, a one-shot calculation. If you're computing a tax — take an income, multiply by a rate, subtract it — that's a function. Wrapping it in a class adds ceremony and buys you nothing. Listing 3 in the appendix shows that tax calculation as two small procedural functions, and it would be genuinely worse as a class. Second, linear data processing — taking a list, cleaning it, filtering it, transforming it through a pipeline of functions. That's procedural's home turf. Third, mathematical and algorithmic problems. The classic example is factorial — say it "fac-TOR-ee-al", the product of all whole numbers up to some number — or the Fibonacci sequence — say it "fib-oh-NAH-chee". These are pure functions: input goes in, output comes out, there's no state to carry, no entity to model. Listing 4 shows factorial and Fibonacci as plain recursive functions, and forcing them into objects would be pure overhead. So: tax calc, list processing, factorial, Fibonacci — procedural wins.

NARRATOR: Here's a model answer. A one-off temperature conversion — Celsius to Fahrenheit — is best kept procedural, because it's a single mathematical operation with a clear input and output and no state or entity to model, so a class would add complexity without any benefit. Notice the shape of that answer: name the scenario, then justify with the actual reason — no state, no entity, simple input-output. That justification is the mark. "Because it's simpler" on its own is a weak answer; "because there's no state or real-world entity to model, so the object machinery buys nothing" is the strong one. That contrast — the weak version next to the strong version — is the thing to internalise.

NARRATOR: Now OOP's cases, and these are where it genuinely shines. First, modelling real-world entities. When your problem is full of things — students, teachers, courses — each with its own data and its own behaviours, objects fit like a glove. Listing 5 shows a student and a course: a student holds a name, an identifier, a list of grades, and knows how to add a grade and compute its own average; a course holds its enrolled students and computes the class average by asking each student for theirs. The data and behaviour belong together per entity — that's the signal. Second, complex state management. A game character that has health, a level, experience, an inventory, and changes all of those as the game runs — that tangle of evolving state is far cleaner held inside an object than scattered across loose variables. Third, systems with multiple interacting components. A bank account that tracks its balance and history, and a bank that holds many accounts and transfers money between them — Listing 6 shows exactly that, a bank account class and a bank class working together. Multiple objects collaborating, each guarding its own data, talking by messages — that's OOP's sweet spot, and it's the same collaboration idea from the very first episode.

NARRATOR: So here's a clean way to decide, and it's worth saying twice because it's the heart of the dot-point. Reach for OOP when the problem has entities with state and behaviour that belong together, or many components that interact. Stay procedural when the problem is a straightforward calculation, a linear data pipeline, or a pure algorithm. Entities and interaction pull you toward objects; simple input-output pulls you toward functions.

NARRATOR: Now let me give you a symptom you can actually spot in code — a tell that you've outgrown procedural and a class is crying out to be born. Here it is, and it's a great line to drop in an exam: a giant parameter list is procedural crying out for a class. Let me explain the image. Listing 7 shows a battle function in a game where the player's name, health and level, and the enemy's name, health and level, are all separate loose variables, so the battle function has to take six parameters to do anything. Six parameters. That's the smell. When you see a function dragging a long train of related parameters around, those parameters are data that travels together, and data that travels together is begging to be wrapped in an object. The player's three values are one player object; the enemy's three are one enemy object. Suddenly the battle takes two parameters, a player and an enemy, not six loose values. So whenever an exam stimulus shows you a function with a bloated parameter list, you've been handed the answer: that's procedural crying out for a class. Say it: a giant parameter list is procedural crying out for a class.

NARRATOR: That symptom leads us straight into the practical skill the exercises test — converting procedural code into object-oriented code. There's a three-step recipe, and I want you to hold all three, because the exam asks you to do this and asks what the first step is. Here's the recipe. Step one: find the data that travels together. Step two: wrap that data in a class. Step three: turn the functions that act on that data into methods of the class. Find the data that travels together, wrap it in a class, turn the functions into methods. Three steps.

NARRATOR: Let me walk it on a real example, because the steps are easy to recite and easy to get wrong. Listing 8 in the appendix is the conversion, before and after. The before is procedural: a customer's name and email are loose variables, there's a list of the customer's orders sitting separately, and there are free functions — one to add an order to a list, one to total up what's been spent, one to send an email. The data is scattered and the functions take that scattered data as parameters.

NARRATOR: Step one, find the data that travels together. Look at it: the name, the email, the orders — these three always describe the same customer. They move as a group. That's your signal. Step two, wrap them in a class — a customer class, capital C, one word, holding the name, the email and the orders as its own attributes, set when you create the customer. Step three, turn the functions into methods. The add-an-order function becomes an add-order method on the customer that appends to the customer's own list. The total-spent function becomes a method that sums the customer's own orders. The send-email function becomes a method that uses the customer's own email. After the conversion you don't pass the email into a send function — you ask the customer to send, and it already knows its own email. The after side of Listing 8 shows exactly that. Much more intuitive: you tell the customer to do things, instead of operating on the customer from outside.

NARRATOR: If you'd rather rehearse that recipe in exam pseudocode — the form you'll actually write under exam conditions — Listing 10 in the appendix writes the three-step conversion out in NESA style: a loop to find the variable groups, a loop to wrap each group in a class with its attributes, and a loop to move each function in as a method. And Listing 11 sits the two versions of one operation side by side in pseudocode — the total-spent calculation as a procedural routine that takes the orders list as a parameter, then the very same logic as a method that reaches into the object's own orders. QUESTION: That conversion looked almost mechanical — find data, wrap it, convert functions. Is it actually that simple?

NARRATOR: No, and this is the trap I most want you to dodge. Conversion is not mechanical. The hard part is step one — finding the right data groupings — and that takes judgement, not a recipe. Group the wrong things and you get worse code than you started with: a class that's secretly two unrelated things jammed together, or data split across objects that should have been one. In the customer example it was obvious because name, email and orders clearly describe one thing. But in a messy real system, deciding which variables truly travel together is a design decision, and there's no rule that makes it for you. So if an exam asks you to convert, do the grouping thoughtfully and be ready to justify why those particular pieces of data belong together. A strong answer names the data that travels together and explains the grouping; a weak answer just says "make a class" and starts typing. Believing conversion is a mechanical find-and-replace is the second classic trap, right alongside believing OOP is always better.

NARRATOR: Let me say that first trap out loud one more time, plainly, because it's the single most common mistake on this dot-point and it costs real marks. OOP is not always better. A student who writes "object-oriented programming is superior because it is more modern and more organised" has just told the marker they don't understand the trade-off. The whole point of comparing two paradigms is that each fits different problems. The simple, throwaway calculator from Listing 9 in the appendix — a tiny add-and-subtract — is fine, in fact better, as plain functions; wrapping it in a calculator class is over-engineering, more code for no gain. So the mark-earning instinct is balance: name what OOP is good for, name what procedural is good for, and say the choice depends on the problem. Never crown a universal winner.

NARRATOR: Model answer. QUESTION: Now the big one, and the one most likely to appear. Six marks. Compare procedural programming with object-oriented programming. Pause the player, write a full answer as if it's the real exam, then play to check it against the model.

NARRATOR: Here's a six-mark model answer. Open with the core difference: procedural programming organises a solution as functions operating on separate data, using top-down decomposition, while object-oriented programming organises the solution around objects that bundle data and methods together. Then compare across dimensions — this is what the verb "compare" demands, both similarities and differences, structured. Data handling: procedural exposes data as global or parameter-passed variables, whereas OOP encapsulates data inside objects. QUESTION: One more, applied. Four marks. A team is building a school management system with students, teachers and courses that need to be tracked, related and updated over time. Justify the choice of programming paradigm for this scenario.

NARRATOR: Model answer. Object-oriented programming is the appropriate paradigm for this system, because the problem is centred on real-world entities — students, teachers and courses — each of which has its own data, such as a student's name, identifier and grades, and its own behaviours, such as enrolling in a course or calculating an average. Bundling each entity's data with its methods through encapsulation keeps related information together and protected, and modelling the relationships between objects — a course holding its enrolled students — captures the interactions the system needs. The system also has ongoing, changing state across many interacting components, which OOP manages far more cleanly than scattered procedural variables would, and it scales better as the system grows. Notice the move: identify the entities, point to their state and behaviour, point to the interactions, and tie each observation to a named OOP strength — encapsulation, modelling relationships, state management, scalability. That's a justify answer: a claim, then reasons anchored in the scenario. And if the scenario had instead been "convert a single temperature" or "find the largest number in a list," the correct justification would have run the other way, toward procedural — always let the nature of the problem drive the choice, never a blanket preference.
