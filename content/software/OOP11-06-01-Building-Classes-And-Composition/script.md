NARRATOR: So. Defining a class versus instantiating it. You know this as a programmer, but the syllabus framing is worth nailing because markers test the vocabulary. A class is a blueprint. It's written once. It describes what attributes and methods objects of that type will have — but it holds no data itself. Instantiation is the act of building one concrete object from that blueprint — an *instance* — and that instance holds its own actual values. One class, many instances. The blueprint for a phone is not a phone; the phone in your pocket is the instance. We hammered this in the very first OOP episode and it's still the number-one beginner trap: saying "the bank-account class has a balance of a thousand dollars" is wrong. The *class* defines that there is a balance attribute. The *instance* — Alice's specific account — holds the thousand dollars.

NARRATOR: Now the constructor — and this is where today's real teaching starts. In Python the constructor is the method spelled with a double-underscore "init" double-underscore. Out loud we say "dunder init" — dunder is just shorthand for "double underscore". It runs automatically the moment you instantiate an object, and its job is to set up the object's initial state: take the arguments you pass in, and assign them to the object's attributes. Plain enough. But here's the part that earns marks and that beginners skip: a good constructor does not just *store* what it's given. It *validates* it first. It refuses to build a broken object.

NARRATOR: Let me make that concrete with the worked example we'll keep coming back to: a bank-account class. The full code is in Listing One in the supplementary materials, but you'll learn it fine just listening. The constructor takes three things: an account number, an owner name, and an optional starting balance that defaults to zero. A naive constructor just slaps those three values onto the object and moves on. A *strong* constructor checks them first. Is the account number empty or just whitespace? Reject it — raise a value-error with a clear message, "account number cannot be empty". Is the owner name empty? Reject it. Is the starting balance negative? Reject it — you cannot open an account owing money before it exists. Only once all three checks pass does the constructor store the values and set up an empty transaction history.

NARRATOR: And because this is a build-outcome chapter, you may have to write that constructor in exam pseudocode too — the NESA-style version, with the validation checks up front, is in Listing Seven if you want to rehearse the exact form: a sequence of "if the value is bad, raise an error" guards, *then* the assignments using the left-arrow. Same shape as the Python, exam syntax.

NARRATOR: Why does this matter so much? Remember the invariant idea from the encapsulation episode — a condition that must always be true for an object to be in a valid state. For a bank account, "balance is never negative" is an invariant, and "every account has a real owner" is an invariant. Validation in the constructor is how you *guarantee the object is born valid*. If you skip it, you can construct a bank account owned by an empty string, with minus five hundred dollars in it, and every method downstream now has to cope with garbage. The constructor is your first and best line of defence. This is the same instinct as the validating setters from encapsulation — never trust a raw value — and it's the exact same instinct that becomes input validation and defending against injection attacks in Secure Software Architecture next year. Validate at the boundary, every time.

QUESTION: Here's a weak answer and a strong answer. A weak answer to "why validate in the constructor" says: "so the program doesn't crash." Is that enough for the marks?

NARRATOR: It's the band-four version. It's not *wrong*, but it's shallow and it doesn't use the vocabulary. The strong answer says: "Validation in the constructor enforces the class's invariants, so an object can never be constructed in an invalid state. It fails fast, raising a clear value-error at the point of the mistake, rather than silently storing bad data that corrupts the program later." Hear the difference? Invariant, valid state, fail fast, at the boundary. That's the mark-earning phrasing. Say "enforces invariants and fails fast", not "stops it crashing".

NARRATOR: One more piece of the single-class toolkit before we get to the big idea. Methods. Two rules the syllabus cares about. First, single responsibility: each method does one thing well. Second, meaningful names: the name should say exactly what the method does. This is a place students throw away marks in code questions, so let me contrast it. A poor method name is something like "do-money" on an account — do *what* with money? Or "check" with a password — check what? Or "test" on a validator — test what? A good method name is "withdraw", "deposit", "is-valid-email", "authenticate". The name is a tiny contract: it tells the caller what will happen. In an exam, vague method names are a flagged pitfall — name your methods as precise verbs and you signal that you actually understand single responsibility.

NARRATOR: There's also the string representation method — double-underscore "str", which we say as "dunder str". It defines what your object looks like when it's printed or turned into a string. Without it, printing an object gives you that useless "object at memory address" gibberish. With it, you decide: printing a bank account could say "Account A-C-C-double-oh-one, owner Alice Johnson". It's a small thing but it's good practice and it shows up in cohesive, well-built classes. Dunder init builds the object; dunder str describes it.

NARRATOR: Okay. The centrepiece. Composition over inheritance. This is the most important idea in the episode and the one most likely to anchor a big-mark question, so we're going to build it slowly and from the ground up.

NARRATOR: Start with the relationship. Inheritance, from the Chapter Five episode, is the *is-a* relationship. You make a subclass that *is a kind of* its parent and reuses the parent's attributes and methods — a sports car *is a* car *is a* vehicle. Composition is the *has-a* relationship. Instead of inheriting from a parent, you *build* a complex object by giving it other objects as attributes. A car *has an* engine. A car *has* wheels. The car doesn't inherit from engine — that would be nonsense, a car isn't a kind of engine. The car *contains* an engine. That's composition. Here's your mnemonic, and it's a module-wide one you reuse verbatim every time this comes up: "is-a versus has-a — favour has-a when unsure." Inheritance is is-a; composition is has-a; and when you're genuinely not sure which to reach for, the professional default is composition.

NARRATOR: Let me give you the spine example. It's in Listing Two. A car is composed of an engine and a set of wheels. You build an engine object — say a four-hundred-horsepower petrol engine. You build a wheels object — four wheels, eighteen inch. Then you construct the car and *hand it* the engine and the wheels. The car stores them as attributes: the car *has-a* engine, the car *has* wheels. When you tell the car to start, the car doesn't know how to start an engine itself — it forwards the message to its engine object and says "engine, you start". That forwarding is the heart of composition: the car *delegates* to the components it contains. Each component is a small, focused, independently-built object, and the car wires them together into something bigger.

QUESTION: Hang on — couldn't you just make Car inherit from Engine to reuse the start method? Why is that wrong?

NARRATOR: Great question, because it's exactly the trap. Inheriting Car from Engine would be claiming a car *is a kind of* engine. It isn't. The is-a test fails. A car *has* an engine. If the is-a sentence sounds absurd when you say it out loud — "a car is an engine" — that's your signal that you've reached for inheritance where composition fits. Run the sentence test every time: say "X is-a Y" and "X has-a Y" out loud, and use whichever one is actually true. A savings account is-a bank account: inheritance is fine. A car has-a engine: composition. Get this test into your head and you'll never confuse the two under exam pressure.

NARRATOR: Now — *why* favour composition? This is the "give two benefits of composition over inheritance" question, four marks, and there's a four-part mnemonic for the benefits that I want you to learn as a single phrase: composition is "runtime-flexible, loosely coupled, independently testable, no diamond problem." Let me unpack all four, because each one is a sentence you can write for marks.

NARRATOR: One: runtime-flexible. With inheritance, the relationship is fixed when you write the code — a subclass is permanently bound to its parent. With composition, you can swap a component *while the program is running*. You can give the car a different engine object at runtime. Inheritance is decided at compile time and frozen; composition is decided at construction time and changeable. Two: loosely coupled. The components are developed independently — the engine team and the wheels team never have to know about each other, they just have to honour their interfaces. Change the internals of the engine and the car doesn't care, as long as "start" still means start. That's the interface-as-contract idea from the collaboration episode, applied to building objects. Three: independently testable. Because each component is its own small object, you can test the engine on its own, the wheels on their own, without dragging the whole car into the test. That feeds straight into the testing episode later in this chapter — small cohesive components are testable components.

NARRATOR: And four — the diamond problem, no diamond problem. This one's worth understanding properly because it's the killer technical argument. Some languages let a class inherit from two parents at once — multiple inheritance. The trouble is the diamond: imagine class D inherits from both B and C, and both B and C inherit from a common A. Now D inherits from A by two different paths. If A's method got overridden differently in B and in C, which version does D get? The hierarchy is genuinely ambiguous — that's the diamond problem, named for the diamond shape the class diagram makes. Inheritance trees can tie themselves in this knot. Composition simply doesn't have it: you're not inheriting along multiple paths, you're just holding objects as attributes, so there's no ambiguity to resolve. So: runtime-flexible, loosely coupled, independently testable, no diamond problem. Four benefits, one phrase, learn it as a chant.

NARRATOR: Let's go bigger with the composition idea. Listing Three is a laptop. A laptop is composed of a processor, a display, and a battery — three separate component objects, each with its own job. The processor knows how to start and stop. The display knows how to turn on and off. The battery knows its charge level and how to drain and recharge. The laptop *has-a* all three, and when you power the laptop on, it coordinates them: it checks the battery isn't flat, starts the processor, turns on the display, and drains a bit of battery for the boot. The laptop is a *conductor*, not a one-man band. Each component is a cohesive little object; the laptop composes them into a working machine. Notice what you could do — swap in a bigger battery object, a sharper display object — without touching the laptop's own code at all. That's the flexibility we keep talking about, made concrete.

NARRATOR: Now the technique that makes composition really sing: dependency injection. Don't be scared of the name, it's simpler than it sounds. "What is dependency injection?" is a short exam question and here's the clean answer. A dependency is just an object that another object needs to do its job. Injection means: instead of an object *building its own* dependencies internally, you *pass them in* from outside — usually through the constructor. You inject the dependency. That's it. The car didn't build its own engine inside itself; you built the engine outside and handed it in. That handing-in is dependency injection.

NARRATOR: Listing Four is the example that shows why this is powerful: a shopping cart with an injected logger. A shopping cart needs to log what happens — items added, items removed, totals calculated. Now, the cart *could* hardcode "write to a file" inside itself. But then it's stuck logging to a file forever. Instead, we *inject a logger*: the cart's constructor takes a logger object, stores it, and whenever something happens, the cart says "logger, log this message" — it doesn't know or care *how* the logger logs. So you can build a console-logger that prints to the screen, and a file-logger that writes to a file, and hand either one to the cart. Same cart, different behaviour, decided at construction time. Want a silent cart for testing? Inject a do-nothing logger. The cart never changes.

QUESTION: This sounds familiar. Where have we seen "swap one object for another that honours the same interface" before? Pause and think back a couple of episodes.

NARRATOR: You've got it — this is the mock from the collaboration episode, all grown up. Remember the mock payment-processor that honoured the same interface as the real one, so you could build and test against it before the real thing existed, and then the real class dropped in unchanged? That drop-in-unchanged trick *is* dependency injection plus polymorphism. The console-logger and the file-logger are interchangeable because they share the same interface — they both have a "log" method — so the cart, which only ever calls "log", can't tell them apart. That's polymorphism, the P in A-PIE: one interface, many implementations. Dependency injection is *how* you supply the implementation; polymorphism is *why* the swap works. Composition, injection and polymorphism are three views of the same beautiful idea — program to an interface, not a fixed thing.

NARRATOR: Now let's hit cohesion head-on, because it's both a syllabus word and the thing that ties this all together. Cohesion means a class has a single, well-defined purpose, and all its methods work together to support that one purpose. High cohesion: good. Low cohesion: a class doing five unrelated jobs — and that's a flagged trap. Let me give you the classic low-cohesion disaster, it's in Listing Five. Picture a user-account class that does *everything*: it stores the user's data and password, *and* it sends welcome emails, *and* it saves itself to a file, *and* it saves itself to a database, *and* it logs login attempts. Five responsibilities crammed into one class. That's the "god class" we warned about in the design-process episode. It's a nightmare: you can't reuse the email logic without dragging the whole user along; you can't test the database code in isolation; a change to logging risks breaking the file-saving. Everything is tangled.

NARRATOR: The fix is to split it along its responsibilities — and notice this is R-R-C-I in action, the design pipeline from two episodes ago, giving each responsibility its own home. You break that monster into four cohesive classes. A user class that just holds user data and checks passwords. An email-service class that just sends emails. A user-repository class that just handles saving and loading user data. And a login-logger class that just records login attempts. Four classes, each with one job, each independently testable, each reusable. And then — here's the lovely part — you compose and inject them: the higher-level code holds a user, an email-service and a repository, wiring the cohesive pieces together. Cohesion gives you the small focused pieces; composition assembles them into a working system. That's the whole philosophy of this episode in one move: build small cohesive objects, then compose them.

NARRATOR: Let me close the loop on something we promised in Chapter Five. Back in the inheritance episode we built a vehicle hierarchy: a vehicle parent, with car and motorcycle as subclasses that inherited from it and overrode an accelerate method. That was a perfectly good *teaching* example for inheritance. But it's also a great example of where inheritance can get rigid, and you can re-cast it with composition. Instead of car *being* a vehicle by inheritance, you give a vehicle a motion-system component that handles speed and acceleration, an info component for make and model, and a features component for the car-specific bits like the number of doors. Now a car *has-a* motion system rather than *being* a vehicle. The payoff: you can swap the motion system at runtime, reuse the motion system in something that isn't a vehicle at all, and test the motion system completely on its own. Same problem, composed instead of inherited — more flexible, more testable. That's not to say inheritance is *wrong* here; it's to show you the same design done both ways, so you can argue the trade-off in an exam.

NARRATOR: Now, a quick true story, because reuse is the dark side of all this and it's worth a scar. Composition and inheritance are both about *reuse* — building new things from existing pieces. Reuse is powerful. It's also where catastrophes hide. In June nineteen-ninety-six, the European Space Agency launched the very first Ariane Five rocket — Flight five-oh-one. About thirty-seven seconds after lift-off, it veered, broke up, and self-destructed. Around three hundred and seventy million dollars, gone in under a minute. The cause? Reused software. The Inertial Reference System — the component that tells the rocket which way is up — was lifted straight from the older, slower Ariane Four, and *never re-tested against the new rocket's flight profile*. Ariane Five flew faster and built up sideways velocity much more quickly. Deep in that reused code, a sixty-four-bit floating-point number representing that velocity was converted into a sixteen-bit integer. On Ariane Four that number was always small enough to fit. On Ariane Five it wasn't — it overflowed, the conversion failed, the guidance system crashed, the backup crashed for the identical reason, and the rocket tore itself apart.

NARRATOR: Here's the lesson, and it's exactly today's lesson. The component was *reused without re-checking that it fit the new context*. Whenever you compose an object from a part you didn't write — or inherit from a parent someone else built, or inject a dependency you grabbed off the shelf — you are *trusting its contract*. Reuse is powerful, but you must re-check the contract every time the context changes. A component that was correct in its old home can be lethal in a new one. We'll tell the full Ariane story properly in its own episode later, but plant the moral now: reuse, then re-verify. Don't reuse and assume.
