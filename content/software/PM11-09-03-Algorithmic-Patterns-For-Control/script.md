QUESTION: Start with the big one. Think about a washing machine or a set of traffic lights — they're clearly in one distinct mode at a time, and they switch between modes. What's the natural way to write that in code, rather than a pile of tangled if-statements?

NARRATOR: A state machine — the single most important control pattern in this course. A state machine models a system as a set of distinct states with defined rules for moving between them. It has four parts, and here's your hook — S-T-E-A: States, the modes the system can be in, like idle, running, error; Transitions, the allowed moves between states; Events, the triggers that fire a transition — a button press, a sensor reading, a timer expiring; and Actions, what happens on entering, leaving, or while in a state — enable the motor, sound an alarm. States, Transitions, Events, Actions — S-T-E-A. The reason it beats a tangle of if-statements is that it's clear, it's predictable, it's easy to test, and — crucially — it's easy to modify.

NARRATOR: Listing 1 develops one: a traffic light as a state machine. Three states — red, green, yellow — each with a duration, and a transition table saying red goes to green, green to yellow, yellow to red. The event is the timer running out; when a state's time is up, it transitions to the next. Run it and you get exactly the cycle you'd expect: red, red, green, green, green, yellow, and round again. That's the develop step — a clean, predictable machine from a tiny table of states and transitions, no tangle of conditionals.

QUESTION: Now the second verb — modify. Suppose the council wants a pedestrian button that cuts the green short when someone's waiting. In a tangle of if-statements that's a nightmare. In a state machine, how much has to change?

NARRATOR: Almost nothing — and that's the whole point. Listing 2 is the modified machine: it adds one rule, in one place — if we're in green and a walk request is pending, end green at the next tick. Everything else is untouched. Run it and the difference is clear: normally green lasts its full three ticks, but with the walk request pressed, green ends early and the lights move to yellow then red much sooner. One localised change, a genuine behaviour change, and no risk to the rest of the logic. That's why the pattern matters: develop once, and modifying is a small, safe, local edit rather than a rewrite. That contrast — a clean state machine versus a tangle of if-statements you're scared to touch — is a classic exam point.

QUESTION: Pause the player and develop one yourself. Sketch a state machine for an automatic garage door. Name its states, and for two of them give the event that triggers a transition out. Work it out, then play.

NARRATOR: Here's a solid answer. States: Closed, Opening, Open, Closing — and a Stopped or Blocked state for safety. Transitions and their events: from Closed, the event "remote button pressed" transitions to Opening; from Opening, the event "fully-open sensor triggered" transitions to Open; from Open, "timer expired" transitions to Closing; from Closing, the event "safety beam broken" transitions to Stopped or back to Opening. The marks come from naming distinct states and pairing a transition with the specific event that fires it — and including a safety state shows real understanding. Notice the fail-safe from last episode is just a state in the machine: an Error or Blocked state the system can always jump to.

NARRATOR: State machines are the headline, but know a few other patterns so you can pick the right one. First, threshold control with hysteresis — and this is examinable. A simple threshold acts when a reading crosses a limit: heater on below twenty degrees, off above. The problem is, right at twenty degrees, tiny fluctuations make it flip on-off-on-off rapidly — chattering, which wears out the hardware. Hysteresis fixes it with two limits instead of one — a deadband: turn the heater on at nineteen, off at twenty-one. Now it can't chatter, because once it's on it stays on until clearly past the target. Two limits, not one, stops the chatter. Second, timed sequences — fixed steps on a clock, like an open-loop wash cycle. Third, event or interrupt handling — respond the instant something happens rather than constantly polling for it. And fourth, scheduling — when you've got many tasks, you coordinate them, usually priority-based, so the most critical task, like safety monitoring, runs first and most often. NARRATOR: Now exam-style questions. Pen down, attempt before the model answer.

QUESTION: Question one. Define a state machine and identify its key components. Three marks.

NARRATOR: A state machine is a control pattern that models a system as a set of distinct states with defined rules for transitioning between them in response to events. Its key components are states — the modes the system can be in; transitions — the allowed moves between states; events — the triggers that cause a transition; and actions — the operations performed on entering, leaving, or while in a state. For three marks, define it as states-plus-transitions and name the components — states, transitions, events, and actions.

QUESTION: Question two. Develop a state machine for a microwave oven: describe its states and the transitions between them. Pause, write, then play.

NARRATOR: A microwave can be modelled with states such as Idle, Cooking, Paused, and Finished. Transitions: from Idle, the event "start pressed with the door closed" goes to Cooking; from Cooking, "door opened" goes to Paused, and "timer reaches zero" goes to Finished; from Paused, "door closed and start pressed" returns to Cooking; from Finished, "door opened" returns to Idle. A safety rule is that cooking can never occur while the door is open — modelled by the door-opened event always leaving the Cooking state. The marks come from naming sensible distinct states and giving transitions each tied to a specific event, including the door-safety behaviour.

QUESTION: Question three. Explain how a state machine makes a control program easier to modify than a long sequence of if-statements.

NARRATOR: In a state machine, behaviour is organised by state, with transitions defined explicitly, so a change usually means adding or editing a single state or transition in one place, leaving the rest of the logic untouched and low-risk. A long chain of if-statements interleaves all the conditions together, so a change can have unexpected effects elsewhere and is hard to test. For example, adding a pedestrian button to a traffic-light state machine is one new transition rule, whereas in tangled conditionals it might require changes scattered throughout. The mark is recognising that the explicit, localised structure of states and transitions makes changes safer and more contained.

QUESTION: Question four. A thermostat using a single temperature threshold rapidly switches the heater on and off near the setpoint. Explain why, and how hysteresis solves it.

NARRATOR: With a single threshold, once the temperature is near the setpoint, tiny fluctuations push the reading just above and just below the limit repeatedly, so the heater rapidly switches on and off — chattering — which is inefficient and wears out the hardware. Hysteresis solves it by using two thresholds with a gap between them, a deadband: the heater turns on at a lower temperature and off at a higher one, so once it switches it stays in that state until the temperature clearly crosses the other limit, eliminating the rapid switching. The mark-earning points: small fluctuations around one limit cause the chatter, and two separated thresholds prevent it.
