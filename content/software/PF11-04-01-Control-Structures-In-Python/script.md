NARRATOR: Objectives up front. By the end you'll be able to: map every NESA pseudocode construct to its Python form and back; explain how Python marks code blocks; use the range function correctly, including its boundary; and spot the two classic control-flow bugs. Let me start with the single biggest difference between pseudocode and Python, because it's where the marks and the bugs both live.

NARRATOR: In NESA pseudocode, a block is closed with an explicit keyword — IF with ENDIF, WHILE with ENDWHILE, FOR with NEXT. Python has none of those closers. Instead, Python uses indentation: the lines indented under a statement are its block, and the block ends when the indentation goes back out. There's a colon at the end of the line that opens a block — after the condition of an if, or a while, or a for — and then everything indented beneath it belongs to that block. The hook: in Python, the indent is the block. No ENDIF, no ENDWHILE — you line the code up, and the alignment is the structure. This is liberating and dangerous: liberating because it's clean, dangerous because if your indentation is wrong, your logic is wrong, and Python won't always warn you. That's trap one, and we'll come back to it.

NARRATOR: Now the mapping itself, construct by construct — the full table is in Listing 1. Sequence is trivial: statements run top to bottom, one per line, no keywords needed. Assignment: pseudocode's SET x equals value, or the left-arrow, becomes simply x equals value. Input and output: pseudocode's INPUT becomes Python's input function — and a crucial detail, the input function always gives you a string, so if you want a number you wrap it in the int or float conversion, exactly the type-conversion point from the data-types episode. Pseudocode's OUTPUT becomes the print function.

NARRATOR: Selection: pseudocode's IF, condition, THEN, body, ENDIF becomes if, condition, colon, then the indented body — no THEN, no ENDIF. The chain IF, ELSE IF, ELSE becomes if, then the keyword Python spells e-l-i-f and pronounces "else-if", then else, each with a colon. And the logical words are almost identical: pseudocode's AND, OR, NOT are Python's lowercase and, or, not. Listing 2 is the grade calculator written this way — a function that takes a score and returns a letter with an if, else-if, else chain, using our usual scale: ninety and up is A, eighty B, seventy C, fifty D, else F. Same first-match-wins behaviour from the control-structures episode, now in real code.

NARRATOR: Iteration is where the one genuine gotcha lives. Pseudocode's WHILE, condition, DO, body, ENDWHILE becomes while, condition, colon, indented body — straightforward. But the counted loop is where people slip. Pseudocode's FOR i equals a TO b is inclusive — it runs with i equal to b on the last pass. Python's for loop runs over the range function, and the range function stops one short of its end value. So range from one to six gives you one, two, three, four, five — not six. The end value is excluded. Therefore pseudocode's FOR i equals one TO five becomes, in Python, for i in range from one to six — you add one to the upper bound to get the inclusive behaviour. The hook: range stops one before the stop. Listing 3 demonstrates every form of the range function so the boundary is concrete — range with one argument starts at zero, range with two is start and stop, range with three adds a step, and a negative step counts down.

QUESTION: Here's one to actually attempt. Pause the player. In Python, what list of numbers does the range function from zero to ten with a step of two produce? And what does range from one to six produce? Work it out, then play.

NARRATOR: Range from zero to ten, step two: zero, two, four, six, eight — it stops before ten, so ten is not included. And range from one to six: one, two, three, four, five — again, six is excluded. Both show the same rule: the stop value is never reached. If you wanted to include ten, you'd write the stop as eleven. Range stops one before the stop. That off-by-one at the boundary is exactly the boundary-value thinking from desk checking, now baked into a language feature.

NARRATOR: Let's do a full conversion, because that's the exam task. Take a number-guessing game in pseudocode: set a secret number; while the guess is not the secret, read a guess, increment the attempts, and if the guess is too low say so, else if too high say so, else say correct; then report the attempts. The Python is almost a one-to-one transcription, in Listing 4: a while loop on "guess not equal to secret", an if, else-if, else chain inside it, the attempts counter incremented each pass. The pseudocode's ENDWHILE and ENDIF simply vanish — the indentation replaces them. That near-perfect correspondence is the point: NESA pseudocode is designed to map cleanly to code, so a clean conversion is mostly mechanical — keep the structure, drop the closers, mind the colons and the indentation.

NARRATOR: Now the two bugs the exam plants, both in iteration. Trap one, indentation — already flagged. If you put a line at the wrong indentation level, it joins the wrong block. A classic: the line that updates the loop counter accidentally sits outside the while loop instead of inside it. The logic looks right, the indentation is wrong, and the behaviour is broken. In Python the indentation is not cosmetic — it is the control flow. Trap two, the infinite loop, straight from the control-structures episode: a while loop whose condition never becomes false because the body never changes the variable the condition depends on. The counter that's meant to count down but is never decremented; the "while not done" that never sets done to true. Listing 5 shows the broken countdown and the fix — decrement the counter each pass so the loop makes progress toward its exit. Both bugs are about the loop body: is it correctly inside the loop, and does it move the loop toward ending?

One: the three control structures map cleanly from NESA pseudocode to Python — sequence is just lines; SET becomes equals; INPUT becomes the input function, converted to a number when needed; IF-THEN-ENDIF becomes if with a colon and indentation; ELSE IF becomes else-if, written e-l-i-f; WHILE becomes while; FOR i equals a TO b becomes for i in range from a to b-plus-one. NARRATOR: Now the exam-style questions. Pen down, and when I say pause, attempt it before the model answer.

QUESTION: Question one. Convert this pseudocode to Python: "FOR i equals one TO five, OUTPUT i, NEXT i." Pause the player, write it, then play.

NARRATOR: In Python: for i in range from one to six, colon, and on the next line, indented, print of i. The marks are three: using a for-loop over the range function, getting the boundary right with six as the stop so that five is included, and indenting the body under the colon. The classic error here is writing range from one to five, which would stop at four and miss the five — range stops one before the stop.

QUESTION: Question two. Explain how Python knows where an if-statement's block begins and ends, and contrast this with NESA pseudocode.

NARRATOR: In Python, the block begins after the colon at the end of the if-line, and consists of the lines indented beneath it; the block ends when the indentation returns to the previous level. There is no explicit end keyword. In NESA pseudocode, by contrast, the block is bounded explicitly — it begins after THEN and ends at ENDIF — and indentation is only for readability. The mark is the contrast: Python uses indentation as the actual block structure, whereas pseudocode uses explicit ENDIF and treats indentation as cosmetic.

QUESTION: Question three. What does the range function from two to ten with a step of three produce, and why?

NARRATOR: Two, five, eight. It starts at two, adds the step of three each time — two, five, eight — and the next value, eleven, would reach or pass the stop of ten, so it halts; and critically, ten itself is excluded because the range function always stops before its end value. The mark is listing the values and stating the rule: the stop is exclusive, so it stops one short.

QUESTION: Question four. A student writes a while loop to count down from five, but the program never stops. Identify the most likely cause and the fix.

NARRATOR: The most likely cause is that the loop body never changes the variable in the loop's condition — the counter is never decremented — so the condition stays true forever: an infinite loop. The fix is to decrement the counter inside the loop body each pass, so the loop makes progress toward its exit condition and eventually stops. A second possibility worth mentioning is that the decrement line is indented outside the loop, so it never runs as part of the loop — an indentation error producing the same symptom. The mark-earning phrasing: "the control variable is not modified within the loop body, so the termination condition is never met."

QUESTION: Question five. Convert this pseudocode to Python: "IF score is greater than or equal to fifty THEN OUTPUT 'pass' ELSE OUTPUT 'fail' ENDIF."

NARRATOR: In Python: if score is greater than or equal to fifty, colon; on the next line, indented, print of "pass"; then else, colon; on the next line, indented, print of "fail". The ENDIF disappears — the dedent after the else block ends it. Full marks: correct if-else with colons, the comparison written correctly, the two branches indented, and no leftover ENDIF. That clean drop of the closer keyword is the whole skill.
