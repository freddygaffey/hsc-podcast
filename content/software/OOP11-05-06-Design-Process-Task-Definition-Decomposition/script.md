NARRATOR: Let me say what each stage actually produces, because that's what turns the acronym into marks. Stage one, Requirements: what does the system need to do? NARRATOR: Stage two, Responsibilities. A responsibility is a specific task the system must perform to fulfil a requirement. And in object-oriented design, responsibilities become methods, living on classes. The question of stage two is: what are the classes, and which class owns each job? Now — how do you actually find the classes from a paragraph of English? This is the heuristic I promised, the one that feels like cheating.

NARRATOR: Read the requirements and underline the nouns and the verbs. Nouns are candidate classes. Verbs are candidate methods. That's it. Nouns become classes, verbs become methods. The verbs are borrow, add, search, calculate — there are your candidate methods. It is genuinely that mechanical to get a first draft. It's a draft, not gospel — you'll merge some, drop some, invent a coordinator class that wasn't a noun anywhere — but it gets you off the blank page, which is most of the battle.

NARRATOR: Now the second technique for stage two, and this is the one that earns the marks because it's the harder judgement: for each responsibility, ask "who should be responsible for this?" This is the heart of what's called C-R-C thinking — Class, Responsibilities, Collaborators. You take a job and you decide which class is the right home for it. Who tracks whether a book is available? The book itself knows its own status — so a method on the Book class. Who knows whether a member is allowed to borrow more? The member holds their own borrowing record and fines — so a method on the Member class. Who enforces the rules and coordinates the whole borrow operation? Neither the book nor the member alone can — so a Library class that orchestrates.

NARRATOR: Let me name the actual methods, because these recur all episode. The Member class gets a "can-borrow" method — it checks the member's own state, are they under their book limit and under their fines limit, and answers true or false. The Book class gets an "is-overdue" method — it checks its own due date against today and answers true or false. And the Library class gets a "borrow-book" method that coordinates: it finds the member, finds the book, asks the member can-borrow, asks the book is it available, and only if both say yes does it actually move the book. Notice each method lives where the data lives. The member answers questions about the member. The book answers questions about the book. That's not an accident — that's encapsulation from episode two doing its job. The object that owns the data owns the behaviour that guards it.

QUESTION: So which class calculates the fines? The book's overdue, the member owes the money — where does that method actually go?

NARRATOR: That's the classic C-R-C judgement call, and it's literally a quiz question on this topic, so let's reason it the way a marker wants. The fine depends on how overdue a book is — that's book data — but it accrues against a member and affects whether they can borrow — that's member state — and the rules for how fines work, the rate, the cap, are policy that belongs to the institution. It could plausibly sit on Member, on Book, or on Library. The mark-earning move is to put it on the class that owns the policy and can see everything it needs — the Library, the coordinator — because calculating a fine needs the overdue duration from the book and applies it under library rules. There's no single forced answer; what scores is justifying the placement by where the data and the rules live. If you can say "I put it on Library because it's a coordination responsibility that needs information from both Book and Member," that's the answer. The reasoning is the mark, not the choice.

NARRATOR: So stage two output: classes, each with its responsibilities as methods. Member with can-borrow. Book with is-overdue. Library coordinating. That noun-and-verb pass plus the who's-responsible question is the engine of object-oriented design. NARRATOR: Stage three, Collaborations. Objects rarely work alone. A collaboration is the relationship where one object needs another to get a job done. The borrow operation is pure collaboration — the Library can't do it by itself. It has to ask the Member "can you borrow?", ask the Book "are you available?", tell the Book "you're now borrowed, here's your due date," and tell the Member "add this book to your list." That sequence of one object sending messages to others — that's collaboration, and it's just message-passing from episode one, the very first thing we did this module. The sender requests, the receiver acts on its own data. Stage three is where you map out those conversations: who calls whom, in what order, to fulfil each requirement.

NARRATOR: And then stage four, Implementation. Now — and only now — you write the code. The reason "implementation" is dead last in R-R-C-I is the single most important discipline in this whole topic, and it's a named trap, so I'm going to hit it hard. The number one mistake is coding before you've assigned responsibilities. You jump straight to the keyboard, you start writing a giant function that does borrowing, and halfway through you realise you don't actually know which object owns which piece, so everything turns into one tangled god-class that knows everything and nobody can maintain. The whole point of doing Requirements, Responsibilities, and Collaborations first is so that by the time you implement, every method has an obvious home and every interaction is already mapped. Implementation should be the boring part. If implementation is where you're making design decisions, you skipped stages one through three.

NARRATOR: Now — decomposition. The dot-point's second named item: top-down and bottom-up. These are two opposite directions you can travel through a design, and the exam adores "choose one and justify" questions. So let's nail what each is, when each wins, and why most real projects use both.

NARRATOR: Top-down design starts with the big picture and breaks it down. You begin with the whole system as one box, split it into major subsystems, split those into components, and keep going until you reach individual classes and methods. It's the structure chart from last episode — that tree, root at the top, branching downward into smaller and smaller jobs, is top-down decomposition drawn as a picture. Take an online shopping system. Level one: the whole shopping system. Level two: you break it into subsystems — user management, product catalogue, shopping cart, order processing. Level three: you take order processing and break it into payment processing, inventory management, shipping. You could go a level four and break payment into validation, card processing, invoicing, confirmation. You're descending, splitting the big into the smaller, three or four levels deep.

NARRATOR: Bottom-up design goes the other way. You start with the small, fundamental pieces and build upward. You identify the basic entities and operations, build those small classes first, then combine them into bigger components, then assemble those into subsystems, then into the whole system. The textbook example is a game. Level one, the tiny building blocks: a two-D vector class for positions, a colour class. Level two, game entities built from those pieces: a game-object that has a position vector and a colour, then a player and an enemy built on top of game-object. Level three, systems that use the entities: a collision system that reads positions, a game-world that holds the player and the enemies. Level four, the whole game assembled from all of it. You're ascending — small, tested, reusable pieces combined into ever-larger wholes.

NARRATOR: When does each win? Top-down wins when requirements are well-defined and stable, when the system has a clear hierarchy, when it's large and complex, when multiple teams need to coordinate against an agreed overall structure. You can see the whole shape early. Bottom-up wins when you're building reusable components, when requirements are likely to change, when you're working in a well-understood domain where the basic operations are obvious, or when you're building on existing systems. You get solid, tested foundations and maximum reuse.

NARRATOR: But each has a failure mode, and these are exactly the traps. Top-down's danger is over-engineering — you design this beautiful elaborate hierarchy of subsystems before you've written a line, and you miss critical details until late, and you've built abstraction layers nobody needed. Bottom-up's danger is the opposite — you build all these lovely little reusable pieces and lose sight of the actual goal, and then integration bites you late when the pieces don't fit the real requirement. Top-down can over-build the top; bottom-up can lose the plot at the bottom.

NARRATOR: So here's the honest answer to almost every "which approach" question: most real projects use a hybrid. You start top-down to understand the overall structure and carve out the major subsystems. Then you switch to bottom-up to build the core components solidly. Then you come back top-down to integrate them into the whole. And you iterate between the two as your understanding grows. The mark-earning phrasing on a "choose and justify" question is rarely "purely top-down" — it's "start top-down to frame the structure, then bottom-up to build reliable, reusable components, because the requirements here are X." Name the driver, then map it to the approach.

QUESTION: Let me make you apply that. You're asked: choose top-down or bottom-up for building a graphics library for game development, and justify it. Pause, decide, give your reason, then play.

NARRATOR: Bottom-up, and here's the justification a marker wants. A graphics library is fundamentally a set of reusable building blocks — points, vectors, colours, transformations — that other programs will combine in ways you can't fully predict. Reusability is the entire point of a library. So you start at the bottom with those fundamental, well-understood primitives, build them solidly and test them, then compose them upward into higher-level operations. The domain is well-understood and the components are meant to be reused — both signals for bottom-up. Contrast that with, say, an enterprise resource planning system — a huge business system with clear modules like accounting, inventory, payroll. That one's top-down: you must understand the overall business workflow first and break it into modules. The skill the exam is testing is reading the scenario for the driver — "reusable pieces, well-understood domain" screams bottom-up; "large, hierarchical, must understand the whole first" screams top-down.

NARRATOR: Now the one I flagged at the start — the facade pattern. This is a named syllabus dot-point, it's the thing students most often skip, and it's worth real marks, so we're going to do it properly and you're going to walk away able to explain it cold.

NARRATOR: Start with the word. A facade — the original architectural sense — is the front of a building. The grand, clean front face you see from the street. Behind that tidy front, the building can be a chaos of pipes, wiring, ducts, structural steel — but you never see it. You see the elegant front. In software, the facade pattern is exactly that idea: one simple front-of-house class that hides a messy, complicated subsystem behind a clean, easy interface. The client code talks only to the facade. The facade does the dirty work of coordinating all the complicated pieces behind it. The client never has to know those pieces exist.

NARRATOR: Here's the mnemonic, and it's a picture so it'll stick: a facade is a tidy front desk over a messy back office. Picture a hotel. You walk up to the front desk. You say "I'd like to check in." One person, one simple request. Behind that desk is chaos — housekeeping schedules, the billing system, the key-card programmer, the reservation database, room assignment, the minibar inventory. You don't talk to any of those. You talk to the front desk, and the front desk talks to all of them on your behalf. A facade is a tidy front desk over a messy back office. The front desk is the facade class. The back office is the subsystem.

NARRATOR: Make it concrete with our library. Imagine borrowing a book is genuinely complicated under the hood. To borrow, the system has to: validate the member is allowed to borrow — that's a validation subsystem. Check and update the inventory so the book is marked out — that's an inventory subsystem. And send the member a confirmation and schedule a due-date reminder — that's a notification subsystem. Three separate subsystems, each with its own fiddly methods. Without a facade, any code that wants to lend a book has to know about all three, call them in the right order, handle their errors, and not forget a step. That's a lot of knowledge spread everywhere, and if the borrowing process changes, you have to fix it in every place.

NARRATOR: With a facade, you create one class — call it the Library Facade — that exposes a single, dead-simple method: "borrow," taking a member and a book. That's the whole interface the outside world sees. Borrow. Inside, the facade is the front desk: it calls the validation subsystem, then the inventory subsystem, then the notification subsystem, in the right order, handling the coordination. The client just calls "borrow" and gets back success or a clear failure. That's the same stable-interface idea as encapsulation and abstraction from earlier in the module — the facade publishes a stable front and hides what's behind it. One clean benefit, stated well: "it decouples the client from the subsystem, so the subsystem can change without breaking client code." That's your mark.

NARRATOR: Last of the four named items: agility. The dot-point ends with the word "agility," and it's really a comment on the whole process. Remember I said R-R-C-I iterates? Agility is the name for taking that seriously. An agile process means you don't try to perfect the entire design up front and then build it once, frozen. You expect requirements to change, so you keep the design flexible enough to absorb that change instead of shattering.

NARRATOR: Connect it back. So when a question asks about agility in the design process, the mark-earning line is: design is iterative, not a one-shot waterfall; you build in small increments, gather feedback, and refactor, because requirements evolve and good object-oriented structure is what makes that affordable.

QUESTION: Question one. Describe the design process used to develop code in an object-oriented language. Six marks. Pause, write your answer, then play.

NARRATOR: Model answer. The object-oriented design process flows through four stages, often called R-R-C-I. First, Requirements: gather and analyse what the system must do, separating functional requirements — the features — from non-functional requirements — qualities like response time and uptime. Second, Responsibilities: identify the tasks the system must perform and assign each to a class, commonly by treating nouns in the requirements as candidate classes and verbs as candidate methods, then asking which class should own each responsibility. Third, Collaborations: design how the objects interact — which objects send messages to which others to fulfil each requirement. Fourth, Implementation: write the code, by which point every method already has a clear home. The process is iterative, not a strict waterfall: you loop back to earlier stages as your understanding improves, which is the agile aspect. For six marks you want all four stages named in order, what each produces, and the word "iterative." That's a full-band answer.

QUESTION: Question two. Distinguish between functional and non-functional requirements, and give one example of each for a library management system. Four marks. Pause, then play.

NARRATOR: Model answer. A functional requirement describes what the system does — a specific feature or behaviour. A non-functional requirement describes how well the system does it — a quality or constraint. They differ in that functional requirements define capabilities while non-functional requirements define standards the system must meet across those capabilities. For a library system, a functional requirement is "members can borrow and return books." A non-functional requirement is "a search must return results in under two seconds." The marks are in the clean distinction — what versus how-well — plus one correct example of each. Naming a quality like response time, uptime, or concurrency for the non-functional one is the safest example to give.

QUESTION: Question three — the one to nail. Explain the facade pattern and describe one benefit of using it. Four marks. Pause, answer it fully, then play.

NARRATOR: Model answer. The facade pattern provides a single, simplified interface — one front-of-house class — to a larger, more complex subsystem. The client code interacts only with the facade, which coordinates the underlying components on the client's behalf, so the client never has to deal with the subsystem's internal complexity directly. For example, a library facade might expose a single "borrow" method that internally coordinates separate validation, inventory, and notification subsystems. One benefit is reduced coupling: because the client depends only on the facade's simple interface, the subsystem's internals can be changed or replaced without affecting the client code, as long as the facade's interface stays the same. The mark-protecting move here is to say the facade hides the complexity, not that it removes it — the subsystems still do all their work behind the facade.

QUESTION: Question four. A team is building a graphics library of reusable components for game developers. Recommend top-down or bottom-up design and justify your choice. Pause, then play.

NARRATOR: Model answer. I would recommend bottom-up design. A graphics library is fundamentally a collection of reusable building blocks — vectors, points, colours, transformations — that developers will combine in unpredictable ways, so reusability is the primary goal. Bottom-up design suits this because you build and thoroughly test the fundamental components first, then compose them upward into higher-level operations, giving solid, reusable foundations. The domain is well-understood and the components are explicitly meant for reuse — both of which are signals for bottom-up. A top-down approach would be wrong here because there's no single fixed hierarchy to decompose; the value is in the reusable parts, not an overarching structure. The marks are in naming the approach, justifying it from the scenario's driver — reusability and well-understood components — and saying why the other approach fits less well.

QUESTION: Question five, the integration one. Explain why coding before assigning responsibilities is considered poor design practice, and relate your answer to the design process. Pause, then play.

NARRATOR: Model answer. In the object-oriented design process, implementation is deliberately the last of the four stages — Requirements, Responsibilities, Collaborations, then Implementation. Coding before assigning responsibilities skips the Responsibilities and Collaborations stages, which means you start writing code without knowing which class should own each task or how objects should interact. This typically produces a single overgrown class — a god-class — that tries to do everything, because the jobs were never distributed to appropriate objects. The result is code that is tightly coupled, hard to test, and hard to maintain, and it tends to violate encapsulation because data and behaviour aren't properly bundled. The correct practice is to complete requirements, responsibilities, and collaborations first, so that by implementation every method has an obvious home and every interaction is already designed — making implementation the routine part rather than where design decisions get made by accident. A strong answer names the stage order, names the god-class symptom, and links it to maintainability and encapsulation.
