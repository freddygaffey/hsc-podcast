NARRATOR: Not for the exam. You know what an integer is as a programmer — but the syllabus has a specific list of standard data types, with specific distinctions it wants you to make, and a specific skill: choosing the right type for a piece of data and justifying it. That justify-the-choice question appears constantly, and there are two classic traps that cost marks. So today is the HSC layer on data types. The dot-point: "Investigate standard data types," and it lists them — "char and string; Boolean; real; single precision floating point; integer; date and time." The outcomes are S-E-eleven-oh-two and S-E-eleven-oh-four — the latter being about safe and secure practices to collect, use, and store data. Choosing the right type is the first step in storing data correctly.

NARRATOR: Objectives up front. By the end you'll be able to: name and describe the standard data types; make the two distinctions the syllabus cares about — char versus string, and real versus single-precision floating point; choose an appropriate type for any field and justify it; convert between types; and avoid the two marquee traps. Let me give you the organising hook first, because the list is long. The standard types fall into four families: Words, Numbers, Truth, and Time. Words is text — characters and strings. Numbers is integers and reals. Truth is boolean. Time is date and time. Words, Numbers, Truth, Time. Now let's walk them.

NARRATOR: Words first — text. A char, short for character, is a single character — one letter, one digit, one symbol, like the letter A or a dollar sign. A string is a sequence of characters — a word, a sentence, a whole document. A char is one; a string is many. And here's the link straight back to last episode that earns you a smart mark: a character is really a number underneath. Each character has a numeric code — in the ASCII and Unicode schemes, capital A is sixty-five, lowercase a is ninety-seven. So a char is stored as an integer code, which is stored as binary, which is what we did last episode. Listing 1 shows that: the letter A is sixty-five, which in binary is one-oh-oh-oh-oh-oh-one. Text is numbers wearing a costume.

NARRATOR: When do you use a string? Names, addresses, messages, identifiers — any textual information. And a sharp exam point: use a string even for things that look like numbers but aren't arithmetic — a postcode, a phone number, a product code. Why? Because you never add or subtract them, and storing them as a number throws away leading zeros and structure. A postcode of oh-two-double-oh-oh stored as an integer becomes two thousand — the leading zero is gone. Postcodes, phone numbers, and codes are strings.

NARRATOR: Numbers next, and this is where the syllabus makes a distinction you must get right. An integer is a whole number — positive, negative, or zero, no fractional part. Ages, counts, years, identifiers, loop counters. And crucially, an integer is exact, and it's stored using the two's complement representation from last episode — so the range and overflow ideas we covered apply directly. Then there's the real, and the single-precision floating point. The syllabus lists "real" and "single precision floating point" as separate items, and the distinction is worth a mark. "Real" is the general category — any number with a fractional part, like a price or a measurement. "Floating point" is the specific way computers actually store reals: a sign, a mantissa, and an exponent — like scientific notation in binary. And "single precision" names a specific size: a single-precision float is thirty-two bits and holds about seven significant digits; a double-precision float is sixty-four bits and holds about fifteen or sixteen. So: real is the concept, floating point is the storage method, and single versus double is how many bits — and therefore how much precision — you give it. Listing 2 demonstrates the difference in code.

NARRATOR: And here is the single most important fact about floating point, the one that becomes a trap: a float is approximate, not exact. Because it stores numbers in binary with a fixed number of bits, many ordinary decimal values can't be represented exactly — the classic is that nought point one plus nought point two does not equal nought point three; it comes out as nought point three-oh-oh-oh-oh-oh-oh-oh-something. An integer is exact; a float is approximate. Burn that in, because it leads straight to trap number one.

QUESTION: Before the traps — here's one to actually attempt. Pause the player. You're storing a student's age, their exact grade average like eighty-seven point three, and their student identifier. Which type for each, and why? Work it out, then play.

NARRATOR: Age: integer — it's a whole-number count, you might do arithmetic on it, and it's exact. Grade average, eighty-seven point three: a real, stored as a floating-point number, because it has a fractional part. Student identifier: a string — even though it might look numeric, you never do arithmetic on an ID, and treating it as a string preserves any leading zeros or letters and signals "this is a label, not a quantity." The justification is the mark every time: name the type and say why — exact whole number, fractional value, or non-arithmetic label.

NARRATOR: Now Truth — the boolean. A boolean holds one of exactly two values, true or false. Status flags, yes-or-no answers, the result of any comparison. Is-enrolled, is-passing, has-permission. And the exam point here: store a yes-or-no as a boolean, not as the string "yes". A boolean is testable directly, it's unambiguous, and it can't be misspelled as "Yes" or "YES" or "y". That's trap territory we'll come back to.

NARRATOR: And Time — date and time. A dedicated type for dates, times, and timestamps: birthdays, deadlines, log entries. Why a real date type and not a string? Because a date type lets you do date arithmetic — days between two dates, is this before that, add two weeks — which you simply can't do reliably with text. Store a birthday as a date and you can compute an age; store it as the string "fifteenth of March" and you're stuck. And a historical aside that shows why representation choices matter: the Year Two Thousand problem, where decades of software stored the year as just two digits to save space, so nineteen-ninety-nine was stored as nine-nine — and the worry was that the year two thousand, stored as oh-oh, would be read as nineteen hundred. A data-representation decision that triggered a global remediation effort. The type and the size you choose for data have real consequences.

NARRATOR: Now type conversion, because data often arrives as the wrong type — especially as text from user input or a file. Converting a string to an integer works only if the text is a valid number. Converting a number to a string always works. And watch this one: converting a float to an integer truncates — it chops off the decimal part, it does not round. Three point nine becomes three, not four. That truncation surprises people and causes silent logic errors.

NARRATOR: Which brings us to the two marquee traps, the ones examiners love. Trap one: storing a number as a string when you need arithmetic. If age is the string "seventeen" — the characters one and seven — then "seventeen" plus one doesn't give eighteen; it gives the string "one-seven-one", because the plus concatenates text instead of adding numbers. Listing 3 shows it. The fix: store age as an integer, or convert before doing maths. Trap two, the famous one: using a float for money. Because floats are approximate, financial arithmetic drifts — nought point one plus nought point two isn't nought point three, and those tiny errors accumulate into real money over millions of transactions. Listing 4 shows the drift and the fix: store money as an integer number of cents, and divide only for display. Never store money in a float — use whole cents. Say that in an exam and you've shown you understand both the float's nature and the consequence.

One: the standard data types are four families — Words, Numbers, Truth, Time — that is, char and string; integer and real or floating point; boolean; and date-time. QUESTION: Question one. Identify a suitable data type for each of the following and justify your choice: a person's email address, the number of items in a shopping cart, a product's price, and whether a user is logged in. Pause the player, write your answer, then play.

NARRATOR: Email address: string — textual data containing letters and symbols, never used in arithmetic. Number of items: integer — a whole-number count, exact, used in arithmetic. Product's price: a real stored as floating point — it has a fractional part, cents — though note for exact money you'd store cents as an integer. Whether a user is logged in: boolean — a simple true-or-false status. Full marks come from the justification on each, not just the label: text, whole-number count, fractional value, two-state status. That pattern — type plus one-line reason — is the whole answer.

QUESTION: Question two. Explain why a floating-point number is unsuitable for storing monetary values, and state a better approach.

NARRATOR: A floating-point number stores values approximately, because it represents them in binary with a fixed number of bits, so many decimal fractions like nought point one cannot be stored exactly. In financial calculations these tiny errors accumulate and produce incorrect totals — money appears or disappears. A better approach is to store the amount as an integer number of the smallest unit, such as cents, so all arithmetic is exact, and divide only when displaying. The marks: identify the approximation and its cause, state the consequence for money, and give the integer-cents fix.

QUESTION: Question three. Distinguish between a char and a string, and between single-precision and double-precision floating point.

NARRATOR: A char is a single character — one letter, digit, or symbol — whereas a string is a sequence of zero or more characters. Single-precision and double-precision are both floating-point formats, but single precision uses thirty-two bits and stores roughly seven significant digits, while double precision uses sixty-four bits and stores roughly fifteen to sixteen — so double precision is more accurate but uses more memory. The mark in each is the precise distinguishing feature: one character versus many, and thirty-two bits versus sixty-four with the precision that follows.

QUESTION: Question four. A student stores a postcode as an integer and finds that "zero-two-eight-seven-zero" becomes "two-eight-seven-zero". Explain what went wrong and what type should be used.

NARRATOR: Storing the postcode as an integer dropped the leading zero, because an integer represents a numeric quantity and two thousand eight hundred and seventy has no leading zero — the zero carries no numeric value. A postcode is an identifier, not a quantity: you never do arithmetic on it, and its exact sequence of digits, including leading zeros, must be preserved. It should be stored as a string. The mark-earning point: a postcode is a non-arithmetic label, so a string preserves its exact form including leading zeros.

QUESTION: Question five. A program reads the text "seventeen" — the digits one and seven — as a user's age and computes age plus one, getting "one-seven-one". Explain the error and the fix.

NARRATOR: The age was stored as a string, so the plus operator performed string concatenation rather than numeric addition — joining the text "seventeen" and the text "one" into "one-seven-one" instead of adding. The fix is to convert the string to an integer before doing arithmetic, or to store the age as an integer in the first place. The phrasing that scores: "the value is a string, so plus concatenates rather than adds; convert to an integer to perform numeric addition."
