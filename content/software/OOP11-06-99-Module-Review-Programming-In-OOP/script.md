NARRATOR: Let me do the proper spaced-repetition lap now, lesson by lesson, fast, because we have a lot of ground and some of this is two months old. Chapter Five, lesson one: objects, classes and message-passing. An object bundles data — its attributes, the nouns, its state — with behaviour, its methods, the verbs. A class is the blueprint, written once, holds no data. An instance is the concrete object built from it, holding its own real values. One class, many instances. And calling a method is really message-passing: you send a message to an object and it acts on its own data and replies. The five-step dispatch behind that is our first mnemonic — L-B-P-E-R: Lookup the method on the class, Bind the receiver to self, Pass the parameters, Execute, Return. Lookup, Bind, Pass, Execute, Return.

NARRATOR: Lesson two: encapsulation. Two halves, you need both — bundle the data with the methods that control it, and restrict direct access to that data. The public interface is the approved methods outside code may call, which should stay stable; the internal state is the data nobody outside should touch. The interface is the buttons, the state is the wiring. And why we bother is the second mnemonic — I-C-F-S: Integrity, Consistency, Flexibility, Security. You encapsulate to protect the object's invariants — the conditions that must always hold, like a balance never going negative — by funnelling every change through a validating method.

NARRATOR: Lesson three completed the four behaviours, and here's the master mnemonic for the entire module. If you remember one thing today, remember this. Have a slice of A-PIE. A-PIE: Abstraction, Polymorphism, Inheritance, Encapsulation. Encapsulation we just did. Abstraction hides the complexity — expose only the essentials through a simple interface. The one-liner to keep those two apart: encapsulation hides the data, abstraction hides the complexity. Then generalisation and inheritance, which people constantly muddle, and the mnemonic fixes it: generalise to model, inherit to reuse. Generalisation is the modelling act — on the whiteboard you notice a car and a motorcycle are both vehicles and capture the shared idea. Inheritance is the implementation act — in code a subclass actually reuses the parent's members, calling super to run the parent's constructor, and can add or override. And polymorphism: one interface, many behaviours. One loop calls one method name, each object runs its own version. In Python you don't even need a shared parent — that's duck typing, and the line is: duck typing, if it quacks, it'll do.

NARRATOR: Lesson four was the big step-back — comparing procedural programming with object-orientation. The whole contrast lives in one sentence, worth writing on your paper verbatim. Procedural: data and functions live apart. OOP: data walks with its methods. Every trade-off falls out of that. And the marquee trap: do not crown object-orientation the universal winner. Markers penalise "OOP is always better." A one-shot tax calculation, a pure factorial, a linear data-cleaning pipeline — those are fine procedural. Object-orientation wins when you've got real entities with state that interact. The tell that you should reach for a class: a giant parameter list is procedural crying out for a class.

NARRATOR: Lesson five: modelling, three diagrams. The mnemonic does the work — Class equals things, Chart equals jobs, DFD equals data. The class diagram shows static structure — what classes exist, their attributes and methods, how they relate. The structure chart shows functional decomposition — one big job broken top-down into a tree of smaller jobs. The data flow diagram, the DFD, shows where data comes from, what transforms it, where it ends up. Three high-value facts. One — on a class diagram, a filled diamond means composition: filled diamond equals composition, the part dies with the whole. Two — the DFD symbols: a process is a circle, an external entity is a closed rectangle, a data store is an open-ended rectangle. Three, the marquee distinguish trap — a DFD is not a flowchart. A DFD shows where the data goes; a flowchart shows what the program does, in order. Data flow versus control flow.

NARRATOR: Lesson six: the design process — how you produce those diagrams. The pipeline is R-R-C-I: Requirements, Responsibilities, Collaborations, Implementation. Always say iterative; it loops, it's not a waterfall. Requirements split into functional — what it does — versus non-functional — how well it does it; response time, uptime and concurrency are the non-functional tells. Responsibilities use the heuristic nouns become classes, verbs become methods, and then you ask, who should be responsible for this? Each method lives where its data lives — encapsulation given a job. Collaborations are which object sends which message — message-passing scaled up. Implementation comes last. We did decomposition, top-down versus bottom-up, most real projects hybrid, and the one named design pattern in the syllabus, the facade. A facade is a tidy front desk over a messy back office — one simple front-of-house class hiding a whole messy subsystem behind a clean interface. And the trap: a facade hides complexity, it does not remove it.

NARRATOR: Lesson seven closed Chapter Five: collaboration and version control. The spine sentence — clear interfaces let teams work apart, then merge. Because each class is a module with a well-defined interface, and that interface is a contract — this is what you call, what you pass, what you get back — different people own different classes and build in parallel. Stubs and mocks let you build against an interface before the real class exists; when the real one lands it honours the same interface and drops in unchanged. Then the four named practices in the syllabus's order: consistency, code commenting, version control, feedback. Comment the why, not the what. One idea per commit. And feedback is code review through a pull request — comment the code, not the coder. That's all of Chapter Five.

NARRATOR: Now Chapter Six, and the verbs flip from design to build. Lesson one of Six: building classes and composition. You build a complex object out of simpler component objects held as attributes — composition, the has-a relationship — rather than inheriting. The mnemonic: is-a versus has-a, favour has-a when unsure. A car has-an engine; a car is not a kind of engine, so you compose, you don't inherit. Run the sentence test out loud. The constructor — say "dunder init" — must validate its inputs and raise before storing, so the object is born valid: validate then store, enforces invariants and fails fast. And dependency injection — pass an object's dependencies in from outside rather than building them inside — lets you swap a console logger for a file logger for a do-nothing logger, same object, different behaviour. That swap working is just polymorphism again. The four benefits of composition over inheritance, as one chant: runtime-flexible, loosely coupled, independently testable, no diamond problem.

NARRATOR: Lesson two of Six: control structures within methods. Selection and iteration living inside a method, driven by the object's own state. The guard clause — an early return that handles a bad case immediately and bails, so the happy-path logic sits flat at the bottom: guard clauses flatten the arrow of nested ifs. And keeping a method to one job — the Single Responsibility Principle for methods: one method, one job, under about twenty lines. A while-loop has no guaranteed termination, so a runaway while is a non-terminating failure — fix it with an explicit safety limit, a counter and a max-iterations cap. And method extraction is the centrepiece refactor: pull each distinct responsibility out of a long do-everything method into a focused helper, and the original becomes a short coordinator that reads like a table of contents.

NARRATOR: Lesson three of Six: designing subroutines and stubs. A method signature is name plus parameters plus return — the promise. Signature equals name plus parameters plus return equals the promise. It's a contract: call me this way, give me these inputs, I return this; change the body freely and callers still work. The mainline orchestrates one-task subroutines in order and does no work itself — the mainline reads like a table of contents, elevated now from the method to the whole program. And a stub is a placeholder that keeps the real signature but fakes the body — prints a to-do or returns a dummy of the right type. Stub first, fill later. The high-value reason students drop: because each stub keeps the real signature, the methods connect, so you can test the integration between methods before the real logic exists. Stubs enable early integration testing.

NARRATOR: Lesson four of Six: code quality and maintainability. Code is read far more often than it is written, so readability is where the value lives. Two headline refactors — Extract Method, and Replace Magic Number with a Named Constant. No magic numbers — name them. Comment the why — the code already shows the what. And the maintainability checklist, the gold for a "list four features" question, four groups, take one from each for four distinct marks: Name it, Document it, Size it, Structure it. Ease of maintenance is bigger than one file — version control gives you documented, reversible history and safe rollback; regular backup protects the whole project against catastrophic loss.

NARRATOR: Lesson five of Six: testing — unit, subsystem and system, plus quality assurance. Three levels by scope — U-S-S: Unit, the smallest testable part in isolation; Subsystem, the exam's preferred name being integration testing, a group of classes working together across their interfaces; System, the whole application end-to-end against a realistic workflow. Count the classes under test: one is unit, several is subsystem, the whole app is system. A good unit test is FIRST: Fast, Independent, Repeatable, Self-validating, Timely. Test behaviour, not implementation — behaviour tests survive refactoring. And quality assurance is the systematic wrapper around testing that builds quality in and prevents defects: testing detects, QA prevents.

NARRATOR: Lesson six of Six: test strategies — black, white and grey box. This is the other axis. Levels are how much of the system you test at once; strategies are how much you can see inside the code while you test. They're perpendicular and they combine. Black equals spec, White equals code, Grey equals both. Black box tests purely from the specification with no view of the code, and its two named techniques are B-V-A plus E-P: Boundary Value Analysis and Equivalence Partitioning — boundaries are where bugs hide. White box tests from the code structure, asking have I run every part — and the word is coverage, with branch coverage being the one to define: every decision tested both true and false. Grey box uses partial internal knowledge to aim tests at risky spots — integration, security, timing. And the headline: none alone is enough — combine all three.

NARRATOR: Lesson seven of Six, the last content lesson: code optimisation and assessing effectiveness. The four effectiveness dimensions — C-C-P-M: Correctness, Clarity, Performance, Maintainability. Assess the effectiveness means name all four and apply each to the actual code; the number-one loss is writing three paragraphs on performance and forgetting the other three. Optimisation improves efficiency without changing behaviour, and must end by re-verifying correctness against the tests. Fix the algorithm before the line — turning a linear search into a constant-time dictionary lookup dwarfs any clever one-liner. And the workflow: measure first, optimise second — Clear, Profile, Optimise, Re-verify. Premature optimisation, optimising before you know the bottleneck, is the famous mistake.

NARRATOR: Now the most valuable thing a review can do is not re-list facts — it's connect them. So let me draw the big threads that run the length of the whole module, because the exam writes questions that span topics and the marks live in the connections. Thread one, and it's the spine of everything: hide the messy inside, publish a stable front. Encapsulation hides one object's data behind its methods. Abstraction hides one object's complexity behind a simple interface. A facade hides a whole subsystem behind one class. A method signature hides the body behind name, parameters and return. A team interface hides one developer's implementation behind a contract. And a stub or a mock honours that same interface so code can be built before the real thing exists. That is one single instinct — stable front, hidden internals — appearing six times across both chapters. Listing 2 is the bank-account spine showing that stable interface with its validated, hidden state, and the bypass line underneath it is the underscore-isn't-privacy trap made concrete.

NARRATOR: Thread two: the same idea that designs the system also tests it. Message-passing from the very first lesson — sending a message to an object — is collaborations in the design process, is polymorphism when each object answers in its own way, and is exactly what integration testing checks when it verifies that objects hand data across their interfaces correctly. One idea — objects talking to objects — runs from lesson one of Chapter Five all the way to subsystem testing in Chapter Six. Thread three, the build-to-test bridge: every quality move from the maintainability lesson also makes the code testable. A short single-responsibility method is the only kind you can unit-test cleanly; behaviour tests are what let you run Extract Method fearlessly, because the behaviour stays identical and the test still passes. Maintainability and testability are two sides of one coin. And thread four: the diagrams and the design process from Chapter Five are the plan; the classes you build, refine and test in Chapter Six are that plan realised. A class diagram documents the responsibilities you assigned in R-R-C-I, and then documents the classes you actually built. Design and build are not separate skills — the build is the design made real.

QUESTION: First real retrieval, and it's the foundation. Name the seven key features of an object-oriented language, and group them sensibly so you never drop one. Pause the player, write them down, then play.

NARRATOR: The seven are objects, classes, encapsulation, abstraction, inheritance, generalisation, polymorphism. The way to never lose one is the structural trio plus the behavioural four. The structural trio is O-C-G — Objects, Classes, Generalisation: the things you build with and the modelling relationship between them. The four behaviours are A-PIE — Abstraction, Polymorphism, Inheritance, Encapsulation. O-C-G plus A-PIE equals all seven. If an eight-mark question says apply the key features of an object-oriented language, you write O-C-G and A-PIE down the margin and you've got your seven paragraph headings before you've thought of a single example. That structure is half the marks.

QUESTION: Marquee distinguish round now, fast, because the HSC writes "distinguish" questions on exactly these confusable pairs. Pair one — distinguish a class from an instance. Pause, answer out loud, then play.

NARRATOR: A class is the blueprint — it defines what attributes and methods exist, it's written once, and it holds no actual data. An instance is a concrete object built from that class, and it holds its own real values. The marking sentence: the class defines the structure; the instance holds the data. The trap that loses the mark is saying "the bank-account class has a balance of a thousand dollars." Wrong. The class defines that there is a balance attribute; the instance holds the thousand.

QUESTION: Pair two — distinguish generalisation from inheritance. Pause, answer, play.

NARRATOR: Generalise to model, inherit to reuse. Generalisation is the modelling act — on the whiteboard you identify shared characteristics across objects and capture them in a more general class; it's a design decision, no code yet. Inheritance is the implementation act — in code, a subclass actually reuses the parent's attributes and methods and can add or override. Generalisation is the idea; inheritance is the mechanism that realises it.

QUESTION: Pair three — distinguish composition from inheritance, has-a from is-a. Pause, answer, play.

NARRATOR: Inheritance is is-a — a subclass is a kind of its parent and reuses its members; the relationship is fixed at definition. Composition is has-a — an object holds other objects as attributes and delegates to them; the relationship can be swapped at runtime. Run the sentence test: say "a car is-an engine" — absurd — versus "a car has-an engine" — true — and use whichever is true. The default rule: favour has-a when unsure. And the four benefits of composition you can chant: runtime-flexible, loosely coupled, independently testable, no diamond problem.

QUESTION: Pair four — distinguish the three diagrams. What does a class diagram, a structure chart and a data flow diagram each show? Pause, answer, play.

NARRATOR: Class equals things, Chart equals jobs, DFD equals data. The class diagram shows the static structure — the classes, their attributes and methods, and their relationships, including multiplicity and that filled diamond for composition. The structure chart shows functional decomposition — one big task broken top-down into a tree of sub-tasks. The data flow diagram shows the movement and transformation of data — where it comes from, what processes it, where it's stored. And don't confuse a DFD with a flowchart: a DFD shows where the data goes, a flowchart shows what the program does, in order.

QUESTION: Pair five, and this is the one that spans both chapters of testing — distinguish the three test levels from the three test strategies. Pause, answer, play.

NARRATOR: This is the framing the exam fishes for, so be precise. The levels — U-S-S, Unit, Subsystem, System — are about how much of the system you test at once: one class, several cooperating, or the whole application. The strategies — black, white and grey box — are about how much you can see inside the code while you test: Black equals spec, no view of the code; White equals code, you design tests from the source structure; Grey equals both, partial knowledge aimed at risky spots. They are perpendicular axes that multiply: you can run a black-box unit test or a white-box integration test or a grey-box system test. Treating "unit testing" and "black-box testing" as items on one list is the exact misunderstanding the question is built to catch.

QUESTION: Last pair — name and define the two black-box techniques, and name the three coverage levels in white box. Pause, answer, play.

NARRATOR: The two black-box techniques are B-V-A plus E-P. Equivalence Partitioning divides all inputs into groups that behave the same and tests one representative per group. Boundary Value Analysis tests the value at each edge and just either side of it, because boundaries are where bugs hide — the classic is testing fifty-nine versus sixty at a grade boundary, not eighty-five in the middle. The three white-box coverage levels, weakest to strongest: statement coverage, every line run; branch coverage, every decision taken both true and false — that's the one to define; and path coverage, every route end-to-end, strongest but usually impractical. Branch beats statement because an if with no else gets full statement coverage from a single test yet never runs the false branch.

Now the centrepiece of this review — one big integrated exam task that walks the entire module from design to assessment, because this is the shape of the longest extended-response questions the HSC asks. Here's the task, and it's the kind worth a dozen or more marks. "Design, implement and test the classes for a small system — say a school gradebook. Choose and justify your programming paradigm. Sketch the class diagram. Apply composition. Write a unit test and an integration test. Then assess the effectiveness of your code across the four dimensions." I'll walk a model answer, and notice how almost every mnemonic from the module earns its place.

NARRATOR: Step one, justify the paradigm. The weak answer says "I'll use object-orientation because it's modern and better." That crowns a universal winner and earns nothing. The strong answer reasons from the problem: a gradebook has real entities with state that interact — students, courses, grades — and that state evolves over time, so this is exactly where object-orientation wins. Procedural would scatter a student's name, identifier and grade list across loose variables passed into functions with long parameter lists — and a giant parameter list is procedural crying out for a class. Data and functions live apart in procedural; in object-orientation, data walks with its methods. So I choose object-orientation, and I justify it by naming the driver — interacting entities with evolving state — not by calling it modern.

NARRATOR: Step two, the class diagram, described in words because that's what the marker needs to hear. There's a Gradebook class and a Student class. The Gradebook is composed of many Students — a filled diamond at the Gradebook end pointing to Student, with a multiplicity of one Gradebook to many Students, the star meaning zero-or-more. That filled diamond is composition: the part dies with the whole — delete the gradebook and its student records go with it. Each Student has attributes — a name, an identifier, a list of grades — shown with a minus sign for private internal state — and methods like add-a-grade and calculate-average, shown with a plus sign for the public interface. That minus-and-plus is encapsulation drawn on the page. Listing 3 is that class diagram written out so you can read the notation later.

NARRATOR: Step three, apply composition, and this is where you earn the design marks. The Gradebook has-a collection of Students; it does not inherit from Student, because a gradebook is not a kind of student — run the sentence test and is-a is absurd, has-a is true. The Student holds its grades and owns the logic about its own grades — calculate-average lives on Student because that's where the grade data lives; each method lives where its data lives, which is encapsulation given a job, straight out of the R-R-C-I responsibilities step. The Gradebook coordinates — it adds students, asks each student for its average, and computes the class average by delegating. That delegation is message-passing — the Gradebook sends the calculate-average message and the Student answers using its own data. Listing 4 builds those two composed classes with a validating constructor, so a student can't be born with an empty name or a grade outside zero to one hundred — validate then store, enforce the invariant, fail fast at the boundary.

NARRATOR: Step four, the unit test. A unit test exercises one class in isolation — count the classes under test: one, so it's a unit test. I test the Student's calculate-average alone: a happy-path case with three known grades asserting the exact average, and the error cases, because the marks and the bugs live at the boundaries — adding a grade of negative ten or a hundred and ten must raise, and I assert that it raises. Each test gets a fresh student from the set-up method that runs before every test, so the tests are Independent and Repeatable — that's the I and the R in FIRST. And I'm testing the observable behaviour — the average it returns — not the internal wiring, so the test survives a refactor. Listing 5 is that unit suite.

NARRATOR: Step five, the integration test, and this is the one weaker answers skip. An integration test — the subsystem level — exercises the Gradebook and the Student working together across their interface. Count the classes: two cooperating, so subsystem. I add several real students to a gradebook, record grades through the Gradebook's interface, and assert the class average is correct — which only passes if the Gradebook correctly sends messages to each Student and each Student replies correctly and the data flows across the boundary intact. A unit test on either class alone can never catch a mismatch in that handshake; the integration test is the only thing that does. This is the early-integration payoff of stubs grown up — stubs let you test these connections before the logic exists; the integration test confirms them once it does. Listing 6 is that integration test.

NARRATOR: Step six, assess the effectiveness, and you must name all four dimensions and apply each — C-C-P-M: Correctness, Clarity, Performance, Maintainability. Correctness: the code returns the right average for valid grades and raises on invalid ones, verified by the unit tests at the boundaries — that's where Correctness, behaviour-testing and Boundary Value Analysis all meet. Clarity: the names are self-documenting — calculate-average says exactly what it does — there are docstrings on the public methods and comments explain any why, not the what. Performance: looking up a student by identifier in a list is a linear search, order n; if the gradebook gets large, switching the students to a dictionary keyed by identifier makes that lookup constant time, order one — fix the algorithm before the line. Maintainability: the classes are small and single-responsibility, so a change to grading rules touches one place — Name it, Document it, Size it, Structure it. And critically, Correctness comes first and is non-negotiable: fast wrong code is worthless, which is why Performance is third on that list, not first. That's the full model answer — and notice it touched paradigm choice, class diagrams, composition, encapsulation, message-passing, validation, unit and integration testing, FIRST, the four dimensions and Big-O intuition. One task, most of the module. Listing 7 lays that whole design-build-test-assess sequence out as exam-style pseudocode, so you can rehearse the shape of it.

QUESTION: Let me make you do part of it. For that gradebook, before optimising the student lookup to a dictionary, what must you do, and what must you do after? Pause, answer, play.

NARRATOR: Before: profile — measure first, optimise second, because programmers are reliably wrong about where the time actually goes, and optimising a lookup that was never the bottleneck is premature optimisation. After: re-verify correctness — re-run the full test suite, because a faster wrong answer is a regression, not an optimisation. Green means the optimisation was safe; red means revert. The workflow in four words: Clear, Profile, Optimise, Re-verify.

NARRATOR: Now the part of this review you'll remember longest — three real disasters, told briefly, as a trio. Call them what poor design and poor testing actually cost. Each is self-contained; the full stories are their own episodes, but you don't need them — here's enough to use each one in an exam.

NARRATOR: First, the Mars Climate Orbiter. Nineteen ninety-eight, a roughly one-hundred-and-twenty-five-million-dollar NASA spacecraft. Two teams wrote two modules. The ground software, built by one contractor, produced a thrust figure in imperial units — pound-force-seconds. The navigation software, built by another team, read that figure expecting metric units — newton-seconds. The two numbers differ by a factor of about four and a half. Nobody had written down, as part of the interface between the modules, which units crossed it. The craft arrived at Mars in September nineteen ninety-nine on a trajectory far too low and was destroyed in the atmosphere. The lesson, and the exam sentence: an interface is a contract. The public interface, the method signature, the units that cross a boundary — signature equals the promise — must be specified, because an unstated contract is a time bomb. This is the cost of treating an interface as optional.

NARRATOR: Second, Ariane Five, Flight Five-Oh-One. Nineteen ninety-six. The rocket reused a working software component — the inertial reference system — straight from the older Ariane Four, without re-testing it against the new rocket's flight profile. Ariane Five flew faster and steeper. A value that had always been small on Ariane Four was now large, a sixty-four-bit number was crammed into a sixteen-bit slot, it overflowed, the guidance system failed, and the rocket self-destructed about thirty-seven seconds after launch — roughly three hundred and seventy million dollars gone. The lesson: reuse is powerful, but you must re-test a reused component in its new context. Reuse without re-testing is exactly the gap that integration and system testing exist to close. When you reuse a class, the old unit tests passing tells you nothing about the new flight profile.

NARRATOR: Third, the Therac-Twenty-Five. A radiation-therapy machine, nineteen eighty-five to eighty-seven. The earlier models had hardware interlocks that physically stopped an overdose; the Therac-Twenty-Five removed them and trusted software to do the job. Hidden inside the software was a race condition in the machine's state: if a skilled operator typed the treatment settings fast enough, two parts of the program updated the same state in the wrong order, and the machine delivered a radiation dose around a hundred times the intended amount — while the screen calmly read normal. Several patients died. Reused code was trusted without rigorous testing, the state was hidden and unguarded, and the quality assurance on life-critical software was threadbare. The lesson ties three of our topics together: invariants on internal state — the encapsulation lesson — plus real quality assurance, plus testing that can reach a timing-and-state bug, which is precisely a grey-box concurrency test, because only someone aiming a test at the known-risky internal state would ever hit it.

NARRATOR: So the trio as one moral: Mars is the unstated interface contract, Ariane is reuse without re-testing, Therac is hidden state plus no real QA plus inadequate testing. Three failures, three module topics — interfaces and signatures, reuse and integration testing, state and quality assurance — and in each case the engineering was clever and the discipline was missing. That's the marker's favourite shape: the failure wasn't a lack of skill, it was a lack of process.

NARRATOR: Now let me consolidate the traps in one place, because across the whole module the same five mistakes recur, and they all have the same shape — refusing a false universal. Notice traps three, four and five are the same move — the marker is rewarding you for refusing to crown a universal winner and instead giving a balanced, conditional judgement. QUESTION: Question one, six marks. Distinguish between procedural programming and object-oriented programming, and identify one scenario where each is the better choice. Pause the player, write a full answer, then play.

NARRATOR: Model answer. Lead with the contrast sentence: procedural, data and functions live apart — functions operate on separate data passed as parameters or held globally, organised by top-down decomposition. Object-orientation, data walks with its methods — data and the methods that act on it are bundled into objects, with encapsulation as the organising principle. Then go dimension by dimension, briefly: organisation, functions versus classes; state, external and global versus internal to the object; reuse, function libraries versus inheritance and composition. Then the scenarios, and this is where the marks finish: procedural is the better choice for a simple one-shot computation with no entity to model — a tax calculation, a factorial — clear input to output, no state. Object-orientation is the better choice for modelling interacting entities with evolving state — a banking system, a game with characters. Finish with the balanced line: neither is universally better; the choice depends on whether the problem has entities and state worth modelling. That balance is the top-band marker.

QUESTION: Question two, six marks. Distinguish unit, subsystem and system testing, and explain how black-, white- and grey-box testing relate to them. Pause, answer, play.

NARRATOR: Model answer. The levels, by scope — U-S-S. Unit testing exercises the smallest testable part, one method or class, in isolation. Subsystem testing, the integration level, exercises a group of related classes working together, checking their interfaces line up and data flows correctly across the boundary. System testing exercises the complete application end-to-end against a realistic user workflow. The clean tell: count the classes under test — one is unit, several is subsystem, the whole app is system. Then the crucial relation: the box strategies are a different, perpendicular axis — Black equals spec, White equals code, Grey equals both — they describe how much you can see inside the code, not how much you test at once. The two axes multiply: you can run a black-box unit test, a white-box integration test, a grey-box system test. The mark-earning point is saying explicitly that levels and strategies are independent axes that combine, not one list.

QUESTION: Question three, four marks. Explain the facade pattern and one benefit, and explain how it relates to encapsulation. Pause, answer, play.

NARRATOR: Model answer. A facade is a tidy front desk over a messy back office — a single front-of-house class that hides a complex subsystem behind one simple, clean interface; the client talks only to the facade, which coordinates the internals. The benefit: decoupling — because the client depends only on the simple facade interface, the subsystem internals can change freely while the facade's signature stays stable. The relation to encapsulation: it's the same instinct at a larger scale — encapsulation hides one object's data behind its methods; the facade hides a whole subsystem behind one class. Both publish a stable front and hide the internals. The trap to avoid in the answer: a facade hides complexity, it does not remove it — the subsystems still exist and still do all the work. Writing "removes" loses the mark.

QUESTION: Question four, six marks, the integrated one. Assess the effectiveness of a class that calculates student grade averages. In your answer, refer to all four dimensions of effectiveness. Pause, write a full response, then play.

NARRATOR: Model answer, and the whole game here is naming all four dimensions and applying each — C-C-P-M — because the number-one loss is writing only about speed. Correctness: it returns the right average for valid grades and raises an exception on invalid input like a grade above one hundred, and this is verified by unit tests at the boundaries — the boundary cases are where Boundary Value Analysis confirms correctness. Clarity: the code is readable — self-documenting names like calculate-average, docstrings on the public methods, and comments that explain the why, not the what. Performance: name the complexity — if it looks a student up in a list that's a linear search, order n; swapping to a dictionary keyed by identifier makes it constant time, order one, and that algorithmic change dwarfs any line-level tweak — fix the algorithm before the line. Maintainability: small single-responsibility classes mean a change to grading rules touches one place — Name it, Document it, Size it, Structure it. Close by ranking them: Correctness is non-negotiable and comes first — fast wrong code is worthless — which is why Performance sits third, not first. Four named dimensions, each applied to the actual code, with a priority ordering — that's the full six.

QUESTION: Question five, four marks. With reference to a real example, explain why a reused software component must be re-tested in its new context. Pause, answer, play.

NARRATOR: Model answer. State the principle first: reuse saves effort, but a component that worked correctly in one context can fail in another because its assumptions — the range of its inputs, the conditions it runs under — may no longer hold; the old tests passing proves nothing about the new context. Then the real example, told tightly: Ariane Five, Flight Five-Oh-One, nineteen ninety-six. The flight-control software reused a working inertial-reference component from the slower Ariane Four without re-testing it for Ariane Five's faster, steeper flight profile. A value that was always small on Ariane Four was now large, it overflowed a sixteen-bit slot, the guidance failed, and the rocket self-destructed about thirty-seven seconds after launch, around three hundred and seventy million dollars lost. The lesson, and the closing mark: integration and system testing exist precisely to re-validate reused components against the new system — reuse without re-testing is the gap they close. That real example anchors the principle and earns the application marks.
