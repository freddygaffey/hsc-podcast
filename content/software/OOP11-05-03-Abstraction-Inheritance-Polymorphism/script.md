NARRATOR: Here's the part that trips people up, so let's be precise: abstraction and encapsulation are close cousins and the exam loves to test whether you can tell them apart. Encapsulation, from last episode, is about access control — bundling data with its methods and restricting who can touch the internals. Abstraction is about complexity management — hiding the how, exposing the what. They work together: you encapsulate to protect the data, and the result is an abstraction — a simple surface over a complicated inside. A clean one-liner for the exam: encapsulation hides the data; abstraction hides the complexity. Same instinct, different target.

NARRATOR: Now generalisation — and pay attention here because this is the concept most students can't keep separate from inheritance, and the exam directly asks you to distinguish them. Definition: generalisation is the process of identifying the common characteristics and behaviours shared across several different objects, and capturing those shared traits in a single, more general model. Read that again — it's a process of identifying and modelling. Think about a car, a motorcycle, a truck, a bicycle. They're all different, but they share traits: they all have a make and a model, they all have a speed, they can all start, accelerate, and stop. Generalisation is the act of noticing that and saying "there's a more general thing here — a Vehicle — and these are all kinds of it."

NARRATOR: Here's the line I want burned into your memory, because it's the answer to the "distinguish generalisation from inheritance" question, and it's worth real marks: generalisation is a modelling act; inheritance is an implementation act. Generalisation happens in your head and on the whiteboard — it's design thinking. You look at Car and Motorcycle, you spot what they have in common, and you decide there should be a general Vehicle concept above them. You haven't written a single line of code yet. Inheritance is what you do afterwards, in the actual programming language, to make that model real — you write a Vehicle class and you have Car and Motorcycle inherit from it. Generalisation is the design decision; inheritance is the code that delivers it. Same relationship, two different layers.

NARRATOR: So here's the mnemonic, and write it down because it's the whole distinction in five words: "Generalise to model, inherit to reuse." Generalise to model — that's the thinking step, spotting the shared traits and drawing the general concept. Inherit to reuse — that's the coding step, where the subclasses reuse the general class's code. If a question says "distinguish generalisation from inheritance," you open with: generalisation is a modelling activity that identifies shared traits to form a general class; inheritance is the implementation mechanism that lets a subclass reuse that general class's attributes and methods. Those two sentences are the marks.

NARRATOR: So let's do the inheritance — the I in A-PIE. Definition: inheritance lets you create a new class based on an existing one, where the new class automatically receives the attributes and methods of the existing one, and can add new features or modify what it inherited. The existing class is called the parent class, the base class, or the superclass — those are three names for the same thing, and the exam uses all three, so know all three. The new class is the child class or subclass. We say the subclass "is-a" kind of the parent — a Car is-a Vehicle. Hold onto that "is-a" phrase; it comes back next episode as the test for whether inheritance is even the right tool.

NARRATOR: Let's make it real with the Vehicle hierarchy — this is Listing two. We write a Vehicle class with the shared stuff: a make, a model, a speed, and methods to start and stop. Then Car inherits from Vehicle, and Motorcycle inherits from Vehicle. Each subclass gets start and stop for free — that's the reuse. But each adds and changes things. Now, the two pieces of inheritance machinery the exam cares about, and that students get wrong.

NARRATOR: First: super, spelled s-u-p-e-r, said "super." When a subclass needs to set up the attributes the parent defines, it calls the parent's constructor using super, dot, double-underscore-init — which we pronounce "dunder init", because in Python the double underscore around a name is read as "dunder", short for double-underscore. So in Car's constructor you write super, dot, dunder init, passing the make and the model up to the Vehicle constructor, and then you set the car-specific attribute, like the number of doors. The mark-earning phrasing: super lets a subclass call a method on its parent class — most importantly the parent's constructor — so the parent's setup runs and isn't duplicated. And the single most common bug in all of beginner OOP, the one I want you to flag in your own code forever: if you forget to call super, dunder init, in a subclass constructor, the parent's constructor never runs, so none of the inherited attributes — make, model, speed — ever get set, and your object is half-built. Forgetting super, dunder init, is the classic inheritance mistake.

NARRATOR: Second piece of machinery: overriding. A subclass can redefine a method it inherited, providing its own version. In the Vehicle example, both Car and Motorcycle define their own accelerate method — Car adds ten to the speed, Motorcycle adds twenty, because motorcycles accelerate harder. Same method name, accelerate, but the subclass's version replaces the inherited behaviour for objects of that subclass. That's overriding — and hold that thought, because overriding is the bridge straight into the fourth concept. The reuse came from inheriting start and stop; the customisation came from overriding accelerate. That combination — inherit what's common, override what differs — is the entire point of an inheritance hierarchy.

NARRATOR: Which brings us to polymorphism — the P in A-PIE, and the one with the intimidating name. Polymorphism is Greek for "many forms." Definition, exam-ready: polymorphism means a single interface — the same method call — produces different behaviours depending on the object it's called on. One message, many responses. You saw the seed of it a second ago: calling accelerate on a Car and calling accelerate on a Motorcycle are the same method name, but they do different things. That's polymorphism. The deeper, more useful version is this: you can write one piece of code that calls a method on a collection of different objects, and each object responds in its own way, and your code doesn't need to know or care which specific type each object is.

NARRATOR: The example to lock this in is what the textbook calls the Animal Concert — Listing three. You have three classes: Dog, Cat, and Bird. Each one has a method called make-sound. The Dog's make-sound returns "Woof", the Cat's returns "Meow", the Bird's returns "Tweet." Now you write one function — call it animal-concert — that takes a list of animals and loops over them, and for each animal it just calls make-sound. One loop. One method call inside it. But the dog barks, the cat meows, the bird tweets. The loop never asks "are you a dog or a cat?" It just sends the make-sound message and each object responds in its own form. That's polymorphism doing its job — one interface, many behaviours — and it's exactly the answer to the exam question "explain how polymorphism lets one loop handle many object types." The loop calls one method; each object's own version runs. You can add a fourth animal — a Cow — tomorrow, and the loop doesn't change one character. That's the power: the code is open to new types without modification.

QUESTION: So in that Animal Concert example — were Dog, Cat and Bird inheriting from a common Animal parent class? Did they have to?

NARRATOR: No, and this is the single most important thing in the whole episode, so I'm going to say it more than once and in more than one way. In that example, Dog, Cat, and Bird did not share a parent class at all. They were three completely independent classes that just happened to each have a method called make-sound. And the loop worked anyway. This is the trap that costs marks: students assume polymorphism requires inheritance — that the objects must share a parent. In many languages, like Java or C-sharp, that's broadly true. But in Python it is not. Python uses something called duck typing.

NARRATOR: Duck typing — the phrase comes from the old saying: "If it walks like a duck and quacks like a duck, treat it like a duck." Here's what it means in practice: Python does not check an object's type or its family tree before calling a method. It just tries to call the method. If the object has a make-sound method, it works — Python does not care what class the object is, or whether it inherited from anything. The "type" that matters isn't the declared class; it's whether the object can do what's being asked. If it quacks, it'll do. So in Python, polymorphism does not require a shared base class. It requires only that the objects all respond to the same method name. The mnemonic — say it with me — "duck typing: if it quacks, it'll do."

NARRATOR: Let me hammer the contrast home with an example that has no animals and no shared parent whatsoever — Listing four. Three classes: a WashingMachine, a Dishwasher, and a Printer. These have nothing to do with each other. A printer is not a kind of washing machine. There is no sensible parent class above all three. But suppose each one has a method called start. Now you can write one function that takes any appliance and calls start on it, and it works for all three — the washing machine starts a wash cycle, the dishwasher starts a clean cycle, the printer initialises. No inheritance anywhere. No shared parent. Pure duck typing. The objects are polymorphic because they share an interface — the start method — not because they share a bloodline. If a question asks "what is duck typing," your answer: duck typing is Python's approach to polymorphism where an object's suitability is determined by whether it has the required method, not by its class or inheritance — if an object has the method you call, it works, regardless of its type.

NARRATOR: Now I want to deliberately repeat the key point, because at high listening speed a single mention slides past and this one is worth too much to lose. Polymorphism is the idea: one interface, many behaviours. Inheritance is one way to achieve it — subclasses overriding a shared method. Duck typing is another way to achieve it — unrelated classes that just happen to share a method name. Polymorphism does not require inheritance. Say that in the exam and you've dodged the most common trap in this dot-point.

NARRATOR: Okay. Four concepts, defined and kept distinct. Now let's see all four working together in one piece of code, because the exam's favourite high-mark question — the eight-marker — is "define abstraction, generalisation, inheritance and polymorphism and give an example of each," and a single well-chosen example can carry all four. That example is the Shape hierarchy — Listing five — and it's the capstone, so let's build it carefully.

NARRATOR: We start with a Shape class. Shape is the general model — that's generalisation: we looked across rectangles and circles, saw they're all shapes that have an area and a perimeter, and captured that common idea as a Shape class. Shape has a name and a method called describe that all shapes share. But here's the interesting bit. Shape also defines two methods, area and perimeter — and their bodies do nothing useful. Instead, each one raises an error called NotImplementedError, which we say as "not-implemented-error." This is an abstract method.

NARRATOR: Let me explain that properly because the dot-point and the exam both care about it. An abstract method is a method that's declared in a base class to define part of the interface, but is deliberately left without a real implementation, because the base class can't sensibly provide one. What is the area of a generic "shape"? There's no answer — it depends entirely on whether it's a rectangle or a circle. So the Shape class says, in effect: "every shape must have an area method, but I, the general Shape, refuse to define what it computes — that's my subclasses' job." And the way it enforces that in Python is by having area raise not-implemented-error. The effect is brutal and deliberate: if someone makes a subclass of Shape and forgets to provide a real area method, then the moment anything calls area on it, the program crashes with not-implemented-error — a loud, clear message saying "you forgot to implement this." That's the point of an abstract method: it forces every subclass to fill in the blank, and fails fast and obviously if one doesn't. So when you hear "abstract method raising not-implemented-error," the answer is: it defines a required method in the interface while forcing subclasses to provide the real implementation.

NARRATOR: Now we add Rectangle and Circle, both inheriting from Shape — that's inheritance, the implementation act delivering the generalisation. In each subclass's constructor we call super, dunder init, passing the shape's name up to the Shape class — there's our super again, setting up the inherited attribute. And then each subclass overrides area and perimeter with a real implementation. Rectangle's area returns width times height. Circle's area returns pi times radius squared. Same method names, completely different formulas — and that's polymorphism. Two shapes, one interface, two behaviours.

NARRATOR: And then the payoff, which ties the bow on abstraction and polymorphism at once. You write a function — calculate-total-area — that takes a list of shapes and loops over them, adding up area on each. One loop, one method call. Put a rectangle, a circle, and another rectangle in the list, and the function sums their areas correctly without ever checking which shape is which. It's polymorphic — each shape runs its own area — and it's an abstraction — the function works at the level of "a shape has an area," hiding the formulas entirely. So in that one Shape example you can point to all four: generalisation, when we modelled the common Shape; inheritance, when Rectangle and Circle reused Shape via super; polymorphism, when each overrode area to behave differently; and abstraction, when the total-area function operated on the simple "shape has an area" interface and ignored the messy specifics. One example, four marks — that's why it's the capstone.
