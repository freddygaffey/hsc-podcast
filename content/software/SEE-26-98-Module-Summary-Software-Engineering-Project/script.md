NARRATOR: This is the Software Engineering Project summary — the cram episode, and the last one of the whole course. The job: sweep the project module top to bottom, refresh every dot-point in a couple of sharp sentences, and dump every mnemonic so you can offload the lot in the first minute of the exam. Get a pen — the exam dump first.

NARRATOR: The marquee set, the hooks to write down before you read a single question. "DiP-PP" — the four implementation methods. "Waterfall Falls once; Agile Goes around" — the two project models in five words. "Scope-Time-Cost" — the project triangle. "I-F-N" — the three client-communication issues. And "C-E-R" — the three parts of an evaluation. Those five anchor the module; now we go through it so each one means something.

NARRATOR: The module arc, because the shape is the memory aid. This is the synthesis module — the major project — and it reuses everything: the lifecycle and algorithms from Year Eleven, objects from the object-oriented module, the web stack, security, and automation. Four movements. Defining and ideating — chapter twenty-three: what to build, whether it's feasible, and how to roll it out. Planning and managing — chapter twenty-four: Waterfall, Agile, the hybrid, scheduling, ethics and communication, and quality assurance. Building — chapter twenty-five: constructing, presenting, the back end, backups and version control, overcoming difficulties, and prototyping the interface. Testing and evaluating — chapter twenty-six: testing and optimisation, feedback, and the final evaluation. Define, plan, build, evaluate — the project lifecycle itself.

NARRATOR: Chapter twenty-three, requirements and feasibility. Requirements split two ways — "FUN vs PERF": functional requirements are what the system must do; non-functional are how well it must do it — performance, security, usability. Good requirements are measurable, testable, and carry acceptance criteria, and clear scope boundaries are what stop scope creep. Feasibility is checked across four areas, mnemonic TECO: Technical — can we build it; Economic — is it worth it; Cost-and-schedule — can we afford the time and money; Operational — will it actually fit how people work. The answer shape: name the requirement type or feasibility area, and tie it to evidence.

NARRATOR: Chapter twenty-three, ideation and modelling tools. Ideation — generating the idea — is B-M-S: Brainstorm, Mind-map, Storyboard. Then the modelling tools you already know — data flow diagrams, structure charts, class diagrams — carry straight in from earlier modules to represent the system. And the build-toolkit, the software that supports development, is C-T-I-M: Code generation, Testing and debugging, Installation, Maintenance. The justify-shape for any tool question: name the tool, its mechanism, and why it helps.

NARRATOR: Chapter twenty-three, implementation methods — the marquee, DiP-PP: Direct, Phased, Parallel, Pilot. Direct is the big-bang switch — cheap and fast, but no fallback if it fails. Phased rolls out piece by piece, so you learn as you go. Parallel runs the old and new systems at once — a safety net that lets you verify the new against the old, but it's costly to run both. Pilot launches the whole system to a small group first, then widens. The one-liner: "Direct is cheap and risky; Parallel is safe and expensive." Choose by how costly failure would be.

QUESTION: First retrieval. Pause the player and name the four implementation methods from DiP-PP, and for each give its one defining trait. Then play.

NARRATOR: DiP-PP. Direct — instant switch, cheap, no fallback. Phased — piece by piece, learn as you go. Parallel — both systems at once, safe but expensive. Pilot — small group first, then roll out wide. Cheap-and-risky, gradual, safe-and-costly, test-on-a-few. If you tied each method to its risk-versus-cost trade-off, that's the mark — because every "recommend a method" answer is justified by the cost of failure.

NARRATOR: Chapter twenty-four, the two project-management models. "Waterfall Falls once" — a single sequential pass through the stages, all requirements up front, no cheap going back, best when requirements are stable. "Agile Goes around" — iterative sprints, each delivering working software, requirements allowed to evolve; the four ceremonies are P-S-R-R: Plan, Standup, Review, Retro — and remember the Review is about the product, the Retro about the process — with work framed as user stories, "as a user, I want something, so that I get a benefit." The advantage-disadvantage answer shape is always FEATURE plus CONSEQUENCE, and the marquee point, as in Year Eleven: neither wins universally — fit the model to requirement stability.

NARRATOR: Chapter twenty-four, the WAgile hybrid. "WAgile equals Waterfall gates plus Agile sprints" — plan big, build small: heavyweight phase gates for governance and sign-off, with Agile sprints doing the actual building inside them. The answer shape is the mechanism — gates plus sprints — plus the when-and-how, not just "it combines both."

NARRATOR: Chapter twenty-four, project management tools and the Gantt chart. The trade-off triangle is Scope-Time-Cost, with quality in the middle — you can pin any two, but the third must give. A Gantt chart is bars over time with arrows for dependencies, and the longest chain of dependent tasks is the critical path — and the stimulus rule to bank: the critical path has zero slack, so a slip on any critical task slips the whole project.

NARRATOR: Chapter twenty-four, social, ethical and communication issues. The three communication issues with the client are I-F-N: Involve and empower the client, enable Feedback, and Negotiate. The four ethical areas are PABT: Privacy, Accessibility, Bias, Transparency. Negotiation follows a shape: clarify the need, assess it, lay out options, document the decision. The marks come from naming the specific issue and the concrete practice that addresses it.

NARRATOR: Chapter twenty-four, quality assurance. QA is 3C: Criteria, Continual checking, Compliance. The four quality criteria are C-U-P-S: Correctness, Usability, Performance, Security. And the marquee distinction you must state: QA is the process that prevents defects; testing is the activity that detects them. QA is the whole quality system; testing is one activity inside it.

QUESTION: Retrieval. Pause and state the Scope-Time-Cost triangle in your own words, and give the difference between quality assurance and testing. Then play.

NARRATOR: Scope-Time-Cost: a project has three competing constraints — how much it does, how long it takes, and how much it costs — with quality in the middle; you can fix two, but the third has to move, so widening scope on a fixed deadline and budget costs quality. And QA versus testing: quality assurance is the process built into the whole project to prevent defects — standards, reviews, criteria — while testing is the specific activity that detects defects in the product. Prevention versus detection. Saying QA prevents and testing detects is the mark.

NARRATOR: Chapter twenty-five, building the solution. Build incrementally — the reasons are REFF: Risk reduction, Early feedback, Flexibility, Frequent value. And you hold quality while building with S-R-I: Standards, Review, and continuous Integration. The thread from Year Eleven holds — keep the mainline clean, one task per subroutine.

NARRATOR: Chapter twenty-five, presenting the solution. Match the message to the audience, T-B-E-D: Technical, Business, End-users, Decision-makers — each needs a different level. And the presentation arc is P-S-D-B-N: Problem, Solution, Demo, Benefits, Next steps. Plus slide minimalism — the slide supports you, it isn't the script.

NARRATOR: Chapter twenty-five, algorithms, documentation and back-end engineering. The back-end concerns are T-E-I-S — "the back end teases the front end into working": Technology choice, Error handling, Interfacing, Security. This is where the web module's request flow, the security of CIA-AAA and "hash is one-way, encrypt is two-way," and the supply-chain lessons all come back inside your own build.

NARRATOR: Chapter twenty-five, data backup and version control. Version-control concepts are R-C-B-M-T: Repository, Commit, Branch, Merge, Tag. Backups follow the 3-2-1 rule — three copies, on two media, with one off-site. And version numbers follow semantic versioning: "Major breaks, Minor adds, Patch fixes" — a major bump signals a breaking change, minor adds compatible features, patch fixes bugs. The working habit: commit small, branch per feature, tag your releases.

NARRATOR: Chapter twenty-five, overcoming development difficulties. Blockers come in three kinds, T-R-P: Technical, Resource, Process. And the three syllabus strategies are a ladder, S-P-O: Self-search first, then Peers, then Outsource or escalate. The shape: name the blocker type, then climb the ladder.

NARRATOR: Chapter twenty-five, prototype and interface design. The fidelity ladder is S-W-M-P: Sketch, Wireframe, Mockup, Prototype — rising from rough to interactive. And interface quality reuses the web module's POUR accessibility principles and Nielsen's usability heuristics. Prototype low-fidelity first, because it's cheap to change before you've built anything.

NARRATOR: Chapter twenty-six, testing methodologies and optimisation. A test plan has the components O-S-A-E-S, said "oh-seas": Objectives, Scope, Approaches, Environments, Schedule — and it traces back to the requirements and QA criteria. The box methods: "Black sees nothing, White sees the code, Grey sees a bit" — black-box tests behaviour without seeing inside, white-box tests the internal paths, grey-box is partial knowledge. Test data is the Year Eleven set — every road through plus the edges, path and boundary. And optimisation is measure-optimise-measure: profile first, change, then measure again — never optimise on a guess.

NARRATOR: Chapter twenty-six, feedback analysis. Handle feedback with C-S-A: Collect, Synthesise, Act — gather it, find the patterns, then act on the highest-value items, prioritised on an impact-versus-effort matrix. And mind representativeness — biased or unrepresentative feedback skews what you build, the same bias caution from the automation module.

NARRATOR: Chapter twenty-six, evaluating the software solution — the last teaching lesson of the course. Evaluation is C-E-R: Criteria, Evidence, Reflection. State the criteria the solution is judged against — drawn from the requirements and the C-U-P-S quality set — present the evidence, including actual-versus-expected test results, then reflect: what worked, what didn't, what you'd do differently. Evaluation is a judgement backed by evidence, not a feelings summary — the same standard as the Year Eleven evaluate-solutions lesson, now across a whole project.

NARRATOR: Now the consolidated trap pass — fast, where the marks go. Neither Waterfall nor Agile wins universally — fit the model to requirement stability. "Compare" means contrast on shared axes plus a judgement, not describe-twice. On a Gantt question, the critical path is the longest dependent chain with zero slack — a slip there slips everything. QA is not testing — QA prevents, testing detects. "Evaluate" demands criteria, evidence, and a judgement — not a description and not a feelings summary. Functional versus non-functional — non-functional is the "how well," the quality attributes. And don't recommend an implementation method without justifying it by the cost of failure.

NARRATOR: To finish, a short exam-style set in real NESA verbs, model answers after each. The last self-test of the course.

QUESTION: Question one. A hospital is replacing a critical patient-records system where failure could endanger lives. Recommend an implementation method and justify your choice. Pause, attempt it, then play.

NARRATOR: Model answer: recommend Parallel implementation — run the old and new systems simultaneously for a period. The justification is the cost of failure: because the system is safety-critical, you cannot risk a direct switch with no fallback; running both at once gives a safety net if the new system fails and lets staff verify the new outputs against the trusted old ones before fully cutting over. The trade-off to acknowledge is cost — operating both systems is expensive and doubles the workload temporarily — but for a life-critical system that cost is justified. Naming Parallel, justifying by the cost of failure, and acknowledging the cost trade-off is the full-mark answer.

QUESTION: Question two. Distinguish between quality assurance and testing, and give one example of each. Pause, then play.

NARRATOR: Model answer: quality assurance is the process built into the whole project to prevent defects — for example, setting coding standards and holding code reviews so faults are avoided in the first place. Testing is the activity that detects defects in the built product — for example, running boundary-value test cases against a function to find where it fails. The distinguishing point is prevention versus detection: QA is the overarching preventive process, testing is one detective activity within it. The 3C of QA — Criteria, Continual checking, Compliance — versus the test plan and box methods of testing. Naming the prevent-versus-detect contrast with a concrete example each is the mark.

QUESTION: Question three, the synthesis one. A team has built their major project and must evaluate it. Describe how they should structure their evaluation and what evidence they should present. Pause the player, plan an answer, then play.

NARRATOR: Model answer: structure it as C-E-R — Criteria, Evidence, Reflection. First, state the criteria: the functional and non-functional requirements from the start of the project, plus the quality criteria C-U-P-S — Correctness, Usability, Performance, Security. Second, present evidence against each criterion: test results comparing actual to expected outputs, including boundary and path coverage; performance measurements; and user feedback gathered and synthesised with Collect-Synthesise-Act. Third, reflect: judge how well each criterion was met, what succeeded, what fell short, and what you would do differently next time — a genuine judgement, not a feelings summary. A full-mark answer ties the criteria back to the original requirements, presents real actual-versus-expected evidence, and ends in a justified judgement. That's the whole of the Software Engineering Project — define, plan, build, test, and evaluate — and it's the synthesis of the entire course: every module you've studied comes back inside building one real piece of software.
