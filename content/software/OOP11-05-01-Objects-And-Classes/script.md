NARRATOR: New module, and a big one. This is the first episode of the Object-Oriented Paradigm — the second of your three Year Eleven modules, sitting after Programming Fundamentals and before Programming Mechatronics. So there's no "last lesson" to recap in the usual sense. Instead, let me bridge from where you already are as a programmer, because that's the fastest way into this.

NARRATOR: In Programming Fundamentals you wrote procedural code. You had data on one side — variables, lists, records, dictionaries — and you had functions on the other side that acted on that data. A function took the data in as parameters, did something, handed a result back. The data and the code that operated on it lived apart. You'd pass a customer's name and balance into an update function, the function did its work, and then it forgot all about that customer. The data didn't carry its own behaviour around with it.

NARRATOR: Object-oriented programming, which from here on I'll just call OOP, flips that arrangement. Instead of data sitting passively while functions act on it from the outside, OOP bundles the data and the functions that guard it into a single thing called an object. The data and the behaviour live together, in one unit, and the object protects its own data. That one idea — data and the methods that act on it, bundled together — is the seed of this entire module. Hold onto it.

NARRATOR: Here's the shape of where we're going, so you've got a map. The syllabus lists seven key features of an object-oriented language. There's a structural group — objects, classes, and generalisation — and then there are four behaviours you'll meet over the next few episodes. Those four behaviours have a mnemonic I want you to lock in right now, because it runs through the whole module: A-P-I-E, which you remember as the word "a pie". A-P-I-E stands for Abstraction, Polymorphism, Inheritance, Encapsulation. "Have a slice of a-pie to remember OOP." We're not teaching those four today — today is the foundation underneath them, objects and classes — but every time you hear "a-pie" through this module, that's the four behaviours. Today plants the seed; "a-pie" is the tree that grows out of it.

NARRATOR: So that's the bridge. You already know how to program. What you don't yet have is the HSC's framing — the exact terminology the syllabus uses, the way the exam words its questions, and the answers that actually earn marks. That's my whole job in this module. I'm not going to re-teach you what a variable or a loop is. I'm going to teach you to talk about your code the way a marker wants to hear it.

NARRATOR: Today's topic is the absolute foundation: objects, classes, and how objects talk to each other through something called message-passing. Let me read you the relevant part of the dot-points, because the wording matters. The first one: "Apply the key features of an object-oriented programming, or O-O-P, language. Including: objects, classes." The second, listed separately further down the same content list: "Investigate how OOP languages handle message-passing between objects." The outcome in play is S-E-eleven-oh-two — "explains how structural elements are used to develop programming code." That outcome verb, "explains," is a hint: this topic is examined by asking you to explain and define, not just to write code.

NARRATOR: So here are the questions you'll be able to answer by the end. What exactly is an object, in the syllabus's terms? What's the difference between a class and an instance — and why do students keep losing marks on that one? What's the difference between an attribute and a method? And the one that trips everybody up: what does it actually mean to say objects "pass messages" to each other, and what happens, step by step, when one object sends a message to another? If you can answer those four cleanly, you've got this dot-point.

NARRATOR: Let's start with the object, because everything else is built on it. The syllabus and the textbook both define an object the same way, and it's worth memorising the phrasing: an object is a software entity that combines data and behaviour into a single unit. The data part has a name — those are the object's attributes. The behaviour part has a name too — those are the object's methods. Say it as a slogan: an object is attributes plus methods. Attributes are what the object knows. Methods are what the object can do.

NARRATOR: The reason this feels natural is that it's how you already think about the real world. Take your phone. Your phone is an object. It has attributes — a colour, a screen size, a battery level, a model number. And it has behaviours — it can make a call, send a message, run an app. You don't think of "the battery level" floating around separately from "the phone." The data belongs to the phone, and the phone is the thing that does the actions. OOP just takes that natural way of seeing the world and puts it into code. Your car is an object: attributes like make, fuel level, and current speed; behaviours like accelerate and brake. Your pet is an object: attributes like name and age; behaviours like eat and sleep. Same pattern every time — a bundle of data, and a bundle of things it can do, wrapped together as one entity.

NARRATOR: Now, here's a connection back to Programming Fundamentals that earns marks if you can phrase it. In Fundamentals you used a record, or in Python a dictionary, to group related data — a customer record might hold a name, an address, and a balance. An object is like that record, but with one crucial addition: it carries its own behaviour as well. A record is just data; an object is data plus the methods that act on that data, bundled in. So if a question ever asks you how an object relates to the data structures you already knew, the strong answer is: "an object generalises a record by bundling behaviour, the methods, together with the data, the attributes — whereas a record holds data alone." That sentence is worth a mark because it names the relationship precisely instead of waving at it.

QUESTION: Hang on — you keep saying "attribute" and "method." In plain terms, how do I tell which is which when I'm looking at a class?

NARRATOR: Good, because the exam asks exactly this — "distinguish an attribute from a method" is a standard two-mark question. The clean test: an attribute is a piece of data the object stores, a noun describing its state — a balance, a name, a colour. A method is an action the object can perform, a verb — deposit, withdraw, accelerate. Attributes are what the object is; methods are what the object does. In the exam, define both and give one example of each, and make the examples come from the same object so the contrast is obvious. "In a bank account object, the balance is an attribute — data describing the account's state — while deposit is a method — a behaviour that changes that state." That's the two marks. Attribute equals data equals noun; method equals behaviour equals verb.

NARRATOR: Now the next concept, and this is the one that separates a band-four answer from a band-six answer: the difference between a class and an instance. Listen carefully, because students confuse these constantly and markers pounce on it.

NARRATOR: A class is a blueprint. It's a template. It defines the structure — it says "an account of this kind will have an account number, an owner name, and a balance, and it will be able to deposit, withdraw, and check its balance." But the class itself is not an actual account. It holds no real money. It's the design, the plan, written once. Think of an architect's blueprint for a house: the blueprint isn't a house you can live in, it's the instructions for building one, and you can build many houses from the same blueprint.

NARRATOR: An instance — also just called an object — is what you actually build from that blueprint. When you take the class and create a real, concrete account from it, with a real account number and a real balance, that real account is an instance. And the key point: from one class you can create many instances, each with its own data. The class is written once; the instances are created as many times as you like.

NARRATOR: Let me make that concrete with the example we'll use through this whole module. The class is called Bank Account — capital B, capital A, one word, the way classes are named. That class is the blueprint. Now I create two actual accounts from it. The first is Alice's account: account number A-C-C-zero-zero-one, owner Alice Smith, opening balance one thousand dollars. The second is Bob's account: account number A-C-C-zero-zero-two, owner Bob Jones, opening balance five hundred dollars. Both are instances of the same Bank Account class. They share the same structure — both have an account number, an owner name, and a balance — but they hold completely different data. Alice has a thousand dollars; Bob has five hundred. One blueprint; two real, independent objects. The full class is written out in Listing One, and the two accounts being created are in Listing Two, if you want to read along — but you don't need to see them to follow this.

NARRATOR: Hold onto that phone analogy too, because it's the cleanest way to say it in an exam. The class is "the iPhone design" — the specification every iPhone is built from. An instance is "the specific iPhone in your pocket," with your photos, your battery level, your scratches. The design is one thing; your particular phone is another, built from that design. Same with the car: "the two-thousand-twenty-four Corolla" as a model is the class; the actual silver Corolla parked outside, with forty thousand kilometres on it, is the instance.

QUESTION: This feels like the kind of thing the exam would phrase as a trick. Before you answer — what's the exact difference between a class and an instance? Pause the player now, say it out loud as if you're writing it for three marks, then play.

NARRATOR: Right. Here's the mark-earning answer. "A class is a blueprint or template that defines the attributes and methods objects of that type will have; it is written once and creates no data itself. An instance is a specific object created from that class, holding its own actual data. For example, Bank Account is a class defining account number, owner name, and balance; Alice's account and Bob's account are two separate instances of that class, each with its own balance." Notice what that answer does: it defines both terms, it states the one-to-many relationship — one class, many instances — and it gives an example with two distinct instances. That's the difference between a full-mark answer and a half-mark one.

NARRATOR: And here's the trap, named explicitly so you can avoid it. The most common mistake students make is talking about "the class" when they mean "the object," or describing a class as if it holds data. The class does not hold Alice's thousand dollars — Alice's instance does. If you write "the Bank Account class has a balance of one thousand," that's wrong, and a marker will dock it. The class has a balance attribute — a slot for a balance — but no actual value. The instance has the value. Keep "blueprint" and "built object" separate in your head, and you won't lose that mark.

NARRATOR: Now the second dot-point, and it's the one most students find genuinely strange the first time: message-passing. The syllabus says "investigate how OOP languages handle message-passing between objects." This is examined as its own thing, and it's usually worth around four marks, so let's get it properly.

NARRATOR: Here's the idea. Objects don't work in isolation. A program made of objects gets things done by objects talking to each other — and the way they talk is called message-passing. Now, "sending a message" sounds mysterious, but you already know what it is in code: sending a message to an object is calling a method on that object. That's it. When you write Alice's account dot deposit, two hundred — that's the syntax, object name, dot, method name, the value in brackets — what you are doing, in OOP language, is sending a "deposit" message to Alice's account object, and passing the value two hundred along with the message.

NARRATOR: Why use the word "message" at all, if it's just a method call? Because the framing matters for how you think about a system. The object that sends the message doesn't reach inside the receiving object and change its data directly. It sends a request — "please deposit two hundred" — and the receiving object decides how to handle it. Alice's account receives the deposit message, runs its own deposit method, updates its own balance, and sends back a response. The sender never touches the balance directly; it asks, and the object acts on itself. That's the whole philosophy of OOP in one move: objects are responsible for their own data, and they collaborate by sending each other messages, not by reaching into each other.

NARRATOR: So when I narrate the line "Alice's account dot deposit, two hundred," the right way to describe it in an exam is: "this sends the deposit message to Alice's account object, with two hundred as the parameter; the object runs its deposit method, adds two hundred to its own balance, and returns the new balance." Listing Two shows Alice receiving a deposit message and Bob receiving a withdraw message, if you want to see the code later.

QUESTION: Okay, but "investigate how the language handles it" sounds like they want the under-the-hood detail. What actually happens, step by step, when I call that method?

NARRATOR: Exactly right — that four-mark question wants the sequence, not just "it calls the method." There are five steps, and there's a mnemonic so you can reproduce them under pressure. The mnemonic is L-B-P-E-R. Lookup, Bind, Pass, Execute, Return. Let me walk each one with Alice's deposit.

NARRATOR: Step one, L for Lookup. When you call deposit on Alice's account, the language first looks up the deposit method. The instance itself doesn't store the method — the method lives on the class, the Bank Account blueprint. So Python finds the deposit method defined in the Bank Account class. That's method lookup.

NARRATOR: Step two, B for Bind self. This is the step that confuses everyone, so listen closely. The language automatically passes the object you called the method on — Alice's account — into the method as its first parameter. That first parameter is conventionally named self, spelled s-e-l-f. You never pass it yourself; the language binds it for you. So when you write "Alice's account dot deposit, two hundred," the method actually receives two things: self, which is bound to Alice's account, and the amount, which is two hundred. Self is how the method knows whose balance to change — it's the link from the method back to the specific instance it's running on.

NARRATOR: Step three, P for Pass parameters. The actual arguments you wrote in the brackets — here, the two hundred — get passed into the method's parameters. So amount becomes two hundred inside the method. Self was bound in step two; the explicit arguments are passed in step three.

NARRATOR: Step four, E for Execute. The method body now runs, with full access to the object's data through self. The deposit method checks that the amount is positive, then adds two hundred to self dot balance — that is, to Alice's balance specifically, not Bob's. Because self is Alice's account, every reference to the balance inside the method is Alice's balance.

NARRATOR: Step five, R for Return. The method finishes and hands a result back to whoever called it — here, a confirmation that two hundred was deposited and the new balance is twelve hundred. The caller receives that return value and carries on.

NARRATOR: Lookup, Bind, Pass, Execute, Return — L-B-P-E-R. If a four-mark question asks how the language handles message-passing, you write those five steps, in order, naming self-binding explicitly, and you've earned every mark. The single most impressive thing you can include is the self-binding point, because it's the one most students miss. Let me say it one more time in different words, because at speed it slips past: when you call a method on an object, the language secretly passes that object in as the first parameter, self, so the method knows which instance it's working on. Internally, "Alice's account dot deposit, two hundred" is really "Bank Account dot deposit, with Alice's account and two hundred." You write the short form; the language fills in self. And if you want to rehearse writing this in the exam's own pseudocode style, the deposit method itself is set out as pseudocode in Listing Three, and the full five-step dispatch is in Listing Four — have a read later; you don't need to see them to follow today.

QUESTION: Wait — so does that mean every method I write has to mention self?

NARRATOR: In Python, yes — every method defined in a class takes self as its first parameter, because that's how the method gets at the object's own data. You write the method with self in the brackets when you define it, but you don't pass self when you call it — the language binds it automatically. That asymmetry — defined with self, called without it — is exactly the thing that makes self feel like magic until you understand the binding step. It's not magic; it's step two, B for Bind. And that's a named trap: students forget self is auto-passed, then can't explain why a method written with two parameters is called with one argument. Now you can.

NARRATOR: Let me pull message-passing back to the bigger picture, because there's a mark in the philosophy. Objects collaborating by sending messages is the answer to a deeper exam-style question: "why structure a program as objects at all?" Because each object owns and protects its own data, and the only way to affect another object's data is to send it a message and let it decide what to do. That makes a large program manageable: you reason about one object at a time, and you trust the others to handle their own messages. Contrast that with the procedural world you came from, where any function could reach into any data — that's flexible, but it scales badly, because everything can touch everything. We'll do that procedural-versus-OOP comparison properly in a later episode — for now, just file the contrast: procedural code passes data around to functions; OOP code sends messages to objects that guard their own data.

NARRATOR: Time for a full worked example, the kind you'd see in a written exam, so you can hear the difference between a weak answer and a strong one. Here's the question: "Define the terms object, class and instance, and illustrate each with an example. Three marks."

NARRATOR: First, the weak answer — the band-four version. A weak answer says: "An object is a thing in a program. A class is a type of object. An instance is when you use the class." Now, that's not nonsense — there's a glimmer of understanding there — but it earns maybe one mark out of three. Why? It never names attributes or methods, it doesn't distinguish blueprint from built object, the definitions are circular — "a class is a type of object, an object is a thing" — and there's no example at all, even though the question explicitly says "illustrate each with an example." Listen for those gaps: vague, circular, no example.

NARRATOR: Now the strong answer — the band-six version. "An object is a software entity that combines data, called attributes, with behaviour, called methods, into a single unit — for example, a bank account object holding a balance and able to deposit. A class is a blueprint or template that defines the attributes and methods that objects of that type will have — for example, the Bank Account class defines an account number, an owner name, a balance, and the methods deposit, withdraw and check balance. An instance is a specific object created from a class, holding its own actual data — for example, Alice's account and Bob's account are two instances of the Bank Account class, with balances of one thousand and five hundred dollars respectively." Hear the difference? Every term defined precisely, each illustrated with a concrete example from one consistent scenario, and the class-versus-instance distinction made explicit with two separate instances. That's three marks out of three. The strong answer is longer, but every clause is doing work — naming the syllabus term, then giving the example that proves you understand it.

NARRATOR: One more worked piece, because it's the highest-value question on this dot-point. "Describe how an object-oriented language passes a message between objects. Four marks." The strong answer walks the L-B-P-E-R sequence with a concrete example: "When one object sends a message to another — for instance, calling deposit on Alice's account with the argument two hundred — the language first looks up the deposit method on the Bank Account class. It then binds the receiving object, Alice's account, to the method's first parameter, self, automatically. The explicit argument, two hundred, is passed to the amount parameter. The method executes using self to access Alice's own balance, adding two hundred to it. Finally it returns a result to the caller." Five steps, self-binding named, a worked example throughout. Four marks. If you only remember one thing from this episode for the exam, remember that you answer the message-passing question with a five-step sequence and the word self.

NARRATOR: Let me make two interleaving links forward, because this dot-point is genuinely load-bearing for the rest of your course, and connecting it now makes both ends stick. First, forward into Year Twelve, Software Automation. When you get to machine learning, the models you build are written as classes — there's a model class, you create an instance of it, you train that instance on data, and you call methods on it like fit and predict. Every one of those is exactly what we did today: a class as a blueprint, an instance built from it, methods called on the instance — message-passing. The mechanics you're learning here are the literal building blocks of the machine-learning code later. Second, forward into Programming for the Web, also Year Twelve: a web application is structured as objects too — there's a user object, a request object, a session object, and they collaborate by sending messages. When a web framework hands your code a "request" object and you call a method on it to read the data, that's message-passing, this exact pattern. So today isn't an isolated Year Eleven topic; it's the grammar of almost all the code you'll meet for the rest of the course.

NARRATOR: And one link back, to ground it: remember that an object generalises the record or dictionary you used in Programming Fundamentals — same grouped data, now with behaviour bundled in — and a method is just a subprogram, the functions you already wrote, except now bound to a particular object through self. So nothing here is brand new machinery; it's the Fundamentals machinery, reorganised so the data and the code that guards it live together.

NARRATOR: Let me also flag the third trap, since traps are where marks leak. Trap one was confusing the class with an instance — solved. Trap two was forgetting that self is auto-passed — solved. Trap three: thinking objects act in isolation. They don't. The whole point of OOP is collaboration through message-passing. If an exam asks why message-passing matters and you say "so an object can run its methods," that's incomplete — the real answer is "so objects can collaborate while each protects its own data; the sender requests, the receiver decides." Objects are a society, not a set of hermits. Say "collaborate" and "protect its own data" and you've got it.

NARRATOR: Now let's recap the things to remember from today — phrase these the way you'd write them in an answer. One: an object combines data, the attributes, with behaviour, the methods, into a single unit — attributes are nouns and describe state, methods are verbs and perform actions. Two: a class is a blueprint written once; an instance is a real object built from it, holding its own data — one class, many instances, and Alice's account and Bob's account are the example to reach for. Three: message-passing means sending a message to an object by calling a method on it; the sender requests, the receiver acts on its own data and returns a result. Four: the language handles a message in five steps — Lookup, Bind self, Pass parameters, Execute, Return — L-B-P-E-R — and the self-binding step is the one that earns you the distinguishing mark. And five, the preview: the four behaviours of OOP are A-P-I-E — Abstraction, Polymorphism, Inheritance, Encapsulation — "a slice of a-pie" — and we build those on top of this foundation in the next few episodes.
