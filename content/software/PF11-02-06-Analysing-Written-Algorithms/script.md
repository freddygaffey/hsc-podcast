NARRATOR: Welcome back. Five minutes looking backwards first — spaced repetition is the engine of this whole series, so the ideas that matter keep returning until they're permanent. Newest first.

NARRATOR: Last episode was subprograms — the two kinds. The hook: a function returns, a procedure performs. A function computes and hands a value back, used for its result; a procedure performs an action and returns nothing, used for its effect. You identify which is which by whether a returned value gets used. Parameters carry data three ways — in reads, out writes back, in-out does both — and the classic trap is printing inside a function instead of returning, so the caller gets nothing. Hold all of that close, because today we read whole algorithms full of procedures and functions and untangle how they fit together.

NARRATOR: Before that, decomposition — structure charts diagram a module hierarchy with high cohesion and low coupling, built top-down by stepwise refinement; plus the two strategies, divide-and-conquer and backtracking. Before that, pseudocode and flowcharts. And before that — and this is the one we lean on hardest today — analysing algorithms: I-O-P, determine the Inputs, Outputs, and Purpose, then verify by desk checking with a trace table. Today is I-O-P at full scale.

QUESTION: We did analysing algorithms back in two-point-two. What's left to analyse?

NARRATOR: Size, and connections. Back then the algorithms were tiny — one routine, a handful of lines. Real systems are dozens of subprograms calling each other, and there's a whole analysis sub-skill we deliberately held back for today. The full dot-point is: "Analyse the logic and structure of written algorithms," including "determining inputs and outputs; determining the purpose of the algorithm; desk checking and peer checking; determining connections of written algorithms to other subroutines or functions." We covered the first three earlier. Today's new piece is that last one — determining the connections to other subroutines and functions: which subprogram calls which, and how data flows between them. Outcome S-E-eleven-oh-two. This is the capstone of the analysis thread, and it's the skill you use every time you open unfamiliar code.

NARRATOR: Objectives up front. By the end you'll be able to: apply a systematic method to analyse a complete, multi-subprogram algorithm; identify its inputs, outputs, and purpose at the system level; map its structure and classify its subprograms as procedures or functions; trace a scenario through several subprograms with a trace table; and — the headline — determine the connections between subprograms: the call hierarchy and the data dependencies.

NARRATOR: Start with the method, because having a fixed routine is what stops you drowning in a big algorithm. Six steps, in order — and the order is the point, because each step sets up the next. One: read it through completely, get the big picture before any detail. Two: identify the inputs and outputs. Three: determine the purpose, in one sentence. Four: map the structure — list the subprograms and how they relate. Five: trace the logic — desk check a couple of real scenarios. Six: check the connections and the design — how the parts depend on each other. Notice steps two and three are exactly I-O-P from the earlier episode, now just the middle of a bigger routine. The hook for the whole thing: Read, I-O-P, Map, Trace, Check. Read it, work out I-O-P, Map the structure, Trace a path, Check the connections.

NARRATOR: Let's run that method on a real example — a student course management system that lets a student enrol in a course, withdraw from one, or view their enrolments. The main algorithm and its key subprograms are in Listing 1. Step one, read through: it's a menu loop — show a menu, get a choice, and branch to enrol, withdraw, view, or exit, repeating until exit.

NARRATOR: Step two, inputs and outputs — at the system level, not line by line. The external inputs are the things the user types: the menu choice, a student identifier, and a course code. The external outputs are what the system shows: the menu, confirmation messages on success, error messages on failure, and the list of enrolments. And notice a third category you should name in a strong answer — internal data flow: values returned from one subprogram and passed into another, and updates written to the database. Calling that out is the difference between a surface answer and one that shows you understand the system moves data internally, not just in and out at the edges.

NARRATOR: Step three, purpose, one sentence: the algorithm manages student course enrolments and withdrawals, with validation and clear feedback, and lets students view their current enrolments. Precise, fits this system and no other — the same one-sentence discipline from the I-O-P episode.

NARRATOR: Step four, map the structure. You don't memorise forty subprograms — you group them by job, which is the cohesion idea from two episodes back. There are user-interface subprograms — display-the-menu, get-the-student-identifier, display-an-error. There are validation subprograms — check-eligibility, check-current-enrolment, check-the-withdrawal-deadline. There are business-logic subprograms — process-the-enrolment, get-the-block-reason. And there are data-access subprograms — add-to-the-database, update-the-capacity. Four groups. And as you map, classify each as procedure or function using last episode's test. Check-eligibility returns true or false — function. Get-the-block-reason returns a string — function. Process-the-enrolment performs actions and returns nothing — procedure. Display-an-error — procedure. The grouped map is in Listing 2.

NARRATOR: Step five, trace the logic — desk check, but now across subprogram calls. Take a successful enrolment. The choice comes back as "enrol". Get-the-student-identifier returns, say, S-twelve-three-four-five. Get-the-course-code returns C-S-one-oh-one. Then check-eligibility is called with both, and returns true. Because it's true, process-the-enrolment runs, and display-confirmation shows "Enrolment successful". The full trace table is in Listing 3. Now trace a failure — same start, but the course is full. Check-eligibility returns false this time. Because it's false, the other branch runs: get-the-block-reason is called and returns "Course is full", and display-error shows "Cannot enrol: Course is full". That trace is in Listing 4. Two scenarios, two paths — and remember the rule from the desk-checking episode: never trace just one path. The pass and the fail exercise different branches and different subprograms.

QUESTION: Here's one to actually attempt. Pause the player. In that course system, trace a withdrawal where the student is enrolled but the withdrawal deadline has already passed. Which subprograms get called, and what's the output? Work it out, then play.

NARRATOR: The choice is "withdraw". Get-the-student-identifier and get-the-course-code return their values. Check-current-enrolment is called and returns true — the student is enrolled. Because that's true, check-the-withdrawal-deadline is called — and it returns false, the deadline has passed. So the inner branch fails and display-error shows "Withdrawal deadline has passed". Process-the-withdrawal is never called, because the deadline check gated it. That gating is exactly what we mean by a connection — and that's step six.

NARRATOR: Step six, the new skill: determine the connections between subprograms. There are two kinds, and naming both is what earns the marks. The first is the call connection — which subprogram calls which, the hierarchy. The main algorithm calls check-eligibility; check-eligibility in turn calls four smaller checks — check-prerequisites, check-capacity, check-schedule-conflicts, and check-current-enrolment — and combines their results with "and". So check-eligibility is true only when all four are true. That's a parent calling its helpers, the structure chart from the decomposition episode, read off real code. The second kind is the data dependency — where one subprogram's output feeds another's input or controls a decision. Check-eligibility's returned true-or-false controls whether process-the-enrolment runs at all. Get-the-block-reason is only meaningful after eligibility came back false. The result of one routine determines the path through others. The one-liner to remember: a connection is either a call — who runs whom — or a data hand-off — whose result feeds whom.

QUESTION: How would the exam phrase a question about connections?

NARRATOR: Usually "identify the subprograms that check-eligibility depends on," or "explain the relationship between check-eligibility and process-the-enrolment." For the first: check-eligibility depends on check-prerequisites, check-capacity, check-schedule-conflicts, and check-current-enrolment — it calls all four and returns true only if all return true. For the second: process-the-enrolment has a data dependency on check-eligibility — it only executes when check-eligibility returns true, so the eligibility result controls whether enrolment proceeds. A weak answer says "they're both about enrolling." A strong answer names the call relationship and the direction of the data — who calls whom, and whose result gates whom. That precision is the mark.

NARRATOR: And the trap to avoid here, the one the markers hunt for: missing a data dependency. It's easy to list the subprograms and miss that one routine's output silently controls another. If you say process-the-enrolment and check-eligibility are unrelated siblings, you've missed that eligibility gates enrolment entirely — a real connection, invisible if you only read names and not data flow. The other trap is the one from last episode resurfacing: misclassifying a subprogram, calling a function a procedure or vice versa — check the return, every time.

NARRATOR: To make the connections concrete and checkable, Listing 5 is a simplified version of the enrolment core as runnable code: check-eligibility composed from four boolean checks, and get-the-block-reason mirroring them to explain a failure. You can see eligibility return true only when all four checks pass, and the block reason pick out exactly which check failed — the call hierarchy and the data dependencies, executing.

QUESTION: Question one. For the course management system, state its purpose and identify its inputs and outputs.

NARRATOR: Purpose: the algorithm manages student course enrolments and withdrawals with validation and feedback, and displays a student's current enrolments. Inputs: the user's menu choice, a student identifier, and a course code, all entered by the user. Outputs: the menu, confirmation messages on success, error messages on failure, and the enrolment list. For full marks, add the internal data flow — returned values passed between subprograms and updates written to the database — to show you see the system moving data internally, not just at the edges.

QUESTION: Question two. Identify the subprograms that check-eligibility depends on, and state the relationship. Pause the player, write your answer, then play.

NARRATOR: Check-eligibility depends on four subprograms: check-prerequisites, check-capacity, check-schedule-conflicts, and check-current-enrolment. The relationship: check-eligibility calls all four and combines their boolean results with logical "and", so it returns true only when every one of them returns true — a parent subprogram aggregating its helper checks. The marks are for naming all four and stating the "all must be true" combining logic, not just listing them.

QUESTION: Question three. Classify each of these as a procedure or a function, with a reason: check-current-enrolment, process-the-enrolment, get-the-block-reason, display-an-error.

NARRATOR: Check-current-enrolment is a function — it returns true or false. Get-the-block-reason is a function — it returns a string. Process-the-enrolment is a procedure — it performs actions, updating records, and returns nothing. Display-an-error is a procedure — it performs an action, showing a message, and returns nothing. The reason every time is the return: a used value back means function; an action with nothing back means procedure.

QUESTION: Question four. Explain the connection between check-eligibility and process-the-enrolment, and why missing this connection would be an analysis error.

NARRATOR: There is a data dependency: process-the-enrolment executes only when check-eligibility returns true, so the eligibility result controls whether enrolment proceeds. Missing it would be an analysis error because you'd treat the two as independent when in fact one gates the other — you'd misunderstand the control flow, and any change to eligibility would have an unforeseen effect on enrolment. The mark-earning phrasing: "process-the-enrolment is conditionally executed on check-eligibility's returned value — a data dependency that determines the control flow."

QUESTION: Question five. Describe the systematic method you would use to analyse an unfamiliar written algorithm.

NARRATOR: Read the algorithm through completely to get the overall picture; identify its inputs and outputs; determine its purpose in one sentence; map its structure by listing the subprograms, grouping them by role, and classifying each as a procedure or function; trace the logic by desk checking representative scenarios, including at least one success and one failure path; and determine the connections between subprograms — the call hierarchy and the data dependencies. The marks are for a clear ordered method that ends with verifying behaviour and connections, not just reading. The hook is Read, I-O-P, Map, Trace, Check.
