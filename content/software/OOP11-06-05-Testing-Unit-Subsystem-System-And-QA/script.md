NARRATOR: Let's start with the single most testable fact in this entire topic: the three levels. Unit, subsystem, system. The mnemonic is "U-S-S" — Unit, Subsystem, System — and I want you to picture it as a ship, the U-S-S something, because the three levels stack like the decks of a ship from the smallest cabin up to the whole vessel. U-S-S. When you sit down in the exam, the very first thing you dump on the page is U-S-S, Unit, Subsystem, System, then write a line on each.

NARRATOR: Unit testing first. A unit test checks the smallest testable part of your program in isolation — typically one method, or one small group of related methods inside a single class. The key word in any unit-testing answer is isolation. You are testing one thing, on its own, with nothing else involved. If your account class has a withdraw method, a unit test for withdraw checks: does a valid withdrawal reduce the balance correctly? Does withdrawing more than the balance raise the right error? Does withdrawing zero get rejected? Each of those is one unit test, checking one behaviour of one method. Nothing about the library, nothing about the database, nothing about the user interface — just that method, on its own.

NARRATOR: Now, what makes a unit test a good unit test? This is a guaranteed exam question — "list three properties of a good unit test" — and there's a beautiful mnemonic that's basically standard in the industry, so use it: a good unit test is "FIRST". F-I-R-S-T, FIRST. Fast, Independent, Repeatable, Self-validating, Timely. Let me unpack each, because every letter is markable.

NARRATOR: F — Fast. A unit test runs in milliseconds. Why does that matter? Because you run hundreds or thousands of them, constantly, and if the suite takes ten minutes nobody runs it. Fast tests get run; slow tests get skipped, and a skipped test catches nothing.

NARRATOR: I — Independent. And this is the big one, the one the exam loves, so I'm going to come back to it. Each test stands completely on its own. It does not depend on any other test having run first, and it does not leave behind state that affects the next test. You should be able to run your tests in any order, or run just one of them, and get the same result every time.

NARRATOR: R — Repeatable. Run it a hundred times, get the same answer a hundred times. No dependence on today's date, no dependence on a network connection, no random numbers leaking in. Same input, same result, always.

NARRATOR: S — Self-validating. The test decides pass or fail on its own. It doesn't print a number and ask you to eyeball whether it looks right. It asserts the expected result, and you get a clear green pass or red fail with no human judgement in the loop.

NARRATOR: T — Timely. You write the test close to when you write the code — ideally just before or just after, not bolted on months later when you've forgotten how the thing works. Timely tests are written while the design is fresh, and they shape the design for the better.

NARRATOR: Fast, Independent, Repeatable, Self-validating, Timely. FIRST. That's your "properties of a good unit test" answer, fully loaded.

QUESTION: You flagged Independent as the big one. Why does it matter so much that tests don't depend on each other? Pause the player, have a real go at answering, then come back.

[pause]

NARRATOR: Here's the answer, and it's worth a couple of marks every time. Imagine test number three deposits fifty dollars into a shared account, and test number four assumes that fifty is there and withdrawals against it. Now they're chained. Three problems follow immediately. First, if test three fails or you delete it, test four breaks for no reason of its own — you get a cascade of failures and you can't tell which one is the real bug. Second, you can't run test four on its own to debug it, because it needs three to have run first; you've lost the ability to isolate. Third, the result now depends on the order the tests run in, and test runners don't promise an order — so the suite passes on your machine and fails on the build server, or vice versa, and you've got a flaky, untrustworthy test suite. The whole point of a test is to give you a trustworthy signal. A test that depends on another test gives you a false signal. So: tests must be independent because a failure should point at exactly one cause, you must be able to run any test alone, and the result must never depend on execution order. That's the mark-earning answer to "why must tests be independent". And notice — this is the very same instinct as test independence's design cousin, low coupling, from your maintainability episode. Independent tests are loosely-coupled tests.

NARRATOR: So how do you keep tests independent in practice? Python's standard testing framework — the unit-test framework, "unittest", which ships with Python — gives you the tool: the set-up method. You write a method called set-up, spelled s-e-t-capital-u-p in the code, and the framework runs it automatically before every single test. Not once for the whole suite — before each test, individually. So inside set-up you build a fresh account object, and every test gets its own brand-new account that no other test has touched. Test three's deposit can't possibly affect test four, because test four got a clean account a millisecond ago. The set-up method is how the framework enforces the Independent and the Repeatable properties for you. That's a fact worth knowing cold for the exam: the purpose of the set-up method is to create fresh test fixtures before each test method runs, so tests start from a known, clean state and don't contaminate each other.

Don't worry about reading every line; I'll narrate the shape. The test class has a set-up method that creates a fresh account holding one hundred dollars before each test. Then there are about ten focused tests, and the key technique is the assertion. To check that two values are equal, you call assert-equal — you give it the value you got and the value you expected, and if they differ, the test fails. So one test deposits twenty-five dollars and then asserts that the balance equals one hundred and twenty-five. Clean, self-validating, done.

NARRATOR: But the tests that earn the most marks — and the ones students most often skip — are the error cases. What happens when you withdraw more than the balance? The method should raise an error. How do you test that an error gets raised? The framework gives you a second tool: assert-raises. You wrap the bad call and say "I assert this raises a value-error" — say it as "assert-raises" — and the test passes only if that exact exception is thrown, and fails if the code wrongly lets it through. So in Listing 1 you'll see tests for: a valid initial balance, a zero initial balance, a negative initial balance that must raise an error, a valid deposit, a zero and a negative deposit that must each raise an error, a valid withdrawal, withdrawing the entire balance down to zero, and — the star — withdrawing more than the balance, which must raise an insufficient-funds error. That last one is the test that proves your guard clause from two episodes ago actually fires. Roughly ten tests, each checking one behaviour, each independent thanks to set-up, each self-validating thanks to the assertions. That is a model unit-test suite, and Listing 1 is your template for any "write a unit test for this method" exam question.

QUESTION: That's a lot of tests for the error cases. Is testing the valid path not enough?

NARRATOR: No — and this is a marking pitfall the syllabus cares about. The valid, happy path is the easy half. The marks, and the real bugs, live at the edges: zero, negative, the boundary, the too-much, the empty input, the thing that should fail. Skipping edge and error cases is one of the named traps for this topic. A weak test suite checks that a deposit of twenty-five works and stops there. A strong test suite also checks that a deposit of zero is rejected, that a negative deposit raises an error, that an over-withdrawal raises insufficient-funds. The strong suite proves the code is safe; the weak one only proves it works on a good day. Hear the difference? "It deposits money correctly" is a band-four sentence. "It correctly rejects invalid inputs — zero, negative, and over-withdrawal — by raising the appropriate exceptions" is a band-six sentence. Test the behaviour at the edges, not just the middle.

NARRATOR: Now, one principle that runs underneath all of this, and it's the third mnemonic for today: "test behaviour, not implementation". You test what a method does — its observable result, the contract it promises — not how it does it internally. Concretely: test that withdrawing thirty from a hundred leaves seventy. Do not test that it happens to use a particular private variable, or calls some internal helper in a particular order. Why? Because behaviour is the promise; implementation is a detail you're allowed to change. If you refactor the inside of withdraw — say you Extract a Method, like last episode — the behaviour is identical, so a behaviour test still passes, which is exactly what you want: the test confirms your refactor was safe. But an implementation test, one that was checking the internal wiring, breaks the moment you touch the wiring, even though nothing the user sees has changed. So implementation tests are brittle; they fight refactoring, the very thing your clean-code episode was teaching. Test behaviour, not implementation. That's why a good test suite is the thing that lets you refactor fearlessly — it locks the behaviour while you improve the structure.

NARRATOR: Right — that's unit testing, the U in U-S-S, thoroughly. Now climb a deck. Subsystem testing.

NARRATOR: Subsystem testing — and its much more common name, the one you should actually write in the exam, is integration testing — checks that a group of related classes work correctly together. Unit testing proved each class works alone. Integration testing proves they work in collaboration — that the interfaces between them line up, that messages pass correctly, that data flows from one object to another the way the design intended. This is the level where the action of testing meets the message-passing from way back in episode one: object A sends a message to object B, B acts on its own data and returns — does that handshake actually work? And here's the direct callback I promised: this is exactly what stubs were buying you in episode six-point-three. A stub keeps the real signature, so the connection between two methods exists before the logic does, and you can integration-test the wiring early. Subsystem testing is integration testing grown up — now the real classes are in place, and you check they genuinely cooperate.

NARRATOR: The worked example is a small library. A book class and a library class. Individually, each has unit tests. But the interesting behaviour only appears when they work together: a complete borrow-then-return workflow. In Listing 2 there's an integration test that does the whole dance. It starts with a book that's available. It checks the book out to a borrower through the library. Then it asserts several things across both objects at once: the book object now reports it's unavailable and knows its borrower; and the library object's separate borrower-records now list that book against that person. Then it returns the book and asserts the reverse — book available again, borrower cleared, records updated. Notice what's being tested: not one method, but the consistency of two objects after a workflow. The library updated its records and the book updated its own state, and they have to agree. That agreement across an interface is the thing a unit test can't catch and an integration test exists to catch.

NARRATOR: And the second integration test in Listing 2 is multiple borrowers — Alice takes one book, Bob takes another, and you assert that each book went to the right person and neither got crossed. Plus an error-handling integration test: Alice checks a book out, then Bob tries to check out the same book and must be refused, and Bob tries to return a book that isn't his and must be refused. Those errors only exist at the boundary between the two classes — they're about how the objects interact, which is precisely the subsystem level. So integration testing is your answer whenever the question is about classes cooperating: does the data flow between them correctly, do the interfaces match, do they stay consistent.

QUESTION: This is where I'd lose marks — I can't always tell whether something is a unit test or an integration test. What's the clean line?

NARRATOR: Great question, because confusing the levels is the headline trap for this whole topic, and the line is genuinely simple once you have it. Count the classes under test. One class, in isolation — unit. Two or more classes that have to cooperate — subsystem, integration. The whole application running a real end-to-end scenario — system. So: testing that withdraw subtracts correctly, one class, that's a unit test. Testing that the library and the book stay consistent through a borrow-and-return, two classes cooperating, that's integration, the subsystem level. Testing a whole day of library operations from open to close, the entire system, that's system testing. One class, unit. A few classes together, subsystem. The whole thing end-to-end, system. U-S-S, smallest to largest. If you can say which it is and why in one sentence each, you've got the six-marker.

NARRATOR: Which brings us to the top deck — system testing. System testing evaluates the complete, integrated system as a whole, exercising full user workflows and business scenarios from end to end. Not "does this method work", not "do these two classes cooperate", but "does the whole thing do the job the user actually needs". The example in Listing 3 is a "daily operations" test for the library: a typical day, scripted. Morning — three students arrive and each borrows a book; assert all three books are now unavailable. Afternoon — two students return their books, and a new student borrows one of the just-returned books. End of day — assert the full final state: the two who returned have nothing out, the one who kept his book still has exactly one, the new student has the book she borrowed, and each book is with the right person. That single test walks the entire system through a realistic scenario and checks that everything ends up consistent. That's system testing — end-to-end, workflow-level, measured against what the business needs, not against one method's signature.

NARRATOR: So, the three levels one more time, because redundancy is doing real work at five-times speed. Unit — one class in isolation, does this method do its job. Subsystem, also called integration — a few classes together, do they cooperate correctly across their interfaces. System — the whole application end-to-end, does it deliver the user's workflow. U-S-S. Smallest cabin, several decks, whole ship. And they're a sequence in practice too: you unit-test as you build each class, you integration-test as you connect them, and you system-test the assembled product. Unit, Subsystem, System.

NARRATOR: Now the second half of the dot-point, and don't let it become an afterthought, because it's worth its own marks: quality assurance. Here's the distinction that earns the first mark every time. Testing is an activity — you run tests, you find defects. Quality assurance, QA, is broader: it's all the activities across the whole development process that build quality in and keep it high, so that fewer defects happen in the first place. Testing asks "is this build broken?" QA asks "is our whole way of working producing good software?" Testing is part of QA, but QA is the wrapper around it. If the exam asks "what is quality assurance", the answer is: a set of planned, systematic activities throughout development that ensure the software meets quality standards — not just testing at the end, but reviews, standards, checklists, and a continuous-testing mindset built into how the team works.

NARRATOR: Name two QA practices is a stock four-marker, so let me give you four solid ones, and a memory hook to hold them. Think "Review, Check, Accept, Continuously" — the four QA practices. Code review, checklists, acceptance criteria, and a continuous-testing mindset. Let me give you each.

NARRATOR: First, code review. This is the feedback practice from your collaboration episode, the pull-request review, seen now as a QA tool: another human reads your code before it merges, catches bugs, checks it meets conventions, and spreads knowledge through the team. A second pair of eyes finds things tests don't. Remember the rule — comment the code, not the coder.

NARRATOR: Second, checklists. A code-review checklist makes quality consistent instead of depending on whoever happened to review it that day. In Listing 4 I've written a QA review checklist you can lift straight into an answer. It has two parts. A design checklist: does each class have a single responsibility, is the data properly encapsulated behind a public interface, are the method names clear, are the methods an appropriate size, is there proper error handling, do the classes and public methods have docstrings, do the critical methods have unit tests. And a testing checklist: are the tests independent of each other, do the test names describe what they check, do they assert the right things, do they cover edge cases, do they cover error cases, do they use realistic controlled test data. Every line on that checklist is a concept from this module — single responsibility, encapsulation, clear naming, docstrings, independence, edge cases — which is exactly why a review checklist is such a good revision tool. The checklist is QA made systematic.

NARRATOR: Third, and this is the one that earns the senior-level mark: acceptance criteria. Acceptance criteria are the clear, agreed conditions that define when a feature is actually done and working — done from the user's point of view, not the programmer's. And they're written in a standard, examinable shape called Given, When, Then. Given some starting context — Given a student already exists in the system. When some action happens — When I try to add another student with the same identifier. Then some expected outcome — Then the operation is rejected with a clear error, and the original student's data is unchanged. Given, When, Then. It reads like a sentence, it pins down exactly what "done" means, and — this is the lovely part — it translates almost directly into a test. The Given becomes your set-up, the When becomes the action you call, the Then becomes your assertion.

NARRATOR: And acceptance criteria usually hang off a user story — the one-line statement of need in the form "As a role, I want a goal, so that a benefit". As a registrar, I want to add a new student, so that they can enrol in courses. In Listing 5 there's an acceptance test that captures exactly this. The user story and the Given-When-Then criteria live right in the test's docstring — so the documentation and the test are the same artefact — and the body of the test follows the three steps: Given the new student's details, When I add them, Then the system confirms success and I can retrieve the student's correct information afterwards. That's an acceptance test. When the question is "what are acceptance criteria", your answer is: the agreed, user-facing conditions for a feature to be considered complete, typically written as Given-When-Then against a user story, and used as acceptance tests. That phrasing is the mark.

NARRATOR: Fourth QA practice: a continuous-testing mindset. Testing isn't a phase you bolt on at the end; it's a habit threaded through development. Run your tests constantly, after every meaningful change, so a defect is caught the moment it's introduced, while the change is small and fresh in your head and cheap to fix — not three weeks later buried under a hundred other changes. The single most important benefit of continuous testing is exactly that: it catches problems early, when they're cheapest, and it gives you the confidence to keep changing the code, because the tests have your back. This is also why the Timely property of FIRST matters — tests written alongside the code make continuous testing possible.

NARRATOR: And there's one more idea worth a sentence, because it's the purest expression of the continuous-testing mindset and the syllabus brushes it: test-driven development, TDD. The taste of it is simple and a bit counter-intuitive — you write the test first, before the code it tests. You write a test for the calculator's add method that says add of two and three equals five — and at that moment there is no add method, so the test fails, deliberately. Then you write just enough code to make it pass. Red, then green. Writing the test first forces you to nail down the behaviour and the interface — the signature, the contract — before you write a line of implementation, which is the signatures-first discipline from episode six-point-three turned into a testing habit. You don't need to master TDD for this course, but know the one sentence: in test-driven development you write the test before the implementation, and let the failing test drive the code.

NARRATOR: So that's QA: Review, Check, Accept, Continuously — code review, checklists, acceptance criteria written Given-When-Then, and a continuous-testing mindset, with TDD as the test-first extreme of it. Quality assurance is the system; testing is one tool inside it.

NARRATOR: Now let me tell you why all of this is not bureaucratic box-ticking — why people have died from the absence of it. This is the Therac-25, and it's the story you should reach for whenever an exam asks why testing levels and QA actually matter. The Therac-25 was a radiation-therapy machine, built in the nineteen-eighties to treat cancer patients with beams of radiation. Its predecessors had hardware interlocks — physical safety mechanisms that made it electromechanically impossible to fire a lethal dose. On the Therac-25, the manufacturer removed those hardware interlocks and trusted the software to enforce safety instead. Now, here is the fatal combination. The software had a race condition — a concurrency bug, a timing flaw in how its hidden internal state changed when a fast operator typed and edited the treatment settings quickly. Under that exact timing, the machine could enter an invalid state and deliver a massive radiation overdose — a hundred times the intended dose — while the screen calmly reported a normal treatment. Between nineteen-eighty-five and nineteen-eighty-seven, several patients were given these overdoses. Several died. And the reused software had been carried over from older machines and trusted without the rigorous, independent testing the new no-hardware-interlock design demanded. The race condition was the kind of bug that thorough integration and timing tests are built to find; the missing interlocks were the kind of gap a serious QA review and proper acceptance criteria around safety would have flagged. The investigators' verdict, in essence: inadequate testing and inadequate quality assurance, on software that human lives depended on. That's the stakes. When the syllabus says "apply methodologies to test and evaluate code", the Therac-25 is why. Keep it brief in an answer, but keep it ready — it's the perfect "why does this matter" anchor. We'll tell the full story properly in its own case study; for now, that's enough to make the point.

NARRATOR: And a one-line callback, because it's the same lesson from a different angle: remember Ariane 5, from the building-classes episode. Reused inertial-reference code, carried into a new rocket and never re-tested for the new flight profile, hit an overflow and the rocket self-destructed thirty-seven seconds after launch — around three hundred and seventy million dollars gone. The moral that cashes in right here: reused code is never automatically safe — you must re-test it in its new context. Reuse without re-testing is exactly the gap that integration and system testing exist to close.

NARRATOR: Let me gather the traps for this topic in one place, because they're predictable. QUESTION: Question one, six marks. Distinguish between unit, subsystem and system testing. Pause the player and write your answer now.

NARRATOR: Model answer. Unit testing checks the smallest testable part of the program — a single method or class — in isolation, verifying one unit of behaviour with nothing else involved; for example, testing that a withdraw method correctly reduces a balance and raises an error on insufficient funds. QUESTION: Question five, four marks. A developer's tests pass when run together but fail when run in a different order. Explain why this is happening and how to fix it. Pause and answer — this one rewards real understanding.

[pause]

NARRATOR: Model answer. The tests are not independent — they share state. One test is leaving behind data, or relying on data that an earlier test created, so the result depends on the order the tests run in. When the order changes, a test that assumed a previous test's state no longer finds it, and fails. This violates the Independent and Repeatable properties of a good unit test. The fix is to make every test start from a clean, known state: use the framework's set-up method, which runs automatically before each test, to build a fresh fixture — a brand-new object — for every test individually, so no test can be contaminated by another and the run order stops mattering. The deeper point worth stating for the fourth mark: order-dependence makes a test suite untrustworthy, because it passes or fails for reasons unrelated to the actual code — and an untrustworthy suite gives a false signal, which defeats the entire purpose of testing.
