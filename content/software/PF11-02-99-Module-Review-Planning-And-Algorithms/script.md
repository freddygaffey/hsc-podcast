NARRATOR: Let's rebuild Chapter One first. It opened with the eight software development steps — the lifecycle. The hook?

QUESTION: The eight steps — what's the acronym, and what's the order-locking sentence?

NARRATOR: R-S-D-D-I-T-I-M: Requirements, Specifications, Design, Development, Integration, Testing, Installation, Maintenance. The sentence to lock the order: "Real Software Demands Discipline: Integrate, Test, Install, Maintain." And the headline mark, the thing markers reward and students miss: the lifecycle is iterative, not linear — feedback at any stage loops back. Say "iterative" and give one loop-back example, like maintenance throwing up a new requirement, and you've earned it. Notice, too, that requirements come before specifications — requirements are the user's need in plain language; specifications are the precise, testable contract. That distinguish pair is a classic.

NARRATOR: Then tools and collaboration. Git takes labelled snapshots, and the three places work lives are W-S-R: Write in the working tree, Stage in the staging area, Record in the repository. And the benefits of online collaboration tools are CRAB: Collaboration, Review, Accountability, Backup. Then documentation and code style — three levels by scope, R-D-C: Read-me for the project, Docstring for the function, Comment for the line; and the rule that's both the mark and the trap — a comment explains why, not what. Then project management models — the marquee mnemonic of the chapter: Waterfall falls once; Agile loops. Compare them on shared axes, R-F-D-C: Requirements, Feedback, Documentation, Change — and never crown a universal winner; the right model depends on requirement stability.

NARRATOR: Now Chapter Two, which is bigger — designing and analysing algorithms. Start with the raw materials: control structures. The hook is S-S-I: Sequence, Selection, Iteration. Sequence runs once in order; selection chooses a path, and in a multiple-selection chain the first true branch wins and the rest are skipped; iteration repeats — and the three loops split on when they check: for counts, while checks first, repeat checks last. The consequence to bank: while may run never, repeat runs once for sure. And the data a loop holds is A-E-F: Accumulator, Extreme, Flag. The trap: an infinite loop is a logic error — the body never moves toward its exit condition.

QUESTION: The three loop types — name each and its defining property.

NARRATOR: The for loop is counted — you know the number of iterations, and termination is guaranteed. The while loop is pre-test — it checks before the body, so it may run zero times. The repeat-until loop is post-test — it checks after the body, so it always runs at least once. While may run never; repeat runs once for sure. That zero-versus-at-least-once consequence is where the marks are.

NARRATOR: Then how you write algorithms down: pseudocode and flowcharts. Pseudocode is structured English in NESA's house style — write that, not Python, in a "write pseudocode" question. Flowcharts are the diagram, and the symbols are the examined fact: rounded terminator for start and stop, parallelogram for input and output, rectangle for a process, diamond for a decision, and a double-barred rectangle for a subprogram call. Diamond decides — it's the only symbol that branches, and every branch must lead somewhere. And the distinguish to remember: a flowchart shows what the program does, in order; a data flow diagram shows where the data goes.

NARRATOR: Then designing at scale — decomposition. Abstraction hides the how and shows the what. Top-down splits a problem down; bottom-up builds up from proven pieces. Stepwise refinement adds detail a layer at a time, and a structure chart diagrams the module hierarchy — who calls whom and what data passes — with the goal of high cohesion and low coupling. The do-everything module is the trap. And the two named strategies: divide and conquer — split, solve, combine, like merge sort — and backtracking — try, fail, undo, retry, like a maze.

QUESTION: Distinguish divide and conquer from backtracking — the classic pairing. Pause, answer, then play.

NARRATOR: Divide and conquer splits a problem into independent sub-problems of the same type, solves all of them, and combines their results — every piece is used. Backtracking builds a solution by trying choices one path at a time and undoes a choice when it leads to a dead end — failed work is discarded. Split-solve-combine versus try-fail-undo-retry. If the sub-problems are independent and you use them all, it's divide and conquer; if you're searching among choices with dead ends, it's backtracking.

NARRATOR: Then the module boxes themselves — subprograms. A function returns a value; a procedure performs an action. You identify which is which by whether a returned value gets used. Parameters carry data three ways: in reads, out writes back, in-out does both. And the trap that bites real coders — printing inside a function instead of returning, so the caller gets nothing.

NARRATOR: Then analysing written algorithms, which had its own method. I-O-P: determine Inputs, Outputs, and Purpose. Check with desk checking — you alone with a trace table — and peer checking — a second person's fresh eyes. Desk is solo, peer is social. And at scale, the full method: Read, I-O-P, Map, Trace, Check, ending with the connections — which come in two kinds, a call connection, who runs whom, and a data dependency, whose result feeds or gates whom. And finally the wide-angle lesson: the four paradigms, I-O-L-F — Imperative is how to do it, Object-oriented models the world, Logic is what is true, Functional transforms data. No paradigm wins universally, and a language is not a paradigm.

QUESTION: Big retrieval. Pause the player and write down what S-S-I, A-E-F, I-O-P, and I-O-L-F stand for, plus the one-liner "function returns, procedure performs." Go.

NARRATOR: S-S-I — Sequence, Selection, Iteration. A-E-F — Accumulator, Extreme, Flag. I-O-P — Inputs, Outputs, Purpose. I-O-L-F — Imperative, Object-oriented, Logic, Functional. And a function returns a value, a procedure performs an action. That's the spine of Chapter Two on one breath. QUESTION: Task two, design. Pause the player and attempt this before I give a model answer. Design an algorithm, in pseudocode, that takes a student's name and a list of their scores, and reports the name, the average, and the letter grade — and decompose it into appropriate subprograms. Use the grade scale: ninety and above is A, eighty B, seventy C, fifty D, below fifty F. Pause now, design it, then play.

NARRATOR: Here's a strong answer, and the marks are as much in the structure as the logic. Decompose it: a function to calculate the average, a function to determine the letter grade, and a procedure to display the report — each with one job, high cohesion. Calculate-the-average is a function: it takes the scores, sums them in a loop with an accumulator, and returns the total divided by the count. Determine-the-grade is a function: it takes the average and returns a letter using a multiple-selection chain — ninety or above returns A, else eighty or above B, else seventy or above C, else fifty or above D, else F. Display-the-report is a procedure: it takes the name, average, and grade and outputs them, returning nothing. The main algorithm reads the name and scores, calls calculate-the-average, passes that result into determine-the-grade — a data dependency, the grade depends on the average — and then calls display-the-report. The full pseudocode is in Listing 4, and Listing 5 is the same thing as runnable code with the values checked. What lifts this to full marks: naming the subprograms as functions or procedures correctly, the single-responsibility decomposition, and noticing the average-feeds-grade data dependency. That one task touches S-S-I, A-E-F, procedures-versus-functions, I-O-P, and connections — the whole chapter in one problem.

NARRATOR: Now the traps, gathered in one place, because the module review is where you inoculate against the predictable mistakes. From Chapter One: calling the lifecycle linear instead of iterative; crowning a universal winner in Waterfall-versus-Agile; a comment that restates what the code does instead of why; the giant unfocused Git commit. From Chapter Two: confusing sequence with selection; the infinite loop from a never-changing exit condition; missing a boundary value when you trace; a dangling, unhandled branch in a flowchart or selection; the do-everything module with low cohesion; printing inside a function instead of returning; missing a data dependency when you analyse connections; and the two paradigm traps — crowning a best paradigm, and confusing a language with a paradigm. NARRATOR: Let's close in full exam mode — a short set of integrated questions, the kind that span several lessons at once, the way real HSC questions do. Pen down, pause where I say, then hear the model answer.

QUESTION: Question one, integrated. A team is building software with stable, well-understood requirements, and they want to design the core algorithm carefully before coding. Name a suitable project management model and justify it, then name the two modelling tools they'd use to design the algorithm's structure.

NARRATOR: A suitable model is Waterfall, justified because the requirements are stable and well-understood, which is exactly the condition Waterfall suits — its sequential, document-heavy, plan-up-front approach is low-risk when requirements won't change. Waterfall falls once. For designing the algorithm's structure, the two modelling tools are the structure chart — showing the module hierarchy and data flow — and stepwise refinement, or equally a flowchart and pseudocode for the detailed logic. Full marks: name Waterfall, tie the justification to requirement stability, and name two genuine modelling tools from the chapter.

QUESTION: Question two. Distinguish a procedure from a function, and give one example of each from a grade-reporting program. Pause, answer, then play.

NARRATOR: A function calculates and returns a value, used for its result; a procedure performs an action and returns nothing, used for its effect. In a grade-reporting program, calculate-the-average is a function — it returns a number; display-the-report is a procedure — it performs the action of showing output and returns nothing. The distinguishing point is the return value: function returns, procedure performs.

QUESTION: Question three, a trace. For the results-summary algorithm in Listing 2, trace the scores ninety, forty, ninety and state the average, the highest, and the pass count.

NARRATOR: Total starts zero, highest starts at the first score ninety, pass count zero. Ninety: total ninety; ninety greater than ninety? No; ninety fifty-or-above? Yes, pass count one. Forty: total one hundred and thirty; forty greater than ninety? No; forty fifty-or-above? No. Ninety: total two hundred and twenty; ninety greater than ninety? No — note, not greater, equal, so highest stays ninety; ninety fifty-or-above? Yes, pass count two. Average is two hundred and twenty divided by three, which is about seventy-three point three; highest is ninety; pass count is two. The subtle mark there is the equal case — the second ninety is not greater than the stored ninety, so highest doesn't change, but it still counts as a pass. Strictly-greater versus or-equal — the boundary thinking again.

QUESTION: Question four, integrated and harder. Explain how the concepts of cohesion and the difference between a procedure and a function together lead to a well-structured algorithm, and name one analysis technique you'd use to verify it works.

NARRATOR: High cohesion means each subprogram has a single, focused responsibility; correctly choosing a function where you need a returned value and a procedure where you need an action means each subprogram's role is clear and its interface is clean. Together they produce an algorithm decomposed into focused, single-purpose subprograms with low coupling between them — easy to read, test, reuse, and maintain. To verify it works, you'd use desk checking — tracing representative scenarios, including boundary cases, through a trace table — and ideally peer checking as well. Full marks: link cohesion to single-responsibility, link the procedure-function choice to clear interfaces, and name a real analysis technique with what it does.

QUESTION: Question five. Name the four programming paradigms and, for a system that models many interacting real-world entities, state which is most suitable and why.

NARRATOR: The four are imperative, object-oriented, logic, and functional — I-O-L-F. For a system modelling many interacting real-world entities, the object-oriented paradigm is most suitable, because it models each entity as an object that bundles its own data and behaviour and lets objects interact by sending messages — which keeps a large system of interacting entities organised, modular, and reusable. The mark is naming all four, choosing object-oriented, and justifying with the "interacting entities with their own state and behaviour" reasoning, not "because it's modern."
