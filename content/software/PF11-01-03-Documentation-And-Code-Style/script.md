NARRATOR: Start with the big picture, the structure that organises everything else. There are three levels of documentation, and they differ by scope, by how much of the program each one talks about. The widest is the read-me file, which documents the whole project. The middle level is the docstring, which documents a single function. And the narrowest is the inline comment, which documents a single line or a small block. Project, function, line. Remember it as R-D-C: Read-me, Docstring, Comment, going from the widest scope down to the narrowest. When an exam asks you to describe how a program should be documented, walking those three levels, project then function then line, is a structured, high-band answer instead of a vague "you add some comments".

NARRATOR: Level one, the read-me file. This is the front door to your project. It's a plain-text file, usually written in Markdown, that sits at the top of the repository, and it answers the questions a stranger, or you in six months, would ask on arrival. Think of it as greeting a newcomer who asks four things, in order. First: what is this? One sentence on the project's purpose. Second: what do I need? The requirements, the Python version, any dependencies. Third: how do I run it? The exact command. And fourth: how do I use it? A basic example showing typical input and the output you'd expect. What, need, run, use, in the natural order you'd actually approach a new tool. I've written a complete read-me for our Grade Calculator project in Listing one if you want the shape of it. The mark-earning point: a good read-me lets someone go from zero to running your software without asking you a single question.

NARRATOR: Level two, the docstring. This is documentation attached to a function, and in Python it's a string sitting right at the top of the function body, in triple quotes. The docstring answers three things about the function: what it does, what parameters it takes, and what it returns. The reason this level matters so much is that a function is an interface, a contract. Someone calling your function shouldn't have to read its internals to use it correctly; the docstring is the contract that tells them how. For our Grade Calculator, the calculate-average function gets a docstring saying it takes the grades and returns the mean rounded to one decimal place. The get-letter-grade function gets one explaining it converts a numeric average to a letter using the standard scale. You can see these in Listing two. The phrase markers like here is "self-documenting interface": the docstring documents the function's contract without the caller needing to see the implementation.

NARRATOR: Level three, the inline comment. This is a note on a single line or a small block, and it is the most misused tool in all of programming, which makes it a goldmine for exam questions. Here is the one rule, and I want you to hold onto it because it's both the mark and the trap: a comment should explain why, not what. The code already says what it does, that's what code is. A comment that repeats the code in English is pure noise. The valuable comment explains the reasoning that the code can't show: why this approach, why this edge case is handled this way, what business rule forces this number.

QUESTION: Can you make that concrete? What does a useless comment actually look like next to a good one?

NARRATOR: Gladly, because this contrast is exactly what gets examined. A useless comment, on a line that adds a grade to a running total, says "add the grade to the total". You can see that. The code is literally "total plus-equals grade". The comment has added nothing; it's just visual clutter you now have to keep in sync. Now a good comment, on a line that picks a grade boundary, says "grade boundaries follow the university standard, ninety and above is an A". That comment explains a why, the business rule behind the number, that you could never recover from the code alone. The code shows that ninety maps to A; only the comment tells you that's a deliberate institutional standard and not an arbitrary choice. I've put a good-versus-bad comment pair in Listing three. The line to carry into the exam: comments explain why; the code shows what.

NARRATOR: And here's the deeper move that lifts a top answer: the best way to reduce the need for comments is to write code that documents itself, and the main tool for that is good naming. If your variable is called "student count" instead of "ess-cee", and your function is called "calculate weighted average" instead of "calc", then the code reads like prose and most of your would-be comments simply vanish, because the what is already obvious. So readability and documentation aren't two separate chores; clean naming is what lets you write fewer, better comments. That's the insight markers reward: self-documenting code needs less commentary, so comments can be reserved for the genuine whys.

NARRATOR: Which brings us to naming conventions, the part of code style the syllabus most directly expects you to know, because Python has standard rules and they have a name. The style guide is called PEP 8, said "pep eight", and it's the agreed convention for how Python code should look. You don't memorise all of it, but a few naming rules are fair game. Variables and functions use what's called snake case: all lowercase words joined by underscores, like "student count" written as one lowercase token with an underscore between the words. Constants, values that never change, use all capitals, like a maximum-grade value written in full uppercase. And classes, which you'll meet properly in the next module, use what's called Pascal case, each word capitalised and jammed together. The hook: snake for your names, all-caps for your constants. Lowercase snake for the everyday variables and functions; SHOUTING capitals for the fixed constants.

QUESTION: Does the convention actually matter for marks, or is it just taste?

NARRATOR: It matters, and here's why it isn't taste. Consistency is the real principle underneath PEP 8. The point of a shared convention isn't that lowercase-with-underscores is objectively superior; it's that when everyone on a project follows the same rules, the code reads as one coherent voice, and a reader can predict what they'll see. A codebase where one file uses one style and the next uses another forces the reader to context-switch constantly, and that costs time and breeds bugs. So in an exam, if you're asked why naming conventions matter, don't say "because PEP 8 says so". Say: conventions make code consistent and predictable, which makes it readable, which makes it maintainable. That's the chain the marker wants: convention, to consistency, to readability, to maintainability.

NARRATOR: Let me pull it together with the worked example, the thing we keep returning to, the Grade Calculator. Picture two versions of the same function. Version one is the kind of thing you write at two in the morning: a function called "calc" taking three parameters named x, y, and z, with a variable "a" for the sum and "r" for the result and "g" for the grade, no docstring, no comments. It works. It produces the right answer. And it is almost unreadable, because every name hides its meaning and there's no documentation at all. Version two is the same logic, but the function is called "calculate grade average", the parameters are named for the three test scores, the sum is called "total points", the result is called "average", there's a docstring stating what it does, and a single comment explaining the grade scale is the standard one. Same behaviour. Completely different maintainability. I've put both side by side in Listing four. If an exam hands you the first version and says "improve the readability of this code", your answer is: rename the cryptic identifiers to descriptive ones, add a docstring describing the function's purpose, parameters and return, and add a comment only where a why needs explaining, like the grade boundary. Name those three moves explicitly and you've got the marks.

NARRATOR: Now the weak-versus-strong contrast on the headline question, so you can hear the boundary. The question: "Identify two features of well-documented code." Two marks, and it looks easy, which is exactly why people throw away the marks.

NARRATOR: A weak answer says: "It has comments and it's easy to read." That's circular, easy to read is the thing being asked about, not a feature, and "has comments" is shallow. Maybe one mark. A strong answer says: "Well-documented code includes docstrings that describe each function's purpose, parameters and return value, and uses descriptive, convention-following names so the code is self-explanatory, with comments reserved for explaining why non-obvious decisions were made." That names concrete, assessable features, docstrings, descriptive naming, why-comments, each tied to its purpose. Same topic, but one of these is a band-six sentence and the other is a shrug.

NARRATOR: Let me flag the trap by name, because it's the most common one on this dot-point and it's the inverse of a good habit. The trap is the comment that restates what the code does instead of why. Students, told that comments are good, sprinkle a comment on every line, "increment the counter", "loop through the list", "return the result", and think they've documented their code. They've done the opposite: they've added noise that clutters the code and rots out of sync the moment the code changes. In an exam, if you're asked to critique commented code and you see comments that merely echo the code, that's your answer: these comments add no information because they restate what the code already expresses; good comments should explain why, not what. Naming that distinction is the mark.

QUESTION: Question one. "Identify two features of well-documented code." Two marks. Pause, answer, then play.

NARRATOR: Model answer: first, docstrings that describe each function's purpose, parameters and return value. Second, descriptive, convention-following names that make the code self-explanatory, supported by comments that explain why non-obvious decisions were made rather than restating what the code does. Two concrete, named features, each tied to its purpose. Avoid the circular "it's easy to read".

QUESTION: Question two. "Explain the difference between a good comment and a poor comment, using an example of each." Four marks. Pause, answer, then play.

NARRATOR: Model answer: a poor comment restates what the code already expresses and therefore adds no information, for example a comment reading "add the grade to the total" placed on a line that adds the grade to the total. A good comment explains why something is done, the reasoning, edge case, or business rule that the code itself cannot convey, for example a comment reading "grade boundaries follow the university standard, ninety and above is an A" on the line that sets the boundary. The distinction is that good comments explain why, not what; the code already shows what. Full marks need both the rule and a contrasting example of each.

QUESTION: Question three. "Outline why following naming conventions such as PEP 8 improves software quality." Four marks. Pause, answer, then play.

NARRATOR: Model answer: naming conventions make code consistent and predictable across a whole codebase, so any reader can anticipate the form of names and read the code as one coherent voice rather than constantly context-switching between styles. This consistency improves readability, and because code is read far more often than it is written, more readable code is easier and cheaper to maintain and less prone to bugs. Descriptive, convention-following names also make code self-documenting, reducing the need for comments. The mark-earning chain is convention, to consistency, to readability, to maintainability, do not stop at "because it's the standard".

QUESTION: Question four. The applied one. "A teacher gives you a function named 'calc' that takes parameters x, y and z, with no docstring and no comments. Recommend three specific improvements to its readability and documentation, and justify each." Six marks. Pause, plan a full answer, then play.

NARRATOR: Model answer: first, rename the function and its parameters descriptively, for example "calculate grade average" with parameters named for the three test scores, because descriptive names make the code self-documenting and reveal intent that cryptic single letters hide. Second, add a docstring stating the function's purpose, its parameters and its return value, because this documents the function's contract so a caller can use it correctly without reading its internals. Third, add an inline comment only where a non-obvious decision is made, such as the grade-boundary scale, because a comment that explains why earns its place, whereas comments restating the code would add only clutter. A top answer notes that these changes improve maintainability, the property that matters most given code is read far more than it is written, and ties back to the readability and documentation aspects the solution will ultimately be evaluated against. Each recommendation must be paired with its justification to score full marks.
