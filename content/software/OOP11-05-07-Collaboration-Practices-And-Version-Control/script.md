NARRATOR: Start with the big idea, the one the six-mark question is really asking: why does OOP support collaborative development? The answer is one word with two halves — boundaries and contracts. Object-oriented design naturally chops a system into distinct classes, each with a single clear responsibility. Those class boundaries are also team boundaries. If the user-manager class, the content-manager class, and the blog-application class are three separate, well-defined units, then three developers can each take one and work in parallel without standing on each other's keyboards. Procedural code, by contrast, tends toward one big shared pile of functions and global data — and when everyone's editing the same pile, everyone's blocking everyone.

NARRATOR: But boundaries alone aren't enough. The magic ingredient is the well-defined interface — the contract. When the user-manager class publishes a method, say "authenticate user, give it a username and a password, get back true or false" — that signature is a promise. The developer building the content-manager class doesn't need to know how authentication works inside. They don't need it finished. They just need the promise: this is what I call, this is what I pass, this is what I get back. As long as both sides honour the contract, they can build their halves completely independently and the pieces will click together at the end.

NARRATOR: This is exactly the facade idea from last lesson, scaled up. A facade gives a client a stable front and hides the internals. Here, every class's public interface is a little facade to the rest of the team. Stable front, hidden internals — that's not just a design nicety, it's the thing that lets people work apart. So here's your first mnemonic for today, and I want it word-perfect because it's the spine of the six-marker: "Clear interfaces let teams work apart, then merge." NARRATOR: There are two more OOP features that feed this. One is small, cohesive classes. We hammered cohesion in the design-process lesson — one class, one job. The smaller and more focused each class is, the easier it is for one person to own it, understand it, test it, and change it without ripping through the rest of the system. A giant unfocused class is the opposite: it touches everything, so everyone has to touch it, so it becomes the bottleneck that nobody can edit safely. That's actually a named trap, so flag it now — one big god-class blocks parallel work. The fix is the same cohesion you already know.

NARRATOR: The second feature is the one that genuinely surprises people, so let me set it up properly. Because a class's interface is a contract that's separate from its implementation, you can write code against an interface before the implementation exists. That's where stubs and mocks come in. A stub is a placeholder implementation — it returns a canned value or just prints "to do" — so the program runs end to end before the real logic is written. A mock is a fake stand-in for a real object, built to satisfy the same interface, used so you can develop and test the code that depends on it without the real thing.

QUESTION: Hang on — why would you build a fake version of a class instead of just waiting for the real one? Pause the player, have a real go at answering this in exam terms, then play.

NARRATOR: Good — this is one of the named exam seeds, so let's earn the marks. Picture three developers on a blog app. Developer C is building the checkout flow, which depends on a payment-processor class — but the real payment processor talks to a live bank, needs API keys, costs money per call, and developer B hasn't finished it yet. If developer C had to wait, they'd be blocked for days. Instead, the team agrees the interface first — "process payment, give it an amount and a method, get back a success-or-failure result." Developer C then writes a mock payment-processor that honours that exact interface but just returns "success" without touching a real bank — that interface and its mock are written out in Listing One if you want to read them after. Now developer C builds and tests the entire checkout flow today, against the mock. When developer B's real payment processor lands, it slots into the same interface and the mock is swapped out — no changes to developer C's code. So the model answer is: a mock object lets a team build and test against an interface before the real implementation exists, removing a blocking dependency, and because both share the interface the real one drops in unchanged. That last clause — "drops in unchanged" — is pure polymorphism, the P in A-PIE: one interface, many implementations, and the calling code can't tell which it's holding.

The mock-and-interface trick is the same "design to an interface" discipline you'll lean on hard in the Year 12 major project, and it's exactly how machine-learning code gets built in the software-automation module — a general model interface with a "fit" method and a "predict" method, and many model classes plugged in behind it. NARRATOR: Let me make the contract idea unforgettable with a real story — and I'll keep it short, because there's a whole case-study episode on it later. In nineteen ninety-nine, NASA lost the Mars Climate Orbiter. A hundred-and-twenty-five-million-dollar spacecraft, gone, because two teams' software exchanged values across an interface — and one team worked in metric units, newton-seconds, while the other expected imperial units, pound-force-seconds. Each piece of software was correct on its own. The interface between them was never nailed down as a contract that said "these are the units." The numbers flowed across, silently wrong, and the craft burned up in the Martian atmosphere. That is the entire lesson of today in one disaster: an interface is a contract, and an unstated contract is a time bomb. When you write "an interface is a contract" in the exam, you can name the Mars Climate Orbiter as your evidence. We'll tell the full story another time.

NARRATOR: So that's the why. OOP supports collaboration through clear module boundaries, well-defined interfaces acting as contracts, small cohesive classes, and the ability to build against interfaces with stubs and mocks. Now the four named practices that turn that potential into a working team. Consistency, code commenting, version control, feedback. And here's a memory hook for the four in order — I want them in the order NESA lists them: think "Code, Comment, Control, Critique." Consistency in how you code, comment what you wrote, control the versions, critique each other's work. Code, Comment, Control, Critique — four C's, in NESA's order.

NARRATOR: First named practice: consistency. This is about naming and style conventions — everyone on the team writing code that looks like it came from one hand. Consistent naming for classes, methods, and variables; a consistent style — indentation, spacing, how you structure a class; agreed conventions like Python's official style guide, the one called PEP 8, say "pep eight." Why does this matter for collaboration specifically? Because when every developer follows the same conventions, you can read a teammate's class as fluently as your own. You're not wasting energy decoding their personal style; the cognitive load drops; code review gets faster; and — this connects straight back to the consistency in I-C-F-S from the encapsulation lesson — the codebase behaves like a single coherent system, not five people's hobby projects stapled together. The exam phrasing: consistency reduces the effort of understanding and modifying each other's code.

NARRATOR: Second: code commenting. The listener's a strong programmer, so I'm not going to tell you what a comment is. I'm going to tell you the one principle that earns marks and the one that loses them. The golden rule is: comment the why, not the what. A comment that says "increment the counter by one" next to a line that increments a counter by one is worthless — the code already says that, and worse, it goes stale when the code changes. A comment that says "we retry three times because the payment gateway intermittently drops the first request" — that's gold, because the code can never tell you that on its own. Why-not-what. In OOP specifically, the high-value comment is the docstring — the block of documentation attached to a class or a method that states its contract: what it does, what arguments it takes, what it returns, and what exceptions it raises. That docstring is the human-readable version of the interface contract we just spent ten minutes on. It's how a teammate uses your class without reading its insides. So commenting isn't decoration here — it's how the contract gets communicated.

QUESTION: Quick one, no pausing needed — what's the difference between a comment and a docstring, in OOP terms?

NARRATOR: A comment is any note in the source for whoever's reading the code. A docstring is a specific, structured piece of documentation bound to a class or method, describing its public contract — and tools can pull it out automatically to generate documentation. So every docstring is documentation, but the point for the exam is: the docstring documents the interface, which is exactly what a collaborator needs. And notice — this is SE-11-09 territory, managing and documenting the project. Commenting is documentation; documentation is collaboration.

NARRATOR: Third, and this is the big one: version control. A version-control system tracks changes to your code over time and coordinates the work of multiple people. Git — say "git" — is the one you'll use and the one the syllabus assumes. Let me give you the vocabulary and the workflow in words, because the actual commands live in the supplementary listings and I never want you depending on seeing a screen. NARRATOR: Here's the mental model. A repository is the project and its entire history. A commit is a saved snapshot of your changes with a message describing them — think of it as a save point you can always return to. You make a commit by staging the files you've changed and then committing them with a message. A branch is an independent line of development — a parallel copy of the project where you can work on your feature without disturbing the main line that everyone shares, usually called "main." The headline workflow is the feature-branch workflow: you create a branch for your feature, do your work and commit as you go, and when it's done you merge your branch back into main. Merging is the act of combining two branches' changes together.

NARRATOR: Now the two practices the four-mark question wants. First, commit hygiene. A good commit is one logical change with a clear, descriptive message. The mnemonic — say it with me — "one idea per commit." One idea per commit. If you've added a feature, fixed an unrelated bug, and reformatted a file, that's three commits, not one. Why? Because the history is documentation — that's SE-11-09 again — and a history of small, single-purpose commits is one you can read, search, and undo surgically. If a bug appears, you can find the one commit that caused it and reverse just that, instead of unpicking a giant tangle. The named trap here is the opposite: committing many unrelated changes at once. That's a real marking pitfall, so name it — a fat commit that mixes a feature, a fix, and a reformat is unreadable history and impossible to undo cleanly.

NARRATOR: The second version-control practice is branching for parallel work — and this closes the loop back to the start of the episode. Clear interfaces let teams work apart, then merge. Branches are the "work apart, then merge" made literal. Developer A branches off and builds the user-manager class. Developer B branches off and builds the content-manager class. They never touch each other's branch, so they never block each other. Then each merges back into main, and the pieces — which honoured their interfaces — come together. The OOP boundaries and the version-control branches are the same idea expressed twice: once in the architecture, once in the tooling.

NARRATOR: Which brings us to the thing that goes wrong: merge conflicts. This is a named exam question — "what is a merge conflict and how is it resolved?" — so let's nail the definition. A merge conflict happens when two branches have changed the same lines of the same file in different ways, and the version-control system cannot decide which version is correct, so it stops and asks a human. It's not an error or a bug — it's the tool being careful. When developer A and developer B both edited the constructor of the user-manager class on their separate branches, and you try to merge, Git marks the file with conflict markers — it puts your version and their version side by side, fenced off with markers, and leaves it for you to sort out. There's an annotated example in Listing Three.

NARRATOR: How do you resolve it? Four steps, and there's a tidy hook: Talk, Edit, Strip, Commit. First, talk — discuss with your teammate which approach is right, or how to combine both; the conflict is often a design disagreement, not just a text clash. Second, edit — manually rewrite the conflicted section into the correct combined version. Third, strip — remove the conflict markers the tool inserted. Fourth, commit the resolved file, ideally after re-running the tests to confirm nothing broke. Talk, Edit, Strip, Commit. The model answer to "how is it resolved" is: a human manually edits the file to combine the changes correctly, removes the conflict markers, tests, and commits the resolution. The trap students fall into is treating a conflict as a catastrophe — deleting the file or starting over. Don't. It's a routine, expected part of merging.

NARRATOR: Now I want to make good on the SE-11-09 framing, because it's a clean way to lift an answer. Version control wears two hats. As a collaboration tool — SE-11-06 — it lets a team work in parallel on branches and merge safely. As a project-management-and-documentation tool — SE-11-09 — the commit history is a living, searchable record of every decision: who changed what, when, and why. The same system that coordinates the team also documents the project. If an exam question is framed around managing and documenting a project, version control is your answer just as much as when it's framed around teamwork. Say both hats and you've shown range.

NARRATOR: Fourth named practice: feedback — and in practice that means code review. Before a developer's branch merges into main, a teammate reads the change and gives feedback, usually through a pull request. A pull request — also called a merge request — is a proposal: "here's my branch, here's what I changed and why, please review it before it goes in." A good pull request describes the change, lists what was added or modified, and says how it was tested. There's a sample in Listing Four. The review then catches bugs, checks that conventions were followed — there's your consistency loop closing — and spreads knowledge so no single person is the only one who understands a piece of the system.

NARRATOR: There's a famous worked contrast here, and it's worth the marks. A weak review comment says "this is wrong, fix it." A strong one says "consider pulling this maximum length out into a named constant on line forty-five, so it's easier to change later and the code reads for itself." Hear the difference? The weak one is vague and a bit hostile; the strong one is specific, explains the reasoning, and is about the code. That's the review mnemonic, and it's the one I most want you to keep: "comment the code, not the coder." Comment the code, not the coder. Reviewers focus on code quality, potential bugs, edge cases, and whether project conventions are followed — never on personal style preferences and never on the person. The named trap is the unhelpful review comment: vague, harsh, or about the author rather than the work. "Comment the code, not the coder" is the fix and the phrasing in one line.
