NARRATOR: Welcome back. Five minutes looking backwards first — spaced repetition is the engine of this series, so the important ideas keep returning until they're permanent. Newest first.

NARRATOR: Last episode was standard data types. The organising hook was four families: Words, Numbers, Truth, and Time — that is, char and string; integer and real; boolean; and date-time. The key distinctions: a char is one character, a string is many; an integer is exact, stored as two's complement; a real is fractional, stored as floating point, and a float is approximate, not exact. And the big skill was choosing the right type for a field and justifying it, plus the two traps — a number stored as a string concatenates instead of adding, and a float used for money drifts, so store money as whole cents. Hold the "choose a type for each field" idea especially close, because today we take all those choices and write them down formally.

NARRATOR: And before that, number systems and two's complement; before that, the Chapter One and Two review. The thread is tight now: we chose a type for each piece of data last episode — but a type alone isn't enough. "Age is an integer" doesn't stop someone entering an age of minus five or two hundred. Today we add the rules. The dot-point: "Create data dictionaries as a tool to describe data and data types, structure data, and record relationships." The outcomes are S-E-eleven-oh-four — safe and secure data practices — and S-E-eleven-oh-six — applying tools to design and manage software. A data dictionary is one of those tools.

QUESTION: A "data dictionary" — is that just a list of variables?

NARRATOR: More than that, and the difference is the marks. A data dictionary is a formal document that describes the structure, format, and constraints of every piece of data in a system. Think of it as a blueprint: just as a building blueprint specifies the exact dimensions of every wall and door before anyone builds, a data dictionary specifies the exact type and rules of every data field before anyone codes. It exists for four reasons, and they're worth naming in an "explain the purpose" answer: consistency, so the whole team uses the same formats; validation, so invalid data is caught; documentation, so current and future developers have a reference; and quality control, so bugs are designed out upfront. It's the documentation idea from the code-style episode — remember R-D-C — applied specifically to data.

NARRATOR: Objectives up front. By the end you'll be able to: state what a data dictionary is and why it's used; list what every entry contains; name the four kinds of constraint and the three kinds of relationship; construct a data dictionary for a described entity — which is the exam question; and turn its constraints into validation code. Let me give you the structure. Every entry in a data dictionary describes one field with a few columns, and the hook is F-T-C-R: Field name, Type, Constraints, Relationship. Plus, in a good dictionary, a description and an example. Field name, Type, Constraints, Relationship — F-T-C-R.

NARRATOR: Field name and type you already have — the field is the piece of information, like name or age, and the type is from last episode, string or integer or float and so on. The new content today is the other two: constraints and relationships. Let's take constraints first, because they're where the real marks are, and the number-one trap is leaving them out.

NARRATOR: A constraint is a rule that limits what values a field will accept. There are four kinds, and the cleanest way to remember them is as four questions you ask of every field. How long can it be? — that's a length constraint, a maximum or minimum number of characters, like a name being two to fifty characters. How big can it be? — that's a range constraint, a minimum and maximum value, like an age from sixteen to twenty-five, or a grade average from zero to one hundred. What shape must it take? — that's a format constraint, a specific pattern, like a product code being the letters P-R-D followed by exactly five digits, or an ISBN being exactly thirteen digits. And must it be there at all? — that's a required constraint, whether the field can be left empty. How long, how big, what shape, must it be there: length, range, format, required. If you want the acronym, it's L-R-F-R, but the four questions are easier to actually use.

QUESTION: Here's one to actually attempt. Pause the player. For a field storing a person's age in a school system, write a complete data-dictionary entry — type, and at least two kinds of constraint. Work it out, then play.

NARRATOR: Age: type integer; constraints — required, and a range of, say, four to nineteen for a school, measured in years. You could add that it's a whole number with no decimal. The mark is naming the type and giving real constraints with actual values — required plus a numeric range. A weak answer just writes "age: integer" and stops, which is exactly the trap: omitting the min and max. The constraint without numbers is no constraint. And notice — those range limits, the four and the nineteen, are precisely the boundary values you'd test later. The range constraint you write here is the boundary test you run in the testing episode. Same numbers, two jobs.

NARRATOR: That's a genuinely important link, so let me make it explicit. A few episodes from now we design test data, and the headline mnemonic there is B-P-F — Boundary, Path coverage, Faulty. The boundary values come straight from the range constraints in your data dictionary: if age must be sixteen to twenty-five, you test fifteen, sixteen, twenty-five, and twenty-six — the values either side of each limit. The data dictionary isn't just documentation; it's the source of your test cases. And it's also the source of your validation code — which we'll get to.

NARRATOR: Now the second new piece: relationships — how one kind of record connects to another. There are three, and they're called cardinalities. One-to-one: each record on one side links to exactly one on the other — each student has exactly one student identifier. One-to-many: one record on one side links to many on the other — one teacher has many students. And many-to-many: records on both sides link to many — students enrol in many subjects, and each subject has many students. One-to-one, one-to-many, many-to-many. Recording these relationships is the second thing students forget, and it's the other half of "structure data and record relationships" in the dot-point. If you only describe fields and never say how the records connect, you've done half the job.

NARRATOR: Let's build a full one. A student record data dictionary — the worked example is laid out as a table in Listing 1. Each row is a field with its columns. Name: type string; constraints required, two to fifty characters; description, the student's full name; example, "Sarah Johnson". Age: type integer; required, range sixteen to twenty-five years; example seventeen. Grade average: type float; required, range zero to one hundred, one decimal place, as a percentage; example eighty-seven point five. Enrolment status: type boolean; required; example true. Student identifier: type string; required; format the letter S plus five digits; and a relationship — one-to-one with the student. That table, field by field with type, constraints, and relationship, is the answer to "construct a data dictionary." When the exam asks for one, you draw that table.

NARRATOR: And here's where it pays off as engineering, not just paperwork: the data dictionary drives your validation code directly. Each constraint becomes a check. Listing 2 is a validate-student-data function that enforces exactly the dictionary: it checks the name is a string of two to fifty characters, the age is an integer in range sixteen to twenty-five, the grade average is a number from zero to one hundred, and the enrolment status is a boolean — returning false with a clear message on the first rule broken, or true if all pass. Listing 3 is the same validation written in NESA pseudocode, the form you'd write for marks. The dictionary on paper, the validator in code — one is the specification, the other is the enforcement.

NARRATOR: Two more constraint kinds in action, because they come up. Format constraints often need a pattern matcher — a regular expression. Listing 4 validates a product code against the pattern "the letters P-R-D followed by exactly five digits," accepting "P-R-D-zero-zero-one-two-three" and rejecting anything else. And conditional constraints, where one field's rule depends on another — this is where constraints meet relationships. Listing 5 enforces a rule that an in-stock item must have a quantity above zero; and a classic library version is that a book may have a borrower identifier only if it is not available for loan. A book on loan has a borrower; an available book has none. That's a relationship expressed as a constraint.

QUESTION: How is a data dictionary different from a database schema? They sound the same.

NARRATOR: Good distinguish question, and it appears. A data dictionary is human-readable documentation, written during design — it includes business rules, descriptions, examples, and the reasoning, for people to read and agree on. A database schema is the machine-readable structure that actually creates the database — column names and types the database engine enforces. The dictionary guides the creation of the schema, but it's richer: it carries the context and the why, not just the what. The one-liner: the data dictionary is for humans at design time; the schema is for the machine at build time. You'll meet schemas properly when we reach databases in the web module — same field-and-type idea, enforced by the database engine.

NARRATOR: Let me weave the threads. Backward: a data dictionary records the data types from last episode, now with rules attached — it's the natural home for "age is an integer" plus "and it must be sixteen to twenty-five." It's also documentation, the R-D-C idea, aimed at data. Forward, three real links: the range constraints are your boundary test values in the test-data episode, B-P-F; the validation logic here becomes enforced invariants in the object-oriented module — when you learn encapsulation, a validating setter that refuses an invalid value is exactly this check, moved inside an object and made unbreakable; and a database schema is a machine-enforced data dictionary, which you'll build in the web module. One cross-module plant: validating input against constraints — never trusting a raw value — is the core instinct of secure software; failing to validate is how attackers get in, which is the heart of S-E-eleven-oh-four and a whole Year Twelve security module.

NARRATOR: Consolidate — takeaways, the way you'd write them. One: a data dictionary is a formal document specifying every field's structure, type, constraints, and relationships, used for consistency, validation, documentation, and quality control. Two: each entry is F-T-C-R — Field name, Type, Constraints, Relationship — plus a description and example. Three: the four constraint kinds answer four questions — how long (length), how big (range), what shape (format), must it be there (required). Four: the three relationships are one-to-one, one-to-many, and many-to-many. Five: the dictionary drives both your validation code and your boundary test data. The traps: omitting the actual min and max on constraints, and forgetting to record relationships — both leave the job half done.

NARRATOR: Now the exam-style questions. Pen down, and when I say pause, attempt it before the model answer.

QUESTION: Question one. State what a data dictionary is and give two reasons it is used.

NARRATOR: A data dictionary is a formal document that describes the structure, data types, constraints, and relationships of all the data in a software system. Two reasons, from the four: it ensures consistency, so everyone uses the same formats and field definitions; and it supports validation, by defining exactly which values are acceptable so invalid data can be rejected. You could equally cite documentation for future developers, or quality control. The mark is a precise definition plus two genuine purposes.

QUESTION: Question two. Construct a data dictionary for a library book, including ISBN, title, author, publication year, and whether it is available. Pause the player, draw the table, then play.

NARRATOR: A strong answer is a table with a row per field. ISBN: string; required; format exactly thirteen digits; example a thirteen-digit number. Title: string; required; maximum two hundred characters. Author: string; required; maximum one hundred characters. Publication year: integer; required; range eighteen hundred to the current year. Available: boolean; required. And for top marks, a relationship or conditional rule — a borrower identifier may be present only when the book is not available. That worked dictionary is in Listing 6. The marks are for each field having a type and at least one real constraint, plus naming the relationship — not just a bare list of field names.

QUESTION: Question three. Name the four kinds of constraint, with an example of each.

NARRATOR: Length — a maximum or minimum number of characters, like a name of two to fifty characters. Range — a minimum and maximum value, like an age of sixteen to twenty-five. Format — a required pattern, like a product code of three letters followed by five digits. Required — whether the field may be empty, like a student name that must always be present. The four questions to recall them: how long, how big, what shape, must it be there.

QUESTION: Question four. Distinguish between a data dictionary and a database schema.

NARRATOR: A data dictionary is human-readable design documentation describing fields, types, constraints, relationships, business rules, and examples, intended for people to read and agree on during design. A database schema is the machine-readable structure that defines and enforces the database's tables and column types at build time. The dictionary is richer and guides the creation of the schema, but the schema is what the database engine actually enforces. The mark is the contrast: documentation for humans at design time versus enforced structure for the machine at build time.

QUESTION: Question five. A data dictionary entry reads "age: integer." Explain why this is inadequate and rewrite it properly.

NARRATOR: It's inadequate because it gives only the type and no constraints — nothing stops an invalid value like minus five or five hundred, so the entry fails its main jobs of validation and quality control. A proper entry adds constraints and context: age — type integer; required; range, say, sixteen to twenty-five years; description, the student's age; example, seventeen. The mark-earning point: a type without constraints is not a usable specification — you must state the range and whether it's required.

NARRATOR: That's the lesson. A data dictionary is the formal blueprint for your data — every field as F-T-C-R, Field name, Type, Constraints, Relationship — with the four constraint kinds, how long, how big, what shape, and must it be there, and the three relationships, one-to-one, one-to-many, and many-to-many. It drives your validation code and your test data both.
