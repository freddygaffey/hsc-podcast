NARRATOR: Let's pick up where we left off. Last episode opened Chapter 6 — Programming in OOP — and the big idea was that Chapter 5 designed the objects, and Chapter 6 builds, refines and tests them. The verbs flip: we stop describing and planning, and we start designing and implementing. The home topic was building classes and composition. The constructor — the dunder init, the double-underscore init method that runs when you instantiate — must validate its inputs and raise a value-error before storing anything, so the object is born valid. We said it like this: validate, then store. It enforces invariants and fails fast at the boundary. Not "so it doesn't crash" — that's the band-four answer. The mark phrase is "it enforces invariants and fails fast".

NARRATOR: The centrepiece of 06-01 was composition over inheritance. Inheritance is an "is-a" relationship; composition is a "has-a" relationship. A car is-a vehicle, but a car has-a engine — it's not a kind of engine. So you build a complex object by holding simpler component objects as attributes and delegating to them. The mnemonic — say it with me, because we reuse it the whole module — is "is-a versus has-a, favour has-a when unsure". And the four benefits of composition over inheritance, as one chant: runtime-flexible, loosely coupled, independently testable, no diamond problem. We also met dependency injection — passing an object's dependencies in from outside rather than building them internally — and cohesion, which means one class, one well-defined job. A class doing email and file access and database work and logging all at once is a low-cohesion god-class, and the fix is to split it by responsibility, giving each one a home. That's the R-R-C-I idea from the design process episode: Requirements, Responsibilities, Collaborations, Implementation.

NARRATOR: Reach back two episodes and you've got the whole Chapter 5 spine still echoing — A-PIE, the four behaviours: Abstraction, Polymorphism, Inheritance, Encapsulation. And I-C-F-S, the four reasons to encapsulate: Integrity, Consistency, Flexibility, Security. Hold onto those; they keep paying off.

NARRATOR: Now, here's the thread into today. You can build a class, and you can compose it from smaller objects. But we've been hand-waving over what actually happens *inside* the methods. A method isn't just a name and a return value — it has *logic*. Branching. Iteration. Decisions made on the object's own state. Today is about the control structures that live inside methods: the if, elif and else; the for and while loops — and, just as important, how to keep that logic clean instead of letting one method swell into a monster. This is the dot-point that says "implement and modify OOP programming code, including use of control structures and data structures", and the one that says "design and implement computer programs involving branching, iteration and functions in an OOP language". Outcomes SE-eleven-oh-two and SE-eleven-oh-seven.

NARRATOR: Here's what you'll be able to do by the end. You'll be able to refactor a long, do-everything method into focused helper methods — and that's a recurring code task in the exam, so it matters. You'll be able to state the Single Responsibility Principle for methods and back it with the under-twenty-lines rule of thumb. You'll be able to rewrite a deeply nested if-statement using guard clauses. And you'll be able to explain why a while loop needs a safety limit. Four concrete skills. Let's earn them.

NARRATOR: Start with selection — the if, elif and else — inside a method. Now, you know how an if-statement works; I'm not going to insult you by explaining branching. The OOP-specific thing here is *what the condition tests*. Inside a method, the most powerful conditions read the object's own state — its attributes — not just the parameters passed in. Picture a withdraw method on a bank-account object. It can ask three different kinds of question. It can ask about the object's state: is this account frozen? It can ask about the parameter: is the amount positive? And it can ask about the relationship between the two: is the amount greater than the current balance? Three checks, three sources — state, parameter, and state-versus-parameter. That's the shape of selection inside a method, and it's worth naming explicitly in an exam answer because it shows you understand that a method operates on the object it belongs to.

NARRATOR: Now I want to talk about *how* you arrange those checks, because this is where marks live. There are two ways to write that withdraw method, and they are night and day. The weak way is nested ifs. You write: if the account is not frozen, then — and you indent — if the amount is positive, then — indent again — if the amount is less than or equal to the balance, then — indent a third time — do the withdrawal. By the time you reach the actual work, you're four levels deep, and somewhere off to the side are the elses that handle each failure. Programmers call this the arrow anti-pattern, or the pyramid of doom, because the code drifts rightward into an arrowhead shape and the real logic is buried at the tip. It's hard to read, hard to test, and easy to get the matching elses wrong.

NARRATOR: The strong way is guard clauses. A guard clause is an early return that handles a bad case immediately and bails out, so the rest of the method doesn't have to worry about it. So instead of nesting, you write: if the account is frozen, return a failure right now. If the amount is not positive, return a failure right now. If the amount exceeds the balance, return a failure right now. And then — flat, un-indented, at the bottom — the happy path: subtract the amount, return success. Every failure case is dealt with and dismissed at the top, one per line, and the main logic sits at ground level where you can read it. The mnemonic for this — write it down — is "guard clauses flatten the arrow of nested ifs". Same checks, same behaviour, completely different readability. The guard-clause withdraw is in Listing 2 if you want to read it later; the contrast between the nested version and the guarded version is the whole point.

QUESTION: Hang on — isn't having lots of return statements in one method considered bad style? I was told a method should have a single exit point.

NARRATOR: That's an old rule, and it's worth knowing why it's mostly dead. The single-exit-point idea comes from a time of manual memory and resource cleanup in languages like C, where multiple returns meant you could skip your cleanup code and leak resources. In modern Python — with garbage collection, with context managers handling cleanup — that risk is gone. And in exchange, guard clauses buy you flat, readable code where each precondition is checked and dismissed up front. So for HSC purposes: early returns as guard clauses are *good* style, not bad. If a marker or a textbook leans on single-exit, the sophisticated answer is "single-exit made sense for manual resource cleanup; guard clauses are clearer and safer in a garbage-collected language". That nuance is a mark, not a trap.

NARRATOR: Let me give you the strong-versus-weak contrast in answer form, because the exam will ask you to rewrite a nested if using guard clauses. The weak answer just re-indents the same logic and calls it done. The strong answer says: "I inverted each condition so the *failure* case is handled first with an early return, removing the nesting, so the main success logic sits flat and unindented at the end of the method." Notice what that sentence does — it names the technique, it explains the transformation, and it states the benefit. That's a full-mark rewrite explanation.

NARRATOR: Now iteration — for and while loops — inside methods. Again, you know loops. The OOP angle is that the thing you're looping over is usually one of the object's own data structures: a list it holds, a dictionary it manages. That's the "data structures" half of the dot-point — control structures and data structures together. Take an inventory object that holds a dictionary of item names to quantities, and another of names to prices. A calculate-total-value method walks the items with a for-loop, multiplies each quantity by its price, and accumulates a running total. A find-low-stock method walks the same items with a for-loop and collects every item whose quantity falls below a threshold into a report list. The for-loop is the right tool here precisely because you know the bound: you're visiting every item in the collection, once. Definite iteration. That inventory loop is in Listing 4.

NARRATOR: A while loop is for when you *don't* know the bound in advance — indefinite iteration. You keep going until some condition flips. And this is where a real danger lives, so lean in. A for-loop over a list will always terminate, because the list is finite and you visit each element once. A while loop has no such guarantee. If the condition never becomes false — because of a bug, a bad input, or an edge case you didn't foresee — the loop runs forever. Your method hangs. The program freezes. So the discipline is: a while loop whose termination isn't *obviously* guaranteed needs an explicit safety limit. You add a counter, you increment it every pass, and you put a second condition on the loop — keep going *while the real condition holds and the counter is under, say, a hundred*. If the real condition somehow never flips, the counter eventually breaks you out anyway. It's a circuit breaker. You'll see this in Listing 5 — a queue-style processor with a counter that caps the iterations — and the same safety-limited loop written in NESA exam pseudocode is in Listing 6, so you can rehearse the form you'd write under exam conditions.

QUESTION: Before I move on — pause the player here and actually answer this. Why is a runaway while loop a worse failure than, say, a wrong calculation? And what specifically do you add to prevent it? Pause now, work it out, then play.

NARRATOR: Welcome back. A wrong calculation gives you a wrong answer — bad, but the program finishes and you can test for it. A runaway while loop gives you *no* answer: the method never returns, the program is frozen, and in a real system that can take a service down. It's a worse class of failure because it's non-terminating, not just incorrect. What you add to prevent it is an explicit safety limit, also called a guard counter or a bounded loop: a counter that increments each iteration and a second loop condition that exits once the counter passes a maximum. The mark-earning phrasing is "the while loop has no guaranteed termination, so I add a counter and a maximum-iteration cap as a safety limit, ensuring the loop always exits even if the primary condition never becomes false". Name it, justify it, done.

NARRATOR: So that's the raw material — selection and iteration inside methods. Now the bigger lesson, which is the real heart of today: keeping methods short and cohesive. Because here's the thing — once a method has a couple of loops and a handful of branches, it starts to grow. And a method that does too much is the single most common code-quality failure students show in the exam, and the single most common refactor task they're asked to fix.

NARRATOR: The principle has a name: the Single Responsibility Principle. For a method, it means each method should do *one logical thing*. One job. Not "process the order" where processing means validate the customer and check inventory and calculate the total and apply discounts and update stock and write the record — that's six jobs wearing one method's name. One job. And paired with that is a rule of thumb you can quote: a method should generally be under about twenty lines. It's not a hard law — a method at twenty-two lines isn't a crime — but if a method is running to forty, fifty, sixty lines, that's a smell, a signal it's doing more than one thing. Put those together into the mnemonic for the whole episode: "S-R-P — one method, one job, under about twenty lines". Single Responsibility Principle, one job, under twenty. Say it as one breath.

NARRATOR: Now let me give you the centrepiece worked example, because this is the one the exam keeps asking. Picture an order-processor class with a method called process-order. The bad version — and it's in Listing 1, labelled the bad version — is one giant method. It validates the customer: checks the customer exists, checks they're active. Then in the same method it loops over the items checking inventory: does each item exist, is there enough stock. Then it loops again to calculate the total. Then it applies a VIP discount and a bulk discount. Then it loops a *third* time to subtract the purchased quantities from inventory. Then it builds the order record dictionary and appends it to the orders list. All in one method. Maybe sixty lines. Three separate loops, a fistful of branches, four or five distinct responsibilities crammed together.

NARRATOR: Why is that bad, concretely, in exam terms? Four reasons, and you should be able to list them. One: it's hard to read — you can't see the shape of the process because every detail is in your face at once. Two: it's hard to test — you can't test the inventory check without also running the customer validation and the discount logic, so a unit test can't isolate anything. Three: it's hard to change — if the discount rules change you have to wade into a sixty-line method and pray you don't break the inventory update. Four: it's hard to reuse — you can't call just the validation from somewhere else, because it's welded to everything else. Read, test, change, reuse. That's your four-point critique of a god-method.

NARRATOR: Now the good version — Listing 1 again, the good version, right beside the bad one so you can hold them up against each other. The fix is method extraction: you pull each responsibility out into its own focused, private helper method. So the main process-order method becomes short and readable. It says: if validate-customer fails, return failure. If check-inventory-availability fails, return failure. Then total equals calculate-order-total. Then call update-inventory. Then create-order-record. Then return success. That's it — maybe eight lines, and it reads like a table of contents for the whole process. Each helper — validate-customer, check-inventory-availability, calculate-order-total, update-inventory, create-order-record — does exactly one job, lives just below, and can be read, tested and changed on its own. We mark them private with a single leading underscore, by convention, because they're internal helpers, not part of the object's public interface — that's the encapsulation idea from 05-02 doing quiet work here.

QUESTION: So when the exam says "refactor this long method into focused methods", what's the actual recipe? Is there a procedure I can follow under pressure?

NARRATOR: There is, and it's worth memorising because this exact task recurs. Four steps. One: identify the distinct responsibilities — read the method and find the comment-worthy chunks, the "validate", "calculate", "update", "build the record" sections. Each chunk is a candidate method. Two: extract each chunk into its own private helper with a name that says what it does — a verb phrase, validate-customer, calculate-total. Three: replace the original chunk with a call to that helper. Four: the original method becomes a short coordinator that calls the helpers in order. And then state the benefit, because the marks are in the justification: "extracting each responsibility into a focused method makes each one readable, independently testable, and reusable, and turns the original method into a clear, high-level summary of the process." That last sentence is the difference between the band-four "I split it up" and the band-six answer.

NARRATOR: Let me draw two cross-links here, because this topic doesn't stand alone. First, look back at the design-process episode, 05-06. We taught the facade pattern — one simple front-of-house class hiding a messy subsystem behind a clean interface. The good process-order method is the *same instinct* at method scale. The coordinator method is a little facade: a clean, readable front that hides the messy details inside the helpers. "A facade is a tidy front desk over a messy back office" — and that's exactly what a well-extracted method is. Same idea, smaller scale. Second, look forward. Next episode, 06-03, is about designing subroutines and stubs — the clear, uncluttered mainline, one logical task per subroutine. What you're learning today *is* the "one logical task per subroutine" discipline applied inside a class. The coordinator method that reads like a table of contents in 06-03 is the same coordinator method you're extracting today. And the whole reason this matters — short, focused, single-responsibility methods — is the maintainability that the Year 12 major project, the SEE project, is literally marked on, and the readable code that Secure Software Architecture expects. Clean methods aren't a nicety; they're an assessed outcome.

NARRATOR: Now, a trap — because every good principle has an over-correction, and the markers know it. Once students learn method extraction, some go berserk and extract *everything*, including trivial one-liners. They'll take a single line that adds two numbers and wrap it in a method called add-numbers. That's over-extraction, and it's its own code smell. It scatters the logic across a dozen tiny methods, and now to understand a simple operation you have to chase calls all over the class — you've traded one too-big method for ten too-small ones. The judgement is: extract when a chunk is a *distinct responsibility* with a name that earns its keep, not when it's a trivial expression that's perfectly clear inline. So the balanced answer — and balance is what markers reward, same as "OOP isn't always better" from 05-04 — is "extract genuine responsibilities, but don't extract trivial one-liners; the goal is clarity, and too many tiny methods harms clarity as much as one giant one." Both extremes lose marks. The middle is the mark.

NARRATOR: Let me consolidate the traps as a set, because the exam loves to plant them. Trap one: deeply nested conditionals — the arrow of doom — fixed by guard clauses. Trap two: one method doing everything — the god-method — fixed by method extraction into single-responsibility helpers. Trap three: a missing loop termination — the runaway while — fixed by a safety limit. Trap four: over-extracting trivial one-liners — death by a thousand tiny methods — fixed by judgement about what counts as a real responsibility. Four traps, four fixes. If you can name the trap and name the fix, you can answer almost any question on this dot-point.

NARRATOR: One more cross-link to lay down for later. The data structures we're looping over inside these methods — the lists, the dictionaries — that's "use of control structures and data structures" as one phrase in the syllabus. Choosing the *right* data structure to loop over is part of writing an effective method, and when we get to 06-07, assessing the effectiveness of code, you'll see that picking a dictionary for an O-of-one lookup instead of scanning a list with an O-of-n loop is exactly the kind of choice that makes a method effective. For now, just notice: the loop and the data structure it walks are a pair, and both are the dot-point.

NARRATOR: Before the exam questions, here's the recap — the handful of things to carry out of today, phrased the way you'd write them. Selection inside a method makes decisions on the object's own state, its parameters, and the relationship between them. Guard clauses — early returns that handle bad cases first — flatten the arrow of nested ifs and are good style in a garbage-collected language. Iteration: a for-loop for definite iteration over a collection, a while loop for indefinite iteration that *must* have a guaranteed exit or an explicit safety limit. The Single Responsibility Principle for methods: one method, one job, generally under about twenty lines. And method extraction: break a long, do-everything method into focused private helpers, turning the original into a short coordinator that reads like a table of contents — but don't over-extract trivial one-liners. The two mnemonics: "S-R-P — one method, one job, under about twenty lines", and "guard clauses flatten the arrow of nested ifs".

NARRATOR: Now let's finish with exam-style questions. Pause the player on each one, attempt a real answer, then play on for the model. These are the kinds of questions NESA actually asks on this dot-point.

QUESTION: Question one. Explain the Single Responsibility Principle as it applies to methods. Three marks. Pause now, write your answer, then play.

NARRATOR: Model answer. The Single Responsibility Principle states that each method should have one clear, well-defined job — one logical task — rather than performing several unrelated operations. A method that follows it is short, generally under about twenty lines, and easy to read, test, change and reuse in isolation. A method that violates it — doing validation and calculation and persistence all at once — is hard to test because its responsibilities can't be isolated, and hard to maintain because a change to one concern risks breaking the others. For the three marks: one, state that each method does one logical task; two, give the practical consequence — short, focused, independently testable; three, contrast it with a multi-responsibility method to show you understand the boundary. Naming "one job, under about twenty lines" lands it.

QUESTION: Question two. Here is a withdraw method written as three nested if-statements, drifting four levels deep. Rewrite it using guard clauses, and explain the benefit. Pause now, work it through, then play.

NARRATOR: Model answer. You invert each condition so the failure case is handled first. If the account is frozen, return failure immediately. If the amount is not positive, return failure immediately. If the amount exceeds the balance, return failure immediately. Then, flat and unindented at the bottom, perform the withdrawal and return success. The benefit, in mark-earning words: "the guard clauses handle each invalid precondition with an early return, eliminating the nested indentation so the main success logic sits flat and readable at the end of the method." The full guarded version is in Listing 2. The mark is for naming guard clauses, showing the inversion, and stating that it flattens the nesting — "guard clauses flatten the arrow of nested ifs".

QUESTION: Question three. The recurring one. You're shown a single sixty-line process-order method that validates a customer, checks inventory, calculates a total with discounts, updates inventory and creates an order record. Refactor it into focused methods. Pause now, plan your refactor, then play.

NARRATOR: Model answer. Identify the distinct responsibilities — customer validation, inventory check, total calculation, inventory update, order-record creation — and extract each into its own private helper method named for its job: validate-customer, check-inventory-availability, calculate-order-total, update-inventory, create-order-record. The original process-order method becomes a short coordinator: it calls validate-customer and returns early on failure, calls check-inventory-availability and returns early on failure, then calls calculate-order-total, update-inventory and create-order-record in turn, and returns success. Then justify: "each helper now has a single responsibility and can be read, tested and changed in isolation, while the main method reads like a clear, high-level summary of the process." That justification — single responsibility, independently testable, readable summary — is where the top-band marks are. QUESTION: Question four. Why should a while loop include a safety limit? Explain with reference to program behaviour. Pause now, then play.

NARRATOR: Model answer. A while loop continues as long as its condition is true, and unlike a for-loop over a finite collection, it has no guaranteed termination — if the condition never becomes false, due to a bug or an unexpected input, the loop runs forever and the method never returns, freezing the program. A safety limit — a counter that increments each iteration combined with a maximum-iteration cap added to the loop condition — guarantees the loop will always exit, even if the primary condition fails to flip. So the answer names the risk (non-termination, a hung program), and names the fix (a guard counter with a maximum-iteration cap as a safety net). The bounded version is in Listing 5.

QUESTION: Question five, the harder one. A student has learned method extraction and has refactored a class so that every operation — including adding two numbers and formatting a single string — is its own one-line method. Evaluate their approach. Pause now, give a balanced judgement, then play.

NARRATOR: Model answer, and the key word is *evaluate*, so you need a balanced judgement, not a one-sided verdict. Acknowledge the good: extracting genuine responsibilities into focused methods improves readability, testability and reuse, and following the Single Responsibility Principle is sound. But then the critique: the student has over-extracted. Wrapping trivial one-liners — adding two numbers, formatting one string — in their own methods scatters simple logic across many tiny methods, so understanding even a basic operation now means chasing calls all over the class, which *harms* readability rather than helping it. The balanced conclusion: method extraction should target distinct, named responsibilities, not trivial expressions; the goal is clarity, and too many trivial methods damages clarity as much as one over-large method does. The mark is in the balance — recognising the principle is right but the application is overdone — exactly the same shape as "OOP isn't always better" and "a facade hides complexity, it doesn't remove it". Markers reward the student who can see both edges of a good idea.
