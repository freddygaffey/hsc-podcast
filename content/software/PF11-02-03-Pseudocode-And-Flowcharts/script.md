NARRATOR: Objectives up front. NARRATOR: Let's start with pseudocode, because it's the one you'll write most in the exam. Pseudocode is structured English that describes an algorithm's steps without the syntax of any particular programming language. The point is that anyone can read it, regardless of which languages they know — and crucially, NESA marks your exam pseudocode against its own house style, not against Python. So writing real Python in a "write the algorithm in pseudocode" question can actually cost you marks. Learn the house style.

NARRATOR: Here are the conventions. An algorithm is wrapped between BEGIN and END, usually with a name. Input and output use the keywords INPUT and OUTPUT. Assignment — putting a value into a variable — uses the word SET, or in the strictest NESA style a left-pointing arrow, which you read aloud as "gets" — total gets price plus tax. Then the three control structures from last episode, each with its own keyword skeleton. Selection is IF, condition, THEN, the statements, and END IF — with ELSE and ELSE IF in between for the branches. Iteration is WHILE, condition, DO, statements, END WHILE for a pre-test loop; FOR, variable, start, TO, end, DO, statements, END FOR for a counted loop; and FOR EACH, item, IN, collection, for walking a list. Notice this is exactly S-S-I — sequence is just lines in order, selection is the IF family, iteration is the loop family. Pseudocode is S-S-I wearing keywords.

NARRATOR: And the style rules are the readability rules from two episodes ago, applied here. Use clear, descriptive names — "total price", not "x". Indent consistently, so the nesting is visible — an IF inside an IF steps in one level, and the matching END IF lines up. One action per line; don't cram four steps onto one line with commas. That's R-D-C thinking — the same readability that earns marks in code earns marks in pseudocode, because an examiner has to be able to follow your logic at a glance.

NARRATOR: Let's make this concrete with the worked example we'll carry through the episode — a library book-borrowing system, the running example for this chapter. The task in plain English: ask for a library card number and a book identifier, check whether the borrower has overdue books, check whether the book is available, and then make a decision. Borrowing is allowed only if there are no overdue books and the book is available. Otherwise, explain why it was denied. Now, that's a decision with four possible situations, and this is where students lose marks, so listen closely. The four cases are: no overdue books and the book available — allow it; overdue books and the book also unavailable — deny, and mention both problems; overdue books but the book is available — deny, return your overdue books first; and no overdue books but the book unavailable — deny, the book is checked out. Four branches, every combination covered. The full pseudocode is in Listing 1. The exam trap here is leaving a branch unhandled — covering "allowed" and "has overdue" but forgetting the case where the book simply isn't available. Every combination of your conditions must lead somewhere. A dangling, unhandled path is a logic error, and markers look for exactly that.

QUESTION: That's a lot of repeated condition-checking. Isn't there a tidier way to write it?

NARRATOR: There is, and it's the second half of today's dot-point: subprograms. Notice that "check whether the borrower has overdue books" is itself a self-contained job — it has an input, the card number, and an output, true or false. So is "check whether the book is available." Each of those can be pulled out into its own named subprogram, and the main algorithm just calls it. In pseudocode, you call a subprogram by naming it and passing its inputs in brackets — the has-overdue check gets the card number and returns a true-or-false, and you store that result in a variable. The main algorithm becomes short and readable: get the inputs, call the overdue check, call the availability check, then make the decision on the two results. The two checks live in their own definitions below. That's in Listing 2. This is the payoff of the whole "structured algorithms" idea — you decompose a big task into named subprograms, each doing one job. It's the same separation-of-concerns instinct from the very first episode, and it's the direct setup for the next two lessons: structure charts, which diagram that decomposition, and procedures versus functions, which is the formal distinction between the kinds of subprogram you just called.

NARRATOR: Now flowcharts — the second notation, the visual one. A flowchart shows the same logic as a diagram: shapes connected by arrows that show the order of execution, where it branches, and where it loops. The most directly examined fact in this whole topic is the symbols — which shape means what — so let's nail them, and there's a memory hook for each because the shape usually hints at its job. The full reference is in Listing 3.

NARRATOR: Start and end are marked by a terminator — a rounded rectangle, an oval-ish stadium shape. Rounded ends top-and-tail the chart. Input and output use a parallelogram — the leaning shape; lean it for data going in or coming out. A process — any ordinary step, a calculation or an assignment — is a plain rectangle; the square box does the work. A decision is a diamond — and this is the one that matters most, because the diamond is the only symbol that branches: a question with, usually, a "yes" arrow and a "no" arrow leaving it. Diamond decides. Flow lines are arrows showing what happens next. And — tying in today's subprograms — a call to a subprogram is drawn as a predefined process: a rectangle with double vertical bars down the sides. The double-barred box is a call. So: rounded for start and stop, parallelogram for in and out, rectangle to do a step, diamond to decide, double-barred rectangle to call a subprogram.

QUESTION: Here's one to actually attempt. Pause the player. Which flowchart symbol is used for a decision, and what makes it different from every other symbol? Work it out, then play.

NARRATOR: The decision is the diamond, and what makes it unique is that it's the only symbol with more than one arrow leaving it — every other shape is one-in, one-out, but the diamond splits the flow into separate labelled paths, one per answer. That's the defining property. And it gives you the number-one flowchart trap to avoid: every branch out of a diamond must lead somewhere. A "yes" path that just dangles, or a decision with no "no" path, is a broken flowchart — the same unhandled-case error we saw in the library pseudocode, just drawn instead of written. When you draw a decision, immediately ask "where does the other arrow go?"

NARRATOR: The real skill the exam tests is converting between the three representations — natural language, pseudocode, and flowchart — because they're the same logic in different clothes. Take a simple task in plain English: "ask for three numbers, find the largest, and display it." To turn that into pseudocode, you identify the inputs — three numbers — the process — compare them to find the largest — and the output. You set the largest to the first number, then check each of the other two: if it's bigger than the current largest, it becomes the new largest. That's a stored running extreme — remember A-E-F from the control-structures episode, the E was Extreme, the best-so-far. Listing 4 shows that natural-language-to-pseudocode conversion in full. To go on to a flowchart, each line becomes a shape: the inputs are parallelograms, "set largest to the first number" is a rectangle, each comparison is a diamond with the update on its "yes" branch, and the display is a parallelogram. Line by line, pseudocode and flowchart map onto each other — every IF, loop, and assignment should appear in both. That alignment is itself a checking technique: if a shape has no matching pseudocode line, one of them is wrong.

NARRATOR: So when do you use which? Use pseudocode when you're planning logic before coding, documenting steps precisely, or communicating with other programmers — it's compact and close to code. Use a flowchart when you're visualising decision paths and branching, presenting to people who think visually, or spotting a missing case — a gap in a diagram jumps out at the eye. Use both for complex algorithms or formal documentation, where two views catch more than one. And to verify the library example actually behaves, Listing 5 is the borrowing decision written as runnable code, with all four cases checked — proof the four branches really do cover every combination.

NARRATOR: One more interleaving link worth planting now, because it's a classic exam trap waiting in a later module. A flowchart is not the same as a data flow diagram. A flowchart shows control flow — the order steps execute in, with decisions and loops. A data flow diagram, which you'll meet properly in the object-oriented module, shows where data moves and is transformed, with no notion of execution order at all. Students confuse them constantly. The one-liner to lock it: a flowchart shows what the program does, in order; a data flow diagram shows where the data goes. Same family, different jobs — we'll cash this in fully later.

NARRATOR: Let's consolidate — today's takeaways, phrased the way you'd write them. One: pseudocode is structured English in NESA's house style — BEGIN and END, INPUT and OUTPUT, SET or the gets-arrow for assignment, and the IF and loop skeletons; it's just S-S-I in keywords, written with descriptive names and consistent indentation. Two: a flowchart is the same logic as a diagram — rounded terminator for start and stop, parallelogram for input and output, rectangle for a process, diamond for a decision, double-barred rectangle for a subprogram call. Three: the diamond is the only branching symbol, and every branch must lead somewhere — a dangling path is a logic error. Four: subprograms let you decompose a task into named, single-job pieces the main algorithm calls. Five: the three representations — natural language, pseudocode, flowchart — are interchangeable, and lining them up is itself a way to check your work.

QUESTION: Question one, recall. Name the flowchart symbol used for each of these: the start of an algorithm, an input, a processing step, a decision, and a call to a subprogram.

NARRATOR: Start, a terminator — a rounded rectangle. Input, a parallelogram. A processing step, a rectangle. A decision, a diamond. A subprogram call, a predefined process — a rectangle with double vertical bars. The memory hook: rounded top-and-tails, parallelogram for in and out, rectangle does a step, diamond decides, double-barred box calls. Five symbols, one mark each in a stimulus question — free marks if you've drilled them.

QUESTION: Question two. Write pseudocode for this task: ask the user for a temperature in Celsius, convert it to Fahrenheit, and display the result. Pause the player, write it, then play.

NARRATOR: Here's a full-mark version. BEGIN. OUTPUT a prompt, "Enter a temperature in Celsius". INPUT celsius. SET fahrenheit to celsius times nine, divided by five, plus thirty-two. OUTPUT a message with the fahrenheit value. END. The marks are for using the NESA keywords — BEGIN, INPUT, SET, OUTPUT, END — for a correct conversion formula, and for descriptive variable names rather than single letters. A weak answer writes it as a line of Python, or uses vague names like x and y; a strong answer reads as clean structured English in the house style.

QUESTION: Question three. In the library borrowing flowchart, a student draws the "has overdue books" decision diamond with only a "yes" arrow leading to a denial message. Identify the error and explain how to fix it.

NARRATOR: The error is an unhandled branch — a decision with a missing path. The diamond has a "yes" arrow but no "no" arrow, so when the borrower has no overdue books, the flow has nowhere to go: a logical dead end. The fix is to add the "no" path, leading to the next check — book availability — so that every outcome of the decision continues somewhere. State it as: "every branch out of a decision must lead to a defined next step; the missing 'no' path is a logic error and must be connected." That phrasing names the rule and the fix.

QUESTION: Question four. Explain one situation where a flowchart is a better choice than pseudocode, and one where pseudocode is better.

NARRATOR: A flowchart is better when you need to visualise branching and decision paths — for example presenting a process to non-programmers or spotting a missing case, because a gap in the diagram is visible at a glance. Pseudocode is better when you're planning logic right before coding or documenting it precisely, because it's compact, close to the final code, and quick to edit. The mark is in giving a reason tied to each one's strength — visual clarity for the flowchart, precision and code-closeness for pseudocode — not just stating a preference.

QUESTION: Question five, application. Rewrite the temperature converter from question two so that the conversion is done by a separate subprogram that the main algorithm calls. Describe how you'd represent that call in a flowchart.

NARRATOR: Define a subprogram — call it celsius-to-fahrenheit — that takes a Celsius value as its input and returns the Fahrenheit value using the formula. The main algorithm then does: OUTPUT the prompt, INPUT celsius, SET fahrenheit to the result of calling celsius-to-fahrenheit with celsius, then OUTPUT the result. In the flowchart, the call to that subprogram is drawn as a predefined process — the rectangle with double vertical bars — rather than a plain process rectangle, signalling that the work happens in a separately defined routine. Full marks: a named subprogram with a parameter and a return, the main algorithm calling it and storing the result, and the predefined-process symbol named for the flowchart representation. That's the decomposition idea the next two episodes build on.
