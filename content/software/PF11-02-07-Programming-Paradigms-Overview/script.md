NARRATOR: First, what is a paradigm? A programming paradigm is a fundamental style or approach to programming — a way of thinking about and organising a solution. The architecture analogy is good: Gothic, modern, classical are all valid ways to design a building, each suited to different purposes. Paradigms are the same — different approaches, each strong for different kinds of problem. And here's the hook for the whole episode, the four paradigms you must be able to name: I-O-L-F — Imperative, Object-oriented, Logic, Functional. I-O-L-F. Write that down the moment a paradigms question appears, then say one sentence about each. Let me give you that one sentence for each now, because the one-liners are the most memorable thing you can carry into the exam.

NARRATOR: Imperative — the thinking is "how to do it." You give the computer an explicit sequence of instructions to follow in order, with variables that change over time and explicit control flow — loops and conditionals. It's the tea recipe: fill the kettle, boil it, add the tea bag, pour. Everything you've written so far is imperative — and note, this is exactly S-S-I from the control-structures episode, sequence, selection, iteration, plus changing variables. Imperative is strong for tasks with clear sequential steps, for system programming, and whenever you need precise, direct control. The language C is essentially pure imperative.

NARRATOR: Object-oriented — the thinking is "model the world." Instead of a list of steps, you model the problem as objects that each bundle data and the abilities that act on that data, and the objects interact by sending messages to each other. A student object has properties — name, age, grades — and abilities — enrol in a course, calculate a grade-point average. A course object has its own properties and abilities. You build the program by deciding what objects exist and how they collaborate. This is strong for complex systems, for user interfaces, for anything that models real-world entities. And this is the one that matters most for you right now, because the entire next module is the object-oriented paradigm — everything from today's "model the world" one-liner is about to become a whole course.

NARRATOR: Logic — the thinking is "what is true." This one is genuinely different: you don't tell the computer how to compute anything. You state facts and rules, and the computer deduces the answers. The classic: the fact "Socrates is a man," the rule "if something is a man, then it is mortal," and the query "is Socrates mortal?" You never wrote a procedure — the engine deduces "yes" from the facts and the rule. Logic programming is query-based and declarative, and it's strong for expert systems, for rule-heavy problems, and for parts of artificial intelligence. The language Prolog — say "pro-log" — is the standard example.

NARRATOR: Functional — the thinking is "transform data." You build the program by combining mathematical functions, each taking input and producing output, with no changing variables — immutability — and no side effects. Remember pure functions from the subprograms episode? Same input, same output, nothing changed on the outside. Functional programming is that idea taken all the way: the whole program is functions composed together, and functions can be passed around and combined. The typical tools are map, filter, and reduce — apply a function to every item, keep the items that pass a test, and fold a collection down to a single value. It's strong for mathematical computation, for data processing, and because pure functions don't interfere with each other, for parallel processing. The language Haskell — "hass-kell" — is purely functional.

NARRATOR: There's a useful way to group these four. Imperative and object-oriented are both about HOW — you specify the steps, you just organise them differently, loose instructions versus instructions bundled into objects. Logic and functional lean declarative — more about WHAT: what is true, or what transformation to apply, leaving more of the how to the machine. That HOW-versus-WHAT split is a clean way to remember why the four feel so different.

QUESTION: Here's one to actually attempt. Pause the player. In your own words, outline the difference between imperative and functional programming. Work it out, then play.

NARRATOR: Imperative programming describes how to perform a task as an explicit sequence of statements that change the program's state over time — variables are updated step by step using loops and conditionals. Functional programming describes a computation as the combination of mathematical functions that transform inputs into outputs, avoiding changing state and side effects — values are not mutated, they're transformed. The core contrast: imperative changes state through a sequence of commands; functional avoids changing state and composes functions instead. That's a four-mark answer — name each, give its mechanism, and state the contrast. The marker is listening for "changing state and step-by-step" versus "no changing state and function composition."

NARRATOR: Now the most useful thing in this episode for actually understanding paradigms: the same problem, solved different ways. Take calculating the total price of a shopping cart. The imperative version, in Listing 1: start a total at zero, loop over each price adding it to the running total — there's our accumulator from the control-structures episode — then add tax. Step by step, a changing variable. The object-oriented version, in Listing 2: a shopping-cart object that holds the items and has a total ability; you tell the cart to total itself — the data and the behaviour live together in the object. The functional version, in Listing 3: take the list of prices, reduce it to a sum with an adding function, then apply a tax function — no loop, no changing variable, just functions transforming data. Three paradigms, three ways of thinking, and — this is the point — the exact same answer comes out of all three. The problem didn't change; the style of thinking did. Logic doesn't naturally express a numeric total like this — which is itself telling — so its example stays the facts-and-rules deduction in Listing 4: declare that Socrates is a man and that men are mortal, ask whether Socrates is mortal, and the engine deduces yes, with no steps written.

NARRATOR: That leads to the two big insights, and the two traps. First insight: no single paradigm is best. Each is strong for different problems — object-oriented for a game full of interacting entities, functional for transforming a big dataset, logic for a rule-based expert system, imperative for low-level system control. The trap is crowning a universal winner — "object-oriented is the modern one so it's best." Markers penalise that, exactly like the Waterfall-versus-Agile trap: the mark is "it depends on the problem." Second insight: a programming language is not the same as a paradigm. Most real languages are multi-paradigm — they support several. Python, the language for this course, is primarily imperative and object-oriented but has functional features too — map, filter, and the rest. The trap is saying "Python is an object-oriented language" as if that's all it is, or thinking a language locks you into one style. The paradigm is the style you write in; the language usually lets you pick. Listing 5 lays out the four one-liners and which languages typify each, plus that multi-paradigm point.

QUESTION: How does the exam usually test this?

NARRATOR: Three common shapes. One: "name the four programming paradigms" — straight recall, that's I-O-L-F, and a sentence each. Two: "outline the difference between two of them" — usually imperative versus functional or imperative versus object-oriented, where the mark is the contrast plus a mechanism for each. Three: a scenario — "which paradigm would suit building a flight simulator, and why?" — where you match the paradigm to the problem and justify. For that last one, the justification is everything: object-oriented for the flight simulator because it's full of interacting entities — aircraft, controls, weather — each with its own state and behaviour, which objects model naturally.

NARRATOR: Now the exam-style questions. Pen down, and when I say pause, attempt it before the model answer.

QUESTION: Question one, recall. Name the four programming paradigms, and give the central idea of each in a few words.

NARRATOR: Imperative — step-by-step instructions with changing variables, "how to do it." Object-oriented — interacting objects that bundle data and methods, "model the world." Logic — facts and rules from which the computer deduces answers, "what is true." Functional — composing mathematical functions with no changing state, "transform data." The hook is I-O-L-F, and the one-liner each is what turns a recall mark into a clear one.

QUESTION: Question two, four marks. Outline the difference between the imperative and object-oriented paradigms. Pause the player, write your answer, then play.

NARRATOR: Imperative programming organises a solution as a sequence of instructions that operate on data and change variables over time, with control flow handled explicitly by loops and conditionals. Object-oriented programming organises a solution around objects that each bundle data together with the methods that act on that data, and which interact by sending messages. The contrast: imperative separates the instructions from the data and focuses on the steps; object-oriented bundles data and behaviour together into objects and focuses on modelling entities. Full marks: a mechanism for each and the explicit contrast — steps-on-data versus data-and-behaviour-bundled.

QUESTION: Question three. Explain why most programming languages are described as multi-paradigm, using Python as an example.

NARRATOR: Most languages are multi-paradigm because they provide features supporting more than one style of programming, letting the programmer choose the approach that best fits the problem rather than forcing a single one. Python is an example: it supports imperative programming with sequences, loops and conditionals; object-oriented programming with classes and objects; and functional features such as map, filter and reduce. The mark-earning point is that the paradigm is the style the programmer writes in, and a single language can support several — so a language is not locked to one paradigm.

QUESTION: Question four, scenario. A team is building a large multiplayer game with many interacting characters, items, and environments. Which paradigm is most suitable, and why?

NARRATOR: The object-oriented paradigm is most suitable. A game of this kind is full of interacting entities — characters, items, environments — each with its own state, such as health or position, and its own behaviours, such as move or attack. Object-oriented programming models these naturally as objects that bundle that data and behaviour and interact by sending messages, which keeps the large system organised, modular, and reusable as it grows. The marks are for naming object-oriented and justifying with the "many interacting entities with state and behaviour" reasoning — not just "because it's modern."

QUESTION: Question five. Identify the paradigm each describes: "states facts and rules and lets the computer deduce the answer," and "composes pure functions and avoids changing state."

NARRATOR: The first is the logic paradigm — facts and rules with deductive, query-based reasoning, as in Prolog. The second is the functional paradigm — composing functions with immutability and no side effects, as in Haskell. The tell for logic is "deduce from facts and rules"; the tell for functional is "no changing state, compose functions." Recognising a paradigm from a description is a common quick mark — the one-liners are exactly what you match against.
