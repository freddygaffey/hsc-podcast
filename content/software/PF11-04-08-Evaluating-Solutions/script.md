QUESTION: Isn't "evaluating" just saying whether it works?

NARRATOR: No — and that confusion is exactly what loses marks. "Evaluate" is a high-order NESA verb: it means make a judgement against criteria, supported by evidence, leading to a conclusion. Not "it works well" — that's an opinion. A real evaluation says what you're judging against, cites the evidence, and reaches a balanced verdict. The dot-point: "Test and evaluate solutions, considering key aspects including functionality, performance, readability of code, quality of documentation." Outcome S-E-eleven-oh-six. Notice it says test AND evaluate — testing produces the evidence; evaluation is the judgement you build on it. And it names four aspects you must consider. That's today.

NARRATOR: Objectives up front. By the end you'll be able to: state the four aspects a solution is evaluated against; explain what evidence supports each; write an evaluation that earns marks rather than vague praise; and apply it to a finished program. Here's the hook for the four aspects: F-P-R-D — Functionality, Performance, Readability, Documentation. Functionality, Performance, Readability, Documentation. Write F-P-R-D at the top of any "evaluate this solution" question and structure your answer around the four. The full framework — the four aspects and the evidence each one needs — is in Listing 1. Let's take them.

NARRATOR: First, functionality — does it do what it's supposed to do? This is judged against the requirements and specifications from the very first episode: does the program meet the spec, produce correct outputs, and handle the cases it should — including the boundary and faulty inputs from the test-data episode — without the errors from last episode? And here's the key: the evidence for functionality is your test results. "All ten test cases pass, including the boundary marks and the invalid inputs" is evidence; "it works" is not. The full grade calculator with its passing test suite is in Listing 2 — those passing tests are the functionality evidence.

NARRATOR: Second, performance — how well and efficiently does it run? Speed, memory use, responsiveness, and whether it scales as the input grows. Two programs can both be functionally correct but perform very differently. Listing 3 shows two correct ways to detect duplicates: one compares every pair, which is slow and gets dramatically slower as the list grows; the other uses a set for instant membership checks and stays fast. Same correct answer, very different performance. The evidence for performance is measurement — timing, or reasoning about how the work grows with the input size. A strong claim: "it responds instantly for a class of thirty and would still scale to thousands"; a weak one: "it's fast."

QUESTION: Here's one to attempt. Pause the player. Two functions both correctly sort a list, but one is noticeably slower on a large list. Are they equal in quality? On which aspect do they differ? Work it out, then play.

NARRATOR: They are not equal in quality. They're equal on functionality — both produce the correct sorted result — but they differ on performance: the slower one does more work as the list grows, so it scales worse. This is the point of evaluating on multiple aspects: functionality alone doesn't capture quality. A correct-but-slow solution and a correct-and-fast one are functionally identical and yet one is clearly better, and only the performance aspect reveals it. The mark is naming that they're equal on functionality but differ on performance, with the reason being how each scales.

NARRATOR: Third, readability of code — can another person read and maintain it? This is the code-style episode, R-D-C, as an evaluation criterion: descriptive names, consistent indentation, clear structure, and single-responsibility functions from the functions episode. Listing 4 contrasts a cryptic version of a function — one-letter name, no structure — with a readable one that does the same thing: a descriptive name, a docstring, one clear job. Identical behaviour, very different maintainability. The evidence is the code itself — you point to the naming, the layout, the cohesion. And note: readability is a real quality measure, not optional polish, because code is read far more than it's written and maintenance is the longest, most expensive step of the lifecycle.

NARRATOR: Fourth, quality of documentation — is the solution documented so others can understand and use it? Again straight from the code-style episode, R-D-C: a README explaining what it is and how to run it, docstrings stating each function's contract, and comments that explain why, not what. The evidence is the presence and clarity of those documents. A strong evaluation: "each function has a docstring and a README explains how to run it"; a weak one: "it has comments." Documentation is a measured quality, not an afterthought.

NARRATOR: Now the thing that separates a band-four evaluation from a band-six, and it's the same move on every aspect: evidence and specifics, not adjectives. The strong answer, for each aspect, names the criterion, cites specific evidence, and concludes. QUESTION: Question one. Name the four aspects against which a software solution is evaluated.

NARRATOR: Functionality, performance, readability of code, and quality of documentation — F-P-R-D. For full marks add a clause on each: functionality is whether it meets its requirements, performance is how efficiently it runs, readability is how easily the code can be read and maintained, and documentation is how well it's explained for users and developers. Naming all four is the mark; the clauses make it unambiguous.

QUESTION: Question two. Explain the difference between a weak and a strong evaluation of a program's functionality. Pause the player, answer, then play.

NARRATOR: A weak evaluation of functionality is a vague opinion — "it works well" — with no supporting evidence. A strong evaluation judges the program against its specification and cites concrete evidence: which requirements are met, and the test results that demonstrate it — for example, "all test cases pass, including the boundary values and the invalid inputs, so the program meets the specification." The difference is evidence: the strong version references the spec and the test outcomes; the weak version asserts a conclusion with nothing behind it. The mark-earning point is that evaluation requires evidence, not adjectives.

QUESTION: Question three. Two programs are both functionally correct, but one runs much faster on large inputs. On which aspect do they differ, and why does this matter?

NARRATOR: They differ on performance. Although both are functionally correct — they produce the right output — one uses a more efficient approach that does less work as the input grows, so it scales better; the slower one may become unacceptably slow on large inputs. It matters because functional correctness alone does not make a solution good: a correct but inefficient program can fail to be usable in practice, which is why performance is a separate evaluation aspect. The mark is identifying performance and explaining that correctness and efficiency are distinct measures of quality.

QUESTION: Question four. Why are readability and documentation considered measures of a solution's quality, not just optional extras?

NARRATOR: Because code is read far more often than it is written, and maintenance — fixing, updating, and extending a program — is the longest and most expensive phase of the software lifecycle. Readable code, with descriptive names and clear structure, and good documentation, with a README and docstrings, make a solution understandable and therefore cheaper and safer to maintain and reuse; poor readability and missing documentation make even a correct program costly to work with. The mark-earning point: quality includes maintainability, and readability and documentation directly determine maintainability — they are not cosmetic.

QUESTION: Question five, extended. Evaluate the finished grade calculator against the four aspects.

NARRATOR: Structure it as F-P-R-D, with evidence on each. Functionality: it meets the specification — it computes the average and assigns the correct letter grade, and all test cases pass, including the boundary marks and invalid inputs, so it is functionally correct. Performance: it processes the scores in a single pass, so it runs efficiently and would scale to large numbers of students with no noticeable delay. Readability: the code uses descriptive, single-purpose functions — calculate-average and determine-grade — with consistent indentation, so it is easy to read and maintain. Documentation: each function has a docstring stating its purpose, and the comments explain reasoning rather than restating code. Conclusion: overall the solution is of high quality across all four aspects, with the strongest evidence being its complete test coverage. The marks come from addressing all four aspects with specific evidence and a balanced concluding judgement — not from praise.
