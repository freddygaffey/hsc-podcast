NARRATOR: A subprogram — and that's today. A subprogram is a named block of code that does one specific task; it's how you actually implement the modules you drew in a structure chart. The syllabus dot-point is short and pointed: "Identify procedures and functions in an algorithm." Outcome S-E-eleven-oh-two. Because there are exactly two kinds of subprogram, and the exam wants you to tell them apart on sight: procedures and functions. We're still in Chapter Two, designing algorithms — last episode you decomposed a system into modules; this episode you learn what those modules are and how data flows in and out of them.

NARRATOR: Objectives up front. By the end you'll be able to: distinguish a procedure from a function and identify which is which in a given algorithm; explain parameters and the three directions data can flow through them; explain return values and how they're used; and apply cohesion to design focused subprograms. And you'll nail the single most common short-answer question on this topic — "distinguish a procedure from a function," usually for three marks.

NARRATOR: Here's the whole distinction in one hook, so write it down: a function returns, a procedure performs. A function calculates a value and hands it back to whoever called it. A procedure performs an action and hands nothing back. Function returns; procedure performs. Everything else follows from that one sentence.

NARRATOR: Let's take functions first. A function takes some inputs, computes, and returns a single value to the calling code. Its job is to compute something. Calculate an average, convert Celsius to Fahrenheit, validate an email and return true or false, work out a person's age from their birth date — all functions, because in each case you want a value back. And there's a quality bar for functions worth naming now: ideally a function is pure. A pure function depends only on its inputs and has no side effects — it doesn't change anything outside itself, doesn't touch global state, doesn't print. Same inputs, same output, every time. Purity makes a function trivial to test and safe to reuse — and it's the seed of the functional programming paradigm we'll preview in a couple of episodes.

NARRATOR: Now procedures. A procedure performs an action — and crucially does not return a value. Display a report to the screen, save data to a file, update a database record, initialise some settings. The point of a procedure is its effect on the world — what it does — not a value it computes. Display-the-report is a procedure: it puts text on the screen and returns nothing. Save-to-file is a procedure: it writes the file and returns nothing. Listing 1 puts a function and a procedure side by side so the shape of each is obvious — the function ends in a return; the procedure just acts.

NARRATOR: Let's make it concrete with the student grade calculator, our running example, now properly decomposed into subprograms — this is exactly the "identify procedures and functions" skill the exam tests. Read the algorithm and tag each call. Calculate-the-student-average — takes the scores, returns a number — function. Determine-the-letter-grade — takes the average, returns a letter — function. Convert-the-grade-to-a-GPA-value — takes the letter, returns a number — function. Display-the-student-report — takes the details, puts them on screen, returns nothing — procedure. Save-the-results-to-a-file — writes the file, returns nothing — procedure. The full labelled breakdown is in Listing 2. The tell is mechanical and reliable: if the algorithm uses the result — assigns it to a variable, or puts it in an expression — it's a function; if it's called on its own line purely for its effect, it's a procedure. "Set average to calculate-the-average of the scores" uses a returned value, so that's a function. "Display the report" stands alone for its effect, so that's a procedure.

QUESTION: Here's one to actually attempt. Pause the player. In the grade calculator, is "calculate the class average" a procedure or a function — and how do you know? Work it out, then play.

NARRATOR: It's a function. You know because it produces a value you want back — the class average — which gets stored and then used, for instance when displaying the summary. The test isn't the name or the size; it's whether a value comes back and gets used. Calculate-the-class-average returns a number, so it's a function. If instead it just printed the average to the screen and returned nothing, it would be a procedure — same words, different category. That distinction is the mark.

NARRATOR: Now parameters — how data gets into a subprogram. Parameters are the inputs a subprogram declares so it can work on different data each time it's called; they're what make a subprogram flexible and reusable. A calculate-circle-area function with a radius parameter works for any radius. And the syllabus wants you to know there are three directions data can flow through a parameter. An "in" parameter is data passed in that the subprogram reads but doesn't change — the normal case, like the radius. An "out" parameter is one the subprogram fills in to send a result back out — useful when a procedure needs to return more than one thing, since it can't use a return value. And an "in-out" parameter is data that comes in, gets modified, and goes back out — like passing in a student record that the subprogram updates in place. The hook: in reads, out writes back, in-out does both. Listing 3 shows all three. One subtlety that earns marks: a function returns a single value through its return; when you genuinely need several values back, that's exactly when out parameters earn their place.

NARRATOR: Return values — the results a function sends back — only functions have them. And the reason they matter is how flexibly you can use them. You can assign a return value to a variable. You can drop it straight into an expression — final grade equals the average times zero-point-eight plus the exam times zero-point-two. You can nest calls, feeding one function's return straight into another — determine-the-letter-grade of calculate-the-average of the scores, inner call first. Or output it directly. A procedure can do none of this, because it hands nothing back — and that's the source of the number-one trap on this whole topic.

NARRATOR: Here's the trap, and it's worth slowing down for because it bites real programmers. You write something you think of as a function — say, to compute an average — but inside it you print the result instead of returning it. Now the caller gets nothing back. When they write "set average to your-average-routine of the scores," the average variable comes back empty — in Python, literally the value None — because a routine with no return statement returns nothing. The screen showed the number, so it looks like it worked, but the value is gone and the next calculation breaks. Listing 4 shows this exactly — the print version whose caller receives nothing, next to the correct version that returns the value. The rule to state in an exam: if the caller needs to use the result, the subprogram must return it, not print it. Printing is an action — that's a procedure's job; computing-and-handing-back is a function's job. Don't mix them up. And Listing 5 is the whole grade calculator as runnable code — each function returning its value and the display procedure returning nothing — so you can watch the very distinction execute.

NARRATOR: And tying back to last episode: cohesion applies to every subprogram you write. High cohesion means a subprogram does one well-defined thing — calculate one value, perform one action. The best kind, functional cohesion, is when everything in the subprogram contributes to a single task. The opposite is the do-everything routine from last episode — validate and calculate and charge and ship and email, all in one. The fix is the same: split it into focused subprograms, each with one job and a clear name. A function should compute one thing; a procedure should perform one logical action. If you can't name it in a short verb phrase — calculate-the-average, save-the-record, validate-the-email — it's doing too much.

NARRATOR: Consolidate — takeaways, phrased the way you'd write them. One: a function returns a value; a procedure performs an action and returns nothing — function returns, procedure performs. Two: identify which is which by whether the result is returned and used — used result means function; called for effect alone means procedure. Three: parameters pass data in three directions — in reads, out writes back, in-out does both; a function returns one value, so multiple results come back via out parameters. Four: only functions have return values, and they're flexible — assign, embed in expressions, nest, or output. Five: the classic trap is printing inside a function instead of returning — the caller gets nothing; if the result is needed, return it. And every subprogram should have high cohesion — one job, one name.

NARRATOR: Now the exam-style questions. Pen down, and when I say pause, attempt it before the model answer.

QUESTION: Question one, the classic — three marks. Distinguish between a procedure and a function.

NARRATOR: A function is a subprogram that calculates and returns a single value to the code that called it, so it can be used in an assignment or expression. A procedure is a subprogram that performs an action — such as displaying output or saving a file — and does not return a value. The distinguishing point is the return: a function returns a value and is used for its result; a procedure performs an action and is used for its effect. Three marks: one for what a function is and does, one for what a procedure is and does, and one for the explicit contrast — the returned value. Lead with "function returns, procedure performs" and you've framed all three.

QUESTION: Question two. In a grade system there are these subprograms: calculate-the-average, save-the-grades-to-a-file, validate-a-score, and display-the-transcript. Identify each as a procedure or a function and justify. Pause the player, write your answer, then play.

NARRATOR: Calculate-the-average is a function — it computes and returns a number. Validate-a-score is a function — it returns true or false. Save-the-grades-to-a-file is a procedure — it performs an action, writing the file, and returns nothing. Display-the-transcript is a procedure — it performs an action, showing output, and returns nothing. The justification, every time, is the same test: does it return a value you use? Functions yes, procedures no. The mark is in giving that reason, not just the label.

QUESTION: Question three. Explain what a parameter is, and describe the difference between an "in" parameter and an "out" parameter.

NARRATOR: A parameter is an input declared by a subprogram so it can operate on different data each time it's called, making the subprogram flexible and reusable. An "in" parameter passes data into the subprogram that it reads but does not change — the typical case. An "out" parameter is one the subprogram writes to in order to pass a result back to the caller, which is how a procedure can return information despite having no return value. The mark-earning contrast: in carries data inward and is read-only to the caller's value; out carries a result back outward.

QUESTION: Question four. A student writes a subprogram to calculate a discounted price, but inside it they print the price rather than returning it, then try to use the result in a later calculation. Explain what goes wrong and how to fix it.

NARRATOR: The subprogram prints the value but does not return it, so it behaves like a procedure, not a function — the caller receives no value, in Python the special value None. When the student then uses that result in a later calculation, the calculation fails or produces a wrong answer, even though the price appeared correctly on screen. The fix is to return the value instead of printing it, so the caller can assign and reuse it; printing is a separate action that belongs to a procedure if display is also wanted. The phrasing that scores: "a function must return its result for the caller to use; printing produces output but returns nothing."

QUESTION: Question five. Explain why functions are ideally written to be pure — with no side effects — and give one benefit.

NARRATOR: A pure function depends only on its parameters and produces no side effects — it doesn't modify external state or perform actions like printing or writing files; given the same inputs it always returns the same output. This is ideal because it makes the function predictable and self-contained. One benefit: it's easy to test, since you only need to check inputs against outputs with no hidden state to set up — and a second, if you want it, is safe reuse, because calling it can't accidentally change anything elsewhere. The marker is looking for "same input, same output, no side effects" plus a concrete benefit like testability.

NARRATOR: That's the lesson. Two kinds of subprogram — function returns a value, procedure performs an action — identified by whether a result comes back and gets used. Parameters carry data in, out, or both; only functions return; keep each subprogram cohesive with one clear job; and never print where you mean to return.
