NARRATOR: Two back was code quality and maintainability — making the working skeleton good. The anchor there was that code is read far more often than it's written, so readability is where the value lives. You met the four naming categories — classes in Pascal case, methods and variables in snake case, constants in screaming snake case, a single leading underscore for "internal, don't touch". You met the docstring, which states a method's contract — what it does, its arguments, what it returns, what it raises. And the rule for comments: comment the why, the code already shows the what. Then the two headline refactors — extract method, and replace a magic number with a named constant. And the gold list, the maintainability checklist: name it, document it, size it, structure it. Four groups, one feature from each gives you four distinct marks.

NARRATOR: And then last episode — and this is the one we're building straight on top of — was testing. Specifically, testing LEVELS. The headline was three levels, defined by SCOPE, by how much of the system you put under test at once. And the mnemonic was U-S-S — unit, subsystem, system. A UNIT test takes the smallest testable part, one method or one class, in ISOLATION. The key word is isolation. A SUBSYSTEM test — and the exam-preferred name for this is INTEGRATION testing — takes a group of related classes working together and checks that their interfaces line up, that data flows across the boundary, that the objects stay consistent. And a SYSTEM test takes the complete integrated application, end to end, against a realistic user workflow. The clean line between the levels was: count the classes under test. One class isolated is a unit test. Several cooperating is a subsystem or integration test. The whole app end to end is a system test.

QUESTION: Quick check before we go on — what does the mnemonic FIRST stand for?

NARRATOR: FIRST is the five properties of a good unit test. Fast, so they actually get run. Independent, so no test depends on another or on leftover state. Repeatable, so the same result every time — no dates, no network, no randomness. Self-validating, so the test asserts pass or fail itself, no eyeballing the output. And Timely, written close to the code. And the last big idea from that episode was quality assurance — QA — which is broader than testing. Testing DETECTS defects; QA is the systematic wrapper around the whole process that BUILDS quality in and PREVENTS them. The four QA practices were review, check, accept, continuously — code review, checklists, acceptance criteria written given-when-then, and a continuous-testing mindset.

NARRATOR: Now — here's the bridge, and I want you to hold onto this sentence for the whole episode, because it is the single thing the exam tests. Last episode was testing LEVELS: how MUCH of the system you test at once. Today is testing STRATEGIES: how much you can SEE INSIDE the code while you test. Those are two completely different axes. Levels is about scope — one class, several, or all of them. Strategies is about visibility — can you see the source code, or are you working blind from the specification? And the three strategies are black box, white box, and grey box. Different axis, and the crucial thing is they COMBINE. You'll see why that matters in a minute, but plant it now: levels and strategies are perpendicular. You can do a black-box unit test, or a white-box integration test. They're not the same list with different words.

NARRATOR: So that's today. The syllabus dot-point — same one as last episode, the next sub-point down — is: "Apply methodologies to test and evaluate code, including black, white and grey box testing." Outcomes SE-11-08, applying language structures to refine code, and SE-11-06, applying tools to develop and evaluate. By the end of this you'll be able to distinguish all three cleanly in a six-marker, name and apply the two black-box techniques the exam asks for by name, define branch coverage in one sentence, and pick the right strategy for a given scenario. Let's go.

NARRATOR: Start with the names, because the names tell you everything. The three strategies are named after how much VISIBILITY you have into the system's internal workings — into the actual source code. Picture a box with the program inside it. Black box: the box is opaque, you cannot see in at all. White box: the box is transparent, you can see every line. Grey box: somewhere in between, you have partial knowledge. That's the whole framing. And here is your first and most important mnemonic, the one you write at the top of the page the second a box-testing question appears: BLACK equals SPEC, WHITE equals CODE, GREY equals BOTH. Black box, you test from the SPECIFICATION. White box, you test from the CODE. Grey box, you use BOTH. Say it again in your head: black is spec, white is code, grey is both. If you can reproduce that one line under exam pressure, you have the spine of every answer in this topic.

NARRATOR: Let's take black box first, properly. Black-box testing means you design your tests purely from the specification — the requirements, the user story, what the thing is SUPPOSED to do — without any knowledge of how the code is written inside. You feed it inputs, you check the outputs against the spec. You genuinely do not care whether it's a tidy little function or a thousand lines of spaghetti; you only care whether, given THIS input, it produces the output the spec promised. Four characteristics worth naming for marks. It's input-output focused — you examine what the system produces for a given input. It's specification-based — the test cases come straight from the requirements. It's implementation-independent — and this is a real strength — the tests stay valid even if someone rewrites the internals completely, because you never depended on the internals. And it takes the USER's perspective, because the user only ever sees inputs and outputs too.

QUESTION: So if black box is just "feed it inputs and check outputs", how do I choose WHICH inputs? There are infinitely many.

NARRATOR: Exactly the right question, and this is where black box stops being vague and starts being a technique with marks attached. You can't test every input — for a function taking a number from zero to a hundred, that's already infinite once you include decimals. So black box uses two disciplined techniques to pick a SMALL set of inputs that catches the most bugs. And these two have names the exam wants you to produce. Technique one: boundary value analysis. Technique two: equivalence partitioning. Your mnemonic for "the two black-box techniques" is B-V-A plus E-P — boundary value analysis and equivalence partitioning. When a question says "name and apply two black-box techniques", that four-marker is asking for exactly these two, named and demonstrated. So let's nail both.

NARRATOR: Equivalence partitioning first, because boundary value analysis builds on it. The idea: divide all the possible inputs into GROUPS — partitions — where every input in a group should be treated the same way by the program. If the spec says scores zero to fifty-nine all get an F, then every score in that range is in one equivalence class — they're EQUIVALENT as far as the behaviour goes. So you don't test all sixty of them; you test ONE representative from the group, say thirty, and trust it stands for the rest. A grade calculator has natural partitions: zero to fifty-nine is the F class, sixty to sixty-nine is D, seventy to seventy-nine is C, eighty to eighty-nine is B, ninety to a hundred is A. Five valid classes. Plus the INVALID classes — below zero, and above a hundred — which the spec says should raise an error. Each of those is its own partition too. So instead of testing a hundred-plus values, you test one from each class — and you've covered every distinct behaviour the spec describes, with about seven tests. That's the principle the exam states as: test a representative value from each group of inputs that should behave similarly.

NARRATOR: Now boundary value analysis, and here is the high-value idea of the whole episode. Bugs don't cluster in the MIDDLE of a range. Nobody writes a bug that mishandles a score of seventy-five. Bugs cluster at the EDGES — at the boundaries between one partition and the next — because that's where the comparisons live, where someone wrote "greater than" when they meant "greater than or equal to", where the off-by-one error hides. So your mnemonic, and write this one down too: BOUNDARIES ARE WHERE BUGS HIDE. Boundary value analysis says: don't just test a representative from each class, test the VALUES RIGHT AT THE EDGE of each class, and the values just on either side of it. For the grade calculator, the A grade starts at ninety. So you test eighty-nine — which must come back B — and ninety — which must come back A. That pair, eighty-nine versus ninety, is the single most valuable test in the whole suite, because that exact spot is where the boundary bug lives.

NARRATOR: Let me make the bug concrete, because this is the classic trap and the exam will hand it to you. Suppose the programmer wrote the A grade condition as "score GREATER THAN ninety" instead of "greater than OR EQUAL TO ninety". Now a score of exactly ninety falls through to B. A pure middle-of-the-range test — ninety-five gives A, eighty-five gives B — passes happily and never notices. The boundary test, ninety expecting A, catches it instantly. That's the off-by-one boundary error, and "eighty-nine versus ninety" is the canonical example. So for the grade calculator, your boundary tests are: fifty-nine versus sixty — the F-to-D edge; sixty-nine versus seventy; seventy-nine versus eighty; eighty-nine versus ninety — the B-to-A edge; and the outer boundaries, zero and a hundred, plus just past them, minus one and a hundred and one, which must raise errors. The full black-box grade-calculator suite is in Listing 1 — boundaries plus a representative from each equivalence class, with the invalid-input cases. Notice the whole thing was designed without ever looking at the code. That IS black box.

NARRATOR: One more black-box example, because the exam likes it on a different shape of input: a password validator. Spec says the password must be eight to twenty characters. Where are the boundaries? Not in the middle — a fourteen-character password tells you nothing interesting. The boundaries are at eight and at twenty. So boundary value analysis says test exactly four values around them: SEVEN characters, which must FAIL — just below the minimum; EIGHT, which must PASS — the minimum itself; TWENTY, which must PASS — the maximum; and TWENTY-ONE, which must FAIL — just over. Seven, eight, twenty, twenty-one. That four-value pattern — one below the edge, the edge, the other edge, one above — is the boundary value analysis fingerprint, and you can apply it to ANY range the exam throws at you. Listing 2 has the password-validator boundary set in full.

QUESTION: Pause the player for this one. The spec for a library fine says: no fine for zero to seven days overdue, then fifty cents a day from eight days on. Name the technique you'd use, and give me the exact pair of values you'd test at that edge. Pause now, work it out, then play.

NARRATOR: Right. The technique is boundary value analysis — you said its name, that's the first mark. And the boundary is between seven days, which is still free, and eight days, which is the first day a fine applies. So the values you test are SEVEN — expecting zero fine — and EIGHT — expecting fifty cents. Seven versus eight. If you also said you'd add a representative from each "rate band" — that's equivalence partitioning, and naming both techniques is exactly the structure the four-marker rewards. The weak answer here just says "test some overdue values and check the fines". The strong answer NAMES boundary value analysis, identifies the seven-to-eight edge specifically, and states the expected output on each side. Hear the difference — the marks are in naming the technique and pinning the exact boundary.

NARRATOR: Now flip the box over. White-box testing. White box means you design your tests by looking AT THE CODE — the actual internal structure — and making sure your tests exercise all of it. Black box asked "does it meet the spec?". White box asks "have I actually run every part of this code?". You're not testing against a description anymore; you're testing against the implementation itself. The characteristics, for marks: it's code-structure focused — tests built from the real implementation; it aims for path coverage — making sure every route through the code gets executed; condition coverage — every logical condition gets tested both ways; and statement coverage — every single line of code gets run at least once. The big advantage of white box over black box — and this is a clean exam point — is that it can find code that NO black-box test would ever reach: untested code paths, and dead code that can never execute at all. Black box can't see those, because black box can't see the code.

NARRATOR: The word the exam centres on here is COVERAGE, and there are three flavours, in increasing strength. Statement coverage: have I executed every LINE of code at least once? Weakest, but a real start. Branch coverage: have I taken every BRANCH of every decision — every if going both true and false, every path out of an elif chain? Stronger, because a line can be covered while a branch is missed. And path coverage: have I exercised every distinct route THROUGH the code, every combination of branches end to end? Strongest, and usually impractical for anything complex because the number of paths explodes. The one the exam asks you to define is branch coverage, so memorise this sentence: branch coverage means every branch of every decision in the code has been executed — every condition tested both true AND false. That's your one-line answer, and it's a whole mark.

QUESTION: Why isn't statement coverage enough? If every line has run, surely I've tested everything?

NARRATOR: Beautiful trap, and the answer is the reason branch coverage exists. Consider an "if" with no "else" — just "if the account is frozen, raise an error", then carry on. You can get full STATEMENT coverage with a single test where the account IS frozen: the if-line runs, the raise-line runs, every statement executed. But you have NEVER run the case where the account is not frozen and the code carries on past the if. You tested the branch going true; you never tested it going false. The "carry on normally" path is completely untested, and that's exactly where a bug could live. Statement coverage said you were done. Branch coverage knows you weren't. That's why branch coverage is the stronger, more honest measure — and it's why the exam picks it.

NARRATOR: Let's work a proper white-box example, the discount calculator, because it shows you how to read code structure and turn it into tests. The spec is simple enough — a discount depends on customer type, order amount, and whether it's the holiday season — but white box means we look at the actual branches. There are three independent decisions stacked up. First decision: customer type. Regular gives zero, premium gives ten percent, V-I-P gives twenty percent, and anything else raises an error — that's FOUR branches right there, and you must hit all four, including the error one. Second decision: order amount. Over a thousand adds ten percent, over five hundred adds five percent, otherwise nothing — three branches. Third decision: holiday season, on or off — two branches. And then — this is the one students miss — there's a final guard at the bottom: if the total discount comes out above thirty percent, CAP it at thirty percent.

NARRATOR: That cap is the trap, and I want to dwell on it because it's the white-box version of the boundary bug. The cap is a branch. It's an "if the discount exceeds the maximum, clamp it" branch. And it only fires in ONE situation — when all the other discounts stack high enough to push past the limit. If your tests only ever check ordinary combinations — a premium customer with a medium order — the discount never gets near thirty percent, the cap branch NEVER executes, and you have a hole in your coverage you didn't even notice. To cover the cap you have to deliberately construct the worst case: the highest customer tier, a huge order, the holiday bonus, all at once, enough to blow past thirty percent — and then assert the result is exactly thirty, not the raw sum. Forgetting that the cap is a branch you must reach is THE classic white-box coverage miss, and the exam plants it on purpose. The mnemonic to carry: every IF is a branch, and a branch you never trigger is a branch you never tested. The full discount-calculator white-box suite, exercising every branch including the cap, is in Listing 3. And if you want them as exam-ready pseudocode, Listing 5 sketches how to design boundary tests for a range, and Listing 6 shows a branch-coverage check on a single decision.

NARRATOR: Notice the contrast with black box. Black box looked at the GRADE calculator's specification and built tests from the letter-grade ranges. White box looked at the DISCOUNT calculator's actual code and built tests from its branches. Same activity — running tests — but the test cases came from completely different places. Black is spec, white is code. And here's the deeper point: they catch different bugs. White box guarantees you ran every line, but it can't tell you a line is MISSING — if the spec required a senior-citizen discount and the programmer forgot to write it, there's no code for that case, so no branch, so white box never looks for it. Black box, working from the spec, would notice the missing behaviour immediately. So white box catches "the code does the wrong thing on this path", and black box catches "the code is missing a behaviour the spec required". Neither finds the other's bugs. That's already the headline of today: you need both.

NARRATOR: Which brings us to grey box — the in-between. Grey-box testing means you have PARTIAL knowledge of the internals. Not the full source like white box, not total blindness like black box — you know SOMETHING about how the system is built, and you use that knowledge to aim your tests at the risky spots. The characteristics for marks: limited internal knowledge — some understanding of the structure without full code access; strategic, risk-based test design — you use what you know to target the areas most likely to break; and it's heavily associated with INTEGRATION and SYSTEM testing, and with SECURITY testing. That last connection is the key to grey box: when you know a system uses, say, password hashing or a session timeout or rate limiting, you can design a test that specifically PROBES that mechanism — even though you can't see the code that implements it.

NARRATOR: The canonical grey-box example is a user-authentication system, and it's perfect because security is exactly where partial knowledge pays off. You don't have the source. But you KNOW, from the design, three things about how it's built. One: passwords are HASHED, not stored in plaintext. Two: sessions have a TIMEOUT. Three: there's RATE LIMITING after repeated failed logins. Each of those bits of internal knowledge lets you write a targeted test. For the hashing: create a user with a password, then peek at the stored data through whatever limited access you have, and assert that the stored value does NOT equal the original password — because if it does, it wasn't hashed, and that's a catastrophic security bug. You couldn't have written that test as pure black box, because the spec might just say "users can log in" — it doesn't say "go check the storage isn't plaintext". Your grey-box knowledge that hashing is USED is what tells you to look there.

NARRATOR: The session timeout test uses the same trick. You know sessions expire, so you log in, confirm the session is valid, then advance the clock past the timeout — and assert the session is now invalid. The rate-limiting test: you know repeated failures trigger a lockout, so you fire off a run of wrong passwords, then try the CORRECT password and assert it's still blocked — because the lockout should kick in regardless — and then advance the clock past the cooldown and assert it works again. Every one of those tests was AIMED by knowing the mechanism existed. That's grey box: spec-level inputs and outputs, but white-box-flavoured TARGETING. Black is spec, white is code, grey is both — and the auth system is the cleanest "both" you'll see. The full grey-box auth suite — hashing, session timeout, rate limiting — is in Listing 4.

QUESTION: When would I actually CHOOSE grey box over the other two? Give me the scenario the exam wants.

NARRATOR: The exam's favourite grey-box scenario is INTEGRATION testing of a system where you know the architecture but not every line — especially anything security-sensitive. The model answer phrasing: grey box is most appropriate when testing how components INTEGRATE, with partial knowledge of the internal architecture used to target high-risk areas. Concretely: testing an e-commerce checkout where you KNOW it uses database transactions and a particular payment-security mechanism, so you design tests that probe whether a payment failure correctly rolls back the inventory, and whether the security mechanism behaves. You're not testing one method in isolation — that'd be a unit, and probably white box. You're testing the integration with architectural awareness. If a scenario gives you "you know the system uses X internally and you want to test how the pieces work together", the answer is grey box. That's the tell.

NARRATOR: Now — the single most important thing in this entire episode, and the line the top-band answer always contains. NO ONE STRATEGY IS ENOUGH. You COMBINE all three. Black box checks the system meets the user's requirements but is blind to the code, so it misses untested paths and dead code. White box guarantees every line and branch runs but is blind to the spec, so it misses requirements that were never implemented at all. Grey box targets the risky integration and security spots but isn't a substitute for thorough coverage of either kind. Each sees what the others can't. So real-world testing layers them: black box for "does it meet the spec", white box for "is every path correct", grey box for "are the high-risk integration and security mechanisms sound". Thinking one strategy suffices is THE marquee trap of this dot-point — exactly the same shape as "OOP isn't always better" and "a facade hides, it doesn't remove". The mark is the BALANCED answer: name all three, say what each catches, and conclude that comprehensive testing combines them. Crown one strategy as the winner and you've lost the top band.

NARRATOR: Let me weave this back into the wider syllabus, because it doesn't stand alone. First, straight back to last episode: this is the OTHER AXIS from levels. Levels — unit, subsystem, system — is how much you test at once. Strategies — black, white, grey — is how much you can see while you do it. And they multiply. You can write a black-box UNIT test: test one method purely from its spec. You can write a white-box INTEGRATION test: look at how two classes' code connects and exercise every path across the boundary. You can write a grey-box SYSTEM test: run the whole app end to end while targeting the security mechanisms you know are inside. Three levels times three strategies — they're a grid, not a list. If an exam answer treats "unit testing" and "black-box testing" as the same kind of thing, that's the misunderstanding the question is fishing for. Keep them perpendicular.

NARRATOR: Second link, back to PF11. Remember designing suitable test data — boundary data, path data, faulty and abnormal data? That whole idea is the seed of what we just did. Boundary test data IS boundary value analysis. Faulty and abnormal data IS the invalid-input equivalence classes. Path data IS white-box branch and path coverage. The HSC introduced the test-data vocabulary in Programming Fundamentals and the box strategies are just that vocabulary given a proper home and proper names. And forward, into Year 12: this testing rigour is exactly what the Software Engineering Project — the SEE major project — is marked on. When you write the testing section of that project and you can say "I used boundary value analysis and equivalence partitioning for black-box validation, branch coverage for white-box verification, and grey-box tests for the authentication and payment integration" — that's the language that earns the marks. These strategies are the testing rigour the project assesses.

NARRATOR: And two one-line callbacks to stories you've already heard. Remember Ariane 5 — the rocket that reused the inertial-reference software from Ariane 4, never re-tested it for the new flight profile, hit an overflow and self-destructed about thirty-seven seconds in. That's a white-box and grey-box failure on REUSED code: nobody looked at whether the reused code's internal assumptions still held in the new environment. White and grey box on reused components is precisely what would have caught it. And Therac-25 — the radiation machine where a race condition in hidden state delivered massive overdoses while the screen read normal. That's a grey-box concurrency and timing problem: the kind of defect you only find when you know enough about the internal mechanism — the state, the timing, the concurrency — to aim a test at it. Pure black box would never have hit that race. Those are the cautionary tales; we've told them in full elsewhere, so just file them as "reuse needs white and grey box" and "concurrency needs grey box".

NARRATOR: Let's recap the way you'd write it in an exam. Three test STRATEGIES, named for how much you can see inside the code. Black box: test from the SPECIFICATION, no knowledge of the internals, input-output focused, implementation-independent. Its two techniques are boundary value analysis — test the values right at the edges of each range, because boundaries are where bugs hide — and equivalence partitioning — divide inputs into groups that behave the same and test one representative from each. White box: test from the CODE structure, aiming for coverage — statement coverage runs every line, branch coverage runs every branch both ways, path coverage runs every route. Branch coverage is the one to define. Grey box: PARTIAL internal knowledge, used to target risky areas — risk-based, ideal for integration and security testing. And the headline: none alone is enough — you COMBINE all three for comprehensive testing. The mnemonics to dump on the page: black is spec, white is code, grey is both; the black-box techniques are B-V-A plus E-P; and boundaries are where bugs hide. QUESTION: Question one. Distinguish between black-box, white-box and grey-box testing. Six marks. Pause now, answer it properly, then play.

NARRATOR: Six marks means a real distinction across all three, not three loose definitions. Black-box testing designs test cases from the SPECIFICATION with no knowledge of the internal code — it checks input against expected output, and is implementation-independent. White-box testing designs test cases from the internal CODE structure, aiming to cover every statement, branch and path — it verifies the implementation runs correctly and can find untested or dead code. Grey-box testing uses PARTIAL knowledge of the internals to target high-risk areas, and is commonly used for integration and security testing. The distinction is the level of visibility into the code: none for black, full for white, partial for grey — black is spec, white is code, grey is both. A top answer adds that they're complementary and used together. A weak answer just defines "testing" three times without the spec-versus-code-versus-both axis — that axis is where the marks are.

QUESTION: Question two. Name and apply two black-box testing techniques to a function that accepts an age from zero to one hundred and twenty. Four marks. Pause, then play.

NARRATOR: Two techniques, named and APPLIED — applied is half the marks. Technique one, boundary value analysis: test the values at the edges of the valid range and just outside them — so minus one expecting an error, zero expecting acceptance, one hundred and twenty expecting acceptance, and one hundred and twenty-one expecting an error. Technique two, equivalence partitioning: divide inputs into classes that behave the same — the valid class zero to one hundred and twenty, the invalid-below class, the invalid-above class, and a non-numeric class — and test one representative from each, say sixty for valid. The weak answer names the techniques but doesn't apply them to the actual range; the strong answer gives the specific test values and their expected outcomes. Name plus apply — that's the full four.

QUESTION: Question three. What is branch coverage? Pause, then play.

NARRATOR: Short and exact. Branch coverage is a white-box measure: it means every branch of every decision in the code has been executed — every condition has been tested both true and false. Add the contrast for a fuller mark: it's stronger than statement coverage, because you can run every line while still missing a branch — for instance an "if" with no "else", where the false case is never exercised even though all the statements ran.

QUESTION: Question four. Give a scenario where grey-box testing is the most appropriate strategy, and justify it. Pause, then play.

NARRATOR: A scenario plus a justification. Scenario: integration testing of an e-commerce checkout, where you know the system uses database transactions and a specific payment-security mechanism, but you don't have full source access. Justification: grey box is most appropriate because you can use your partial knowledge of the architecture to TARGET the high-risk areas — for example, designing a test that forces a payment failure and asserts the inventory correctly rolls back, which neither pure black box, lacking that internal knowledge, nor pure white box, focused on individual units, would naturally aim at. The marker wants the partial-knowledge-targets-integration-risk reasoning, not just "it's in between".

QUESTION: Question five. A grade calculator returns A for ninety to one hundred and B for eighty to eighty-nine. A tester only checks scores of eighty-five and ninety-five and reports the code passes. Explain the testing weakness and how to fix it. Pause, then play.

NARRATOR: This is the boundary trap, dressed as a scenario. The weakness: the tester only checked MIDDLE-of-range values and never tested the BOUNDARY between B and A. The most likely bug — an off-by-one error, such as "greater than ninety" written instead of "greater than or equal to ninety", which would wrongly give a score of exactly ninety a B — sits precisely at that boundary and is invisible to mid-range tests. The fix: apply boundary value analysis — test eighty-nine, expecting B, and ninety, expecting A, the pair right at the edge — because boundaries are where bugs hide. A strong answer names boundary value analysis explicitly, identifies the eighty-nine-to-ninety edge, and states the expected output on each side. That's the off-by-one boundary error, and it's the most examinable single idea in this whole topic.
