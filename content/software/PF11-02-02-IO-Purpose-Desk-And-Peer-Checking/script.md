NARRATOR: Let me give you the objectives up front, because hearing the questions first sharpens what sticks. NARRATOR: Here's your memory hook for the analysis itself. When you read an algorithm, three things you determine — I-O-P: Inputs, Outputs, Purpose. What goes in, what comes out, what's the point. I-O-P. Then two ways you check it: desk checking, which is you, alone, at your desk, tracing it by hand; and peer checking, which is a second person with fresh eyes. Desk is solo; peer is social. Let's take them in order.

NARRATOR: First, inputs and outputs. Inputs are the data the algorithm receives to work with — and the exam wants you to know they don't only come from a user typing at a keyboard. Inputs can come from a file, from a sensor, from another part of the program, or be fixed values written into the code itself. Outputs are the results it produces: text on a screen, data saved to a file, a value returned to another part of the program, a signal to a device, or a change made to stored data. So when a question says "determine the inputs and outputs," don't just say "the user types stuff." Name each input, and ideally its type and source. For our running example — the grade calculator from last episode — the inputs are a student name, which is a string, and three scores, which are numbers, all entered by the user. The outputs are a formatted message with the grade, and the average, both displayed to the screen. The full algorithm is in Listing 1 as exam-style pseudocode and Listing 2 as runnable Python. Notice I named four inputs with their types and two outputs with their destination. That specificity is the mark.

NARRATOR: Second, purpose. The purpose is the problem the algorithm is designed to solve, expressed in one clear sentence. The method: read it carefully, look at the inputs and outputs, follow the main logic, then summarise in a single sentence. Here's where weak and strong answers separate, and it's worth hearing the contrast. A weak answer to "state the purpose" says: "It does grades" or "it works out a student's marks." Vague, and it could describe ten different programs. A strong answer says: "The algorithm calculates a student's average from three scores and assigns a corresponding letter grade, then displays both." Hear the difference? The strong version names the inputs at a high level — three scores — the transformation — average then letter grade — and the output. One sentence, but it pins down exactly this algorithm and no other. That's the band-six purpose statement.

QUESTION: Quick one. Why does the exam bother asking for the purpose at all, if I can already read the code?

NARRATOR: Because stating the purpose proves you've understood the algorithm as a whole, not just line by line. It's the difference between reading the notes and hearing the tune. And in a stimulus question, the purpose statement is often the first mark — get it crisp and you set up everything after it. There's also a real-world reason that links straight back to documentation, two episodes ago: the purpose sentence is exactly what a good docstring says, the function's contract in one line. Same skill, different context — surfacing again.

NARRATOR: Now the heart of the lesson: desk checking. Desk checking means manually tracing through an algorithm step by step, using specific input values, to verify it works correctly. The tool you use is a trace table. Here's how you build one. Choose your test inputs, including edge cases. Draw a table with one column per variable the algorithm uses, plus a column for any output. Then work down the algorithm one step at a time, and every time a variable changes, write its new value in a new row. When you reach the end, read the output column — that's what the algorithm produced. Then check it against what you expected.

NARRATOR: Let's actually do one out loud, because this is the examinable skill and you need to hear the rhythm of it. Take the grade calculator, inputs: name is Alice, assignment one is eighty-five, assignment two is ninety-two, final exam is seventy-eight. Step one: read in the name — the name column holds Alice. Steps two, three, four: read the three scores — eighty-five, ninety-two, seventy-eight go into their columns. Step five: calculate the average — eighty-five plus ninety-two plus seventy-eight is two hundred and fifty-five, divided by three is eighty-five point zero. The average column now holds eighty-five point zero. Step six: is the average greater than or equal to ninety? Eighty-five is not. Step seven: greater than or equal to eighty? Yes — so the grade column becomes B, and the rest of the chain is skipped, exactly the first-match-wins behaviour from last episode. Step eight: output the message — "Alice earned grade: B". Step nine: output the average — eighty-five point zero. Done. The completed trace table is in Listing 3 so you can see the shape on the page, but notice you didn't need to see it — I just talked you through every cell. That's the standard you're aiming for: a trace you could narrate.

NARRATOR: Now the single most important rule of desk checking, and the trap that costs the most marks: test more than one path. An algorithm with selection in it has multiple branches, and tracing only the first one proves almost nothing. You need to choose inputs that drive the algorithm down different paths — one that lands an A, one that lands an F, and especially one that sits exactly on a boundary. Which brings us to the boundary value, the highest-value test you can run.

QUESTION: Before I answer the boundary question — here's one to actually attempt. Pause the player. Desk check the grade calculator for three scores that each equal exactly eighty. What average do you get, and what grade — B or C? Work it out, then play.

NARRATOR: Eighty, eighty, eighty. Average is eighty point zero. Now the boundary: is eighty point zero greater than or equal to ninety? No. Greater than or equal to eighty? Yes — because the test is greater than or equal to, eighty itself counts, so the grade is B, not C. This is the classic boundary trap. A score sitting exactly on the cut-off is where off-by-one logic errors hide — if someone had written "greater than eighty" instead of "greater than or equal to eighty," that student would silently drop to a C and nobody would notice until a parent complained. The completed boundary trace is in Listing 4. Remember this term — boundary value — because it comes back hard in a couple of episodes when we design test data properly. The B-P-F trio we'll meet then starts with B for Boundary, and this is why.

NARRATOR: So that's desk checking — you, verifying your own work on paper. The problem is, you wrote it, so you're partly blind to it. You read what you meant, not what you typed. That's where the second kind of checking comes in: peer checking. Peer checking is having another person review your algorithm to catch the errors you can't see. And this connects straight back to the collaboration episode — remember CRAB, the R was Review. Peer checking is the human version of the code review that pull requests formalise. Same instinct: a second pair of eyes before it ships.

NARRATOR: What does peer checking add? Four things, and there's a natural logic to them so you don't need to memorise a list. Fresh eyes spot problems you've gone blind to. A different perspective surfaces edge cases you never thought to test. The simple act of explaining your logic out loud forces you to clarify it — you often find the bug yourself mid-sentence. And the result is a better algorithm through collaboration. The headline phrase markers reward is "fresh eyes" — a reviewer who didn't write it isn't anchored to the author's assumptions. There's a short peer-checking checklist in Listing 5 you can actually use: is the purpose clear, are all inputs identified, do the outputs solve the problem, does the logic flow, are all cases handled, what about edge cases. Notice that checklist is just I-O-P plus logic plus edge cases — the same analysis skills, applied to someone else's work.

QUESTION: So how would the exam want me to distinguish desk checking from peer checking?

NARRATOR: As a "distinguish" or "compare" question, and the mark is in the contrast, not two separate definitions. A strong answer: "Desk checking is the author manually tracing the algorithm themselves using a trace table to verify the logic; peer checking is a different person reviewing the algorithm to catch errors the author has become blind to. Desk checking verifies the trace; peer checking adds an independent perspective." Name who does it, what they do, and what each one catches. Desk is solo and systematic; peer is independent and catches the blind spots. Lead with that contrast and you can't be marked down for just listing.

NARRATOR: Let's consolidate — today's takeaways, phrased the way you'd write them. One: to analyse a written algorithm, determine I-O-P — Inputs, Outputs, Purpose. Name each input with its type and source; state the purpose in one precise sentence that fits this algorithm and no other. Two: desk checking is manually tracing the algorithm with a trace table — one column per variable, one row per change — using specific inputs, then comparing the output to what you expected. Three: always trace more than one path, and always include a boundary value — the input sitting exactly on a cut-off, where off-by-one errors hide. QUESTION: Question five, distinguish — four marks. Distinguish between desk checking and peer checking, and explain why both are used.

NARRATOR: Desk checking is the author manually tracing the algorithm themselves, typically with a trace table, to verify the logic produces the expected outputs. Peer checking is a different person reviewing the algorithm to find errors the author has overlooked. Both are used because they catch different things: desk checking systematically verifies the trace, but the author is partly blind to their own assumptions; peer checking adds independent, fresh eyes that surface edge cases and unclear logic the author missed. Four marks: one each for what desk and peer checking are, and one each for the distinct value of each. The phrase that earns the top mark is "fresh eyes catch the author's blind spots."
