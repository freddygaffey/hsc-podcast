NARRATOR: Let's pick up the thread. Last episode, six-oh-three, we stepped up from the logic inside a method to designing the methods themselves and the program that drives them. The big idea there was that a method's signature is a contract. We coined it as a line worth memorising: signature equals name plus parameters plus return, equals the promise. The name, the inputs you pass, and what you get back — that's the public face of a method, and callers depend on it. Change the body all you like; as long as the promise holds, everything that calls it still works.

NARRATOR: We also said the top-level driving code — the mainline — should orchestrate, not implement. It creates the objects, sends the messages, calls the one-task methods in order, and the actual work lives down in those methods. The line for that was: the mainline reads like a table of contents. You can glance at it and see the whole story — load, process, display — without drowning in detail.

NARRATOR: And the third idea from six-oh-three was the stub. A stub is a temporary placeholder that keeps the real signature but fakes the body — it prints a "to do", or returns a dummy value of the right type. The mnemonic was: stub first, fill later. You stub every method, get the whole skeleton running on placeholders, and then fill in real logic one method at a time. The payoff students always drop in the exam is that because each stub has the real signature, the methods connect — so you can test the integration between them before any of the real logic exists.

NARRATOR: Go back one more, to six-oh-two. That's where we drilled method cohesion. The line was: single responsibility principle — one method, one job, under about twenty lines. One method should do one logical thing. When a method tries to do five things, you pull each responsibility out into its own focused helper, and the original shrinks into a short coordinator.

QUESTION: Hang on — if six-oh-three already gave us clean methods and a clean mainline, what's left? Haven't we already got good code?

NARRATOR: That's exactly the right question, and it's today's whole topic. Everything so far has made code that *works* and is *structured* well. But there's a second audience for your code that we've barely talked about: a human being. Usually that human is future-you, six months from now, opening this file with no memory of what you were thinking. You've designed clean methods and clean mainlines — now you write them so a person can read, trust, and change them. That's code quality and maintainability.

NARRATOR: Here's the one sentence to anchor the whole episode on, and it's straight out of the syllabus framing: code is read far more often than it is written. You write a line once. It gets read — by you, by your teammates, by the marker, by whoever maintains it next year — dozens of times. So the economics are lopsided. A few extra seconds making a line readable saves minutes, every single time someone reads it after. Professional engineers spend far more of their day reading and modifying existing code than writing fresh code. Maintainability isn't a nicety bolted on at the end; it's where most of the cost of software actually lives.

One: name the conventions for classes, methods, variables and constants, and say them correctly. Two: write a proper docstring and explain why a comment should say *why*, not *what*. Three: spot a method that's too long or doing too much. Four: apply the two headline refactors — extract method, and replace a magic number with a named constant. And five: rattle off a checklist of what makes code maintainable, plus explain how version control and backups support maintenance. That last one is the gold-plated four-marker, so we'll come back to it hard.

NARRATOR: Now, a heads-up about how I'm going to talk for the next forty minutes. The official names of the naming conventions are written as code — they're literally styles of writing identifiers. I'm not going to spell them out letter by letter, because at five-times speed that's gibberish. So I'll say them as their spoken names, and the actual written forms are all sitting in the supplementary listings for you to read. When I say a name "in Pascal case", picture each word capitalised and the words run together with no spaces. When I say "snake case", picture all lowercase with underscores between the words. When I say "upper snake case", sometimes called "screaming snake case", picture all capitals with underscores between the words. Keep those three pictures in your head; we'll use them constantly.

NARRATOR: Let's start with naming, because it's the cheapest, highest-return thing you can do. Good names make code self-documenting — the code explains itself without you having to write a paragraph next to it. Listing one in the supplementary materials has a before-and-after pair, and it's the single most exam-relevant thing in this episode, because "rewrite this code with meaningful names" is a recurring question. In the "before", there's a class with a one-letter name, a constructor that takes three single-letter parameters, and a method called "calc" that takes its own single-letter inputs. You genuinely cannot tell what any of it does. It works perfectly — it's just unreadable.

NARRATOR: The "after" in listing one is the same code, identical behaviour, with real names. The class becomes a bank account, named in Pascal case — picture the two words "bank" and "account" each capitalised and run together. The cryptic "calc" method becomes "calculate net change", written in snake case — all lowercase, words joined by underscores — and now the name itself tells you it returns the difference between the current and opening balance. The single-letter parameters become "account holder", "opening balance", "current balance". Nothing about how the program runs changed. Everything about how a human reads it changed. That contrast — works-but-cryptic versus works-and-clear — is the heart of the marks.

QUESTION: So what are the actual conventions? Which case goes where?

NARRATOR: Four rules, and Python has a standard for each — this is part of the style guide called PEP 8, which you can name in an answer. Classes are written in Pascal case: each word capitalised, run together. A student record class, a library book class — capital, capital, joined up. Methods and variables are written in snake case: all lowercase, underscores between words. "Calculate total", "student name" — lowercase, joined by underscores. Constants — values that never change while the program runs — are written in upper snake case: all capitals, underscores between words. A maximum number of login attempts, a default timeout. And finally, a single leading underscore on a name is a signal: it means "this is internal — don't touch it from outside". We met that in encapsulation back in five-oh-two: the underscore is a polite request, not a locked door. Python won't stop you, but the convention says hands off.

NARRATOR: Now you need a memory hook for which case goes where, because it's exactly the kind of "match the convention" question they put in a multiple-choice. Here's the structure: the more permanent and shouty a thing is, the louder its name. A constant never, ever changes — so it gets SHOUTED in all capitals. A class is a big structural thing — a blueprint — so it gets the dignified capitals-on-every-word treatment, Pascal case. A method or variable is everyday, working machinery — so it's quiet, all lowercase. Loudest for the thing that's set in stone, quietest for the everyday stuff. If you remember "shout the constants, capitalise the classes, lowercase the rest", you've got it.

NARRATOR: Let me flag a trap straight away, because the multiple-choice loves it. Given a class that manages student enrolment, which name is right? People reach for the all-lowercase-with-underscores version, or worse, all-capitals. Wrong. A class is Pascal case — every word capitalised, run together. The all-capitals version would signal a constant, which a class is not. Get the *category* right — is this a class, a method, a variable, or a constant? — and the case follows automatically.

NARRATOR: Right — naming done. The next pillar is documentation, and there are two separate things people muddle: docstrings and comments. They are not the same and they have different jobs. Let's do docstrings first.

NARRATOR: A docstring is structured documentation attached to a class or a method. We touched it in five-oh-seven as the human-readable interface contract. Its job is to state the contract in plain language: what this thing does, what arguments it takes, what it returns, and what it raises — what exceptions it throws when something's wrong. Listing two in the supplementary materials is a full docstring template, and I want you to memorise its shape, because "write a method with a proper docstring" is a code question and the markers want all the sections.

NARRATOR: The shape is: a one-line summary of what the method does, then an "arguments" section listing each parameter with its type and a short description, then a "returns" section saying what comes back and its type, then a "raises" section listing each exception the method can throw and the condition that triggers it. What it does, its arguments, what it returns, what it raises. Four parts. A nice memory hook is the question word "what" four times: what it does, what goes in, what comes out, what can go wrong. If your docstring answers those four "whats", a teammate can use your method correctly without ever reading the body — which is the entire point. The body is hidden behind the contract, exactly like the signature-is-a-promise idea from last episode.

QUESTION: That's a lot of typing for every method. Is a docstring really worth it on a tiny one?

NARRATOR: Fair pushback, and the honest answer is: not always. A trivial one-liner with an obvious name doesn't need a four-section essay. But every class should have a docstring saying what it represents, and every *public* method — every method other code calls — should have the full treatment. Internal helper methods can be lighter. The checklist at the end makes this distinction. Don't mechanically wallpaper every two-line method with a giant docstring; that's the documentation version of the over-extraction trap from six-oh-two. Document the contract that outsiders depend on.

NARRATOR: Now comments — and this is where I want the single most important documentation lesson to land, because it's worth marks and it's a question in its own right. The rule is: comment the *why*, not the *what*. The code already shows the *what*. Let me give you that as the mnemonic, said straight: comment the why — the code already shows the what.

NARRATOR: Here's the weak-versus-strong contrast, and it's in listing three. A weak comment sits next to a line and just restates it in English. Next to a line that adds one to a counter, the comment says "add one to the counter". Next to a line that checks whether the balance is greater than the amount, the comment says "check if balance is greater than amount". That comment is pure noise. It tells a competent reader nothing the code didn't already say, and worse — when someone changes the code and forgets the comment, the comment becomes a *lie*. A stale comment that contradicts the code is worse than no comment at all.

NARRATOR: A strong comment explains something the code *can't* say for itself. Listing three has the good version: next to a compound-interest calculation, instead of "multiply principal by rate", the comment names the actual formula and what each symbol means — principal, rate, number of compounds per year, time. Or next to a balance check, instead of restating the arithmetic, the comment says "business rule: a minimum balance of ten dollars must be maintained". That's the *why*. Why is this number here? Why this rule? Where did it come from? The code shows the mechanism; the comment supplies the *reason and the context* that no amount of reading the code would reveal. A business rule, a tricky algorithm's source, a non-obvious workaround — those are what comments are for.

QUESTION: Quick exam-style one. Which comment is more valuable for maintainability — one that says "add one to counter", or one that says "students must maintain a minimum grade-point average of two-point-zero to stay enrolled"? Pause the player, decide which and why, then come back.

NARRATOR: The second one, easily, and here's the marking logic to write down. The first comment restates the code — it's redundant, it adds no information, and it can go stale. The second documents a business rule — a piece of *why* that lives nowhere in the code itself. Six months from now, a maintainer who reads "minimum grade-point average of two-point-zero to stay enrolled" understands the *purpose* of the check and can change it safely. That's the mark: comments earn their place when they capture intent the code cannot.

NARRATOR: Okay. Naming, docstrings, comments — that's readability. Now the structural side of maintainability, and this is where the syllabus's two named refactoring patterns live. A refactor, remember from five-oh-six and six-oh-two, is improving the structure of code without changing what it does. Behaviour identical, structure better. The two headline refactors for this dot-point are extract method, and replace a magic number with a named constant. The memory hook for the pair is simple: extract method, and name the constant. Two moves. Let's take each.

NARRATOR: Extract method first — and you already know this one, because it's the cohesion fix from six-oh-two seen from the maintainability angle. The problem is the long method: a method that's grown to do many things. Long methods are hard to understand, hard to test, hard to change without breaking something, and impossible to reuse, because the one bit you want is welded to everything else. Listing four is the centrepiece: an order-processing method that validates the customer, then totals up the items, then applies a discount, then calculates tax, then processes the payment — all jammed into one long body. It works. It's a nightmare to maintain.

NARRATOR: The extract-method refactor pulls each distinct task out into its own focused, well-named method, and the original becomes a short coordinator that just calls them in order. Validate customer info — its own method. Calculate the subtotal — its own method. Calculate the discount, calculate the tax, process the payment — each its own method. The "after" in listing four reads like a list of steps: validate, total, discount, tax, pay. That's the table-of-contents quality from the mainline idea, now applied inside a single method. And notice the names of the extracted helpers carry a single leading underscore — they're internal machinery, signalled as "not part of the public interface", exactly the convention we set up earlier.

QUESTION: How do I know *when* a method is too long? Is there a line count?

NARRATOR: Good question, and the trap is thinking the answer is a number. It isn't really about lines — twenty lines is a rough guide, not a law. The real test, and this is straight from the quiz framing, is: can you identify distinct logical tasks inside the method? If a method does one thing, it can be long and still be fine. If a method does five clearly separable things — validate, then total, then tax, then pay — that's the signal to extract, no matter the line count. So when an exam asks "what indicates a method needs refactoring?", the strong answer is not "it has more than twenty lines" and definitely not "it contains a loop". The strong answer is: it performs multiple distinct tasks and is hard to understand as a single unit. Distinct tasks, not raw length.

NARRATOR: Second refactor: replace a magic number with a named constant. A magic number is a bare literal value sitting in your code with no explanation — a seven, a thirty, a nought-point-five — where a human reading it has no idea what it means or why it's that value. Listing five is the worked example, and it's a library late-fee calculator, which is perfect because it's full of these. In the "before" version, the fee logic checks "if days late is seven or fewer", then "if days late is thirty or fewer", and multiplies by nought-point-five, then by one, then by two. Seven? Thirty? Nought-point-five? You're left guessing. Worse — the seven appears in two different places, so if the grace period changes, you have to find and update every copy, and miss one and you've got a bug.

NARRATOR: The "after" in listing five replaces every bare number with a named constant, written in upper snake case — all capitals, underscores between words, because a constant shouts. The seven becomes a constant called "grace period days" — picture it all in capitals, "grace", "period", "days", joined by underscores. The nought-point-five becomes a "grace period fee per day" constant. The thirty becomes a "standard period days" constant. Now read the same logic: "if days late is at most the grace period days, charge days late times the grace period fee per day". It reads like English. Three wins, and these are your three marks for "why replace a magic number with a named constant?".

NARRATOR: Here are those three, because this is a three-marker and you want all three. One — readability: the name explains what the number *means*, so the code documents itself. Two — maintainability: the value is defined in exactly one place, so to change the loan period you edit one line and every use updates, instead of hunting through the file. Three — correctness and consistency: because there's a single source of truth, you can't accidentally update the number in some places and forget others. Meaning, one place to change, no inconsistency. The mnemonic to carry is the one we coined: no magic numbers — name them. If you see a bare literal that isn't obviously zero or one, give it a name.

NARRATOR: Notice what just happened, by the way — naming that fee constant didn't only make it readable, it also turned that nought-point-five into something a business person could find and adjust. That's the maintainability payoff made concrete. And it ties straight back to encapsulation: the constant lives on the class, a single guarded source of truth, exactly the funnel-everything-through-one-place instinct from five-oh-two.

NARRATOR: Let me give you the checklist now, because "list four features of maintainable code" is the most reliable mark in this whole topic, and a checklist is gold for it. Listing six lays the full thing out; I'll give you the spoken version grouped into four areas so it's memorable. The four areas are: naming, documentation, method design, and structure. Within naming: descriptive names following the conventions — Pascal case classes, snake case methods and variables, upper snake case constants — and no cryptic abbreviations. Within documentation: every class and public method has a docstring, and comments explain why, not what. Within method design: each method has a single responsibility, stays reasonably short, takes a sensible number of parameters — around four or fewer is the guide — and handles its errors clearly. Within structure: no magic numbers, repeated code extracted into methods, complex conditionals simplified.

NARRATOR: For the memory hook, group the four areas as: Name it, Document it, Size it, Structure it. Four verbs — name, document, size, structure. If a four-marker asks for four features of maintainable code, you dump one from each: meaningful names following conventions; docstrings and why-comments; short single-responsibility methods; and no magic numbers. One from each bucket, and you've got four clean, distinct marks instead of four versions of the same point. That last bit matters — markers want four *different* features, not "good names" said four ways.

QUESTION: That's all about the code itself. But the dot-point also mentions version control and regular backup. Where do those fit into maintainability?

NARRATOR: This is the part people under-prepare, and it's worth real marks because the syllabus lists it explicitly. The dot-point is: implement and modify object-oriented programming code, including ease of maintenance, version control, and regular backup. Readable code is *one* half of ease of maintenance — the half about a single file being understandable. Version control and backup are the *other* half — the half about safely changing code over time, across a whole project, without losing work. Let me make each one's contribution to maintenance precise, because "explain how version control and backups support maintenance" is a question and it wants the *how*, not just a definition.

NARRATOR: Version control — Git, which we set up properly in five-oh-seven — supports maintenance in a few specific ways. First, history: every change is a commit with a message saying who changed what, when, and why. When you're maintaining code and you hit a line that makes no sense, you can look up the commit that introduced it and read the reasoning — the history is documentation that the code itself can't hold. Second, safe change: because every previous state is saved, you can make a risky modification knowing you can roll back to a known-good version if it breaks. Maintenance is *editing existing code*, which is inherently risky; version control is the safety net that makes editing safe. Third, branches: you can maintain or experiment on a separate branch without disturbing the working code everyone else relies on. History, rollback, isolation — that's how version control underpins maintainability. Notice it's the same idea as the underscore and the constant: a single, trustworthy source of truth you can reason about.

NARRATOR: Regular backup is the simpler one, but don't skip it — it's named in the dot-point, so it's named in the answer. A backup is a separate, safe copy of your work, taken on a regular schedule, so that a hardware failure, an accidental deletion, ransomware, or a corrupted file doesn't wipe out the project. Version control already gives you a lot of this — pushing to a remote repository like GitHub *is* an off-machine copy of every version — but a true backup strategy is broader: it covers the whole project, including things outside the repository, and it's stored somewhere independent. The maintenance angle: software lives for years and gets modified continuously; backups guarantee that no single accident throws away that accumulated work and history. The classic line markers like is the three-copies rule — three copies, on two different kinds of media, with one kept off-site — and dropping that in shows you actually know backup practice, not just the word.

NARRATOR: So when the question says "explain how version control and backups support maintenance", the strong answer hits both with their *mechanism*. Version control lets you track every change, understand why code is the way it is, and safely roll back a bad modification — so maintaining code is low-risk. Regular backups protect the whole project and its history against loss — so years of accumulated work and changes can't vanish to one accident. Mechanism, not just name. A weak answer says "they save your code". A strong answer says "version control gives a reversible, documented history so changes are safe and traceable, and backups protect the project against catastrophic loss" — hear the difference?

NARRATOR: One more thing the dot-points ask, and I'm only going to *introduce* it because its real home is six-oh-seven: explain code optimisation in software engineering. At this stage, all you need is the headline. Code optimisation means improving code so it runs more efficiently — faster, or using less memory — *without* changing what it produces. Same outputs, fewer resources. The crucial discipline, which we'll do properly next time, is "measure first, optimise second": you profile to find where the program is actually slow before you touch anything, because programmer intuition about what's slow is usually wrong. And there's a deliberate tension with today's topic worth flagging now: the most readable version of some code and the fastest version are sometimes not the same, and squeezing out speed can cost you clarity. So optimisation is a *trade-off* against maintainability — which is exactly why it comes right after this episode. We measure that trade-off in six-oh-seven using four dimensions: correctness, clarity, performance, maintainability. For now, one sentence: optimisation makes code more efficient without changing its behaviour, and you measure before you do it. Don't write more than that here; the depth is next episode.

NARRATOR: Let me also draw the lines outward, because that's how this sticks. Backward: this is the documentation and code-style discipline you met in your earlier programming work, now raised to the object-oriented level — naming methods and classes, docstrings on a class's interface. Sideways within this module: the single-responsibility, short-method idea is straight from six-oh-two, and the docstring-as-contract is the signature-is-a-promise idea from six-oh-three made human-readable. Forward, two real links. First, into the project work in Year 12 — maintainability and this exact quality checklist are *what the major project is evaluated on*; clean, documented, version-controlled code isn't optional there, it's marked. Second, into secure software in Year 12 — the magic-number-to-named-constant discipline is the same instinct behind not hard-coding configuration and secrets into your source: pull important values out into one named, managed place. A hard-coded password is a magic number with consequences.

NARRATOR: And the forward link to testing, which is the very next episode, six-oh-five: notice that every quality move we made today also makes code *testable*. So maintainability and testability are two sides of one coin — keep that in your pocket for next time.

QUESTION: Question two, three marks. Why should you replace a magic number with a named constant? Pause, give three reasons, then play.

NARRATOR: Three distinct reasons. Two — maintainability: the value is defined in one place, so changing it means editing a single line instead of hunting every occurrence through the file. QUESTION: Question three, three marks. Explain the difference between a docstring and a comment, and give the rule for what a comment should contain. Pause and answer, then play.

NARRATOR: Model answer. A docstring is structured documentation attached to a class or method that states its contract — what it does, its arguments, what it returns, and what it raises — so other code can use it correctly without reading the body. A comment is an inline note inside the code explaining a specific line or block. The rule for comments is: explain *why*, not *what* — the code already shows what it does, so a comment earns its place only when it captures intent the code can't, like a business rule, a formula's source, or the reason for a non-obvious workaround.
