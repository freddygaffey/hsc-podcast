NARRATOR: Start with the workspace, briefly, because you mostly know this. An integrated development environment, an IDE, is a single program that bundles together the things you'd otherwise juggle: a code editor, a file browser showing your project as a tree, an integrated terminal, and a debugger. Visual Studio Code and PyCharm are the common Python choices. The exam-relevant point isn't which one you pick; it's why bundling matters. NARRATOR: Git is a version control system. The plainest way to say what it does: it takes snapshots of your project over time, so you have a complete, labelled history of every change, and you can go back to any snapshot. That alone, an undo button that spans the entire life of a project, would justify it. But it does much more, and the structure is what you need to understand, because the exam can ask you to explain the workflow.

NARRATOR: Here is the model that makes Git click. Your work lives in three places, and Git is the machinery for moving changes between them. Place one is the working tree: the actual files in your folder as they are right now, the ones you're editing. Place two is the staging area, sometimes called the index: a holding pen where you gather exactly the changes you want in your next snapshot. Place three is the repository: the permanent history of committed snapshots, stored in a hidden folder. So the flow is: you edit files in the working tree, you stage the specific changes you want with the git add command, and then you record them permanently into the repository with the git commit command. Edit, stage, record. Three places, two moves.

QUESTION: Why have a staging area in the middle at all? Why not just save everything that changed in one go?

NARRATOR: Because the staging area is what lets you make focused, meaningful snapshots instead of messy ones. Imagine you've been working and you've fixed a bug in one file and also started a half-finished new feature in another. If you committed everything at once, that snapshot would mix a finished fix with broken, incomplete work, and the history becomes useless. The staging area lets you add only the bug-fix file, commit that as one clean snapshot with the message describing just the fix, and leave the half-finished feature out until it's ready. Each commit becomes one logical, complete idea. That selectivity is the entire point, and it's the foundation of the "commit small and often" habit I promised you last episode.

NARRATOR: Let me give you a memory hook for those three places, because "name the stages of the Git workflow" is exactly the kind of thing that turns up. The three places are Working tree, Staging area, Repository, and the three actions are Write it, Stage it, Record it. Remember it as W-S-R: Write, Stage, Record. Working tree, Staging area, Repository. Say it back to yourself once: Write, Stage, Record.

NARRATOR: Now the core commands, said as words since you'll see them written in the listings. You start a repository with git init, which creates that hidden repository folder and begins tracking. You check what's going on with git status, which tells you which files are new and untracked, which are modified, and which are staged and ready. You move changes into the staging area with git add, naming a file or staging everything. You record the staged snapshot with git commit, attaching a message that explains the change. And you read the history with git log, which lists your commits newest first. Init, status, add, commit, log. You don't need an acronym for these, because they aren't a random set to memorise; they're just the workflow in order. You initialise once at the start, then every working session you check status, add what's ready, commit it, and read the log. Walk the workflow and the commands fall out in sequence. That daily loop is ninety percent of version control.

NARRATOR: A word on commit messages, because they earn marks under the "quality of documentation" idea and they matter in real life. A good commit message is written in the imperative mood, as a command: "Add grade validation", not "Added grade validation" and not "stuff". The subject line stays short, and if you need to, you explain what changed and crucially why, not how, because the how is visible in the code itself. The commit history, written well, becomes a searchable narrative of how the project evolved and why each decision was made. That's documentation you get almost for free, and markers reward you for naming it as documentation.

NARRATOR: Let me make all of this concrete with our running example, the Grade Calculator from last episode. I've written the full sequence out in Listing one, and it's worth following along in your head. You make a folder for the project. You run git init to start version control. You create a read-me file describing what the project is and how to run it. You stage just that file with git add, and you commit it with the message "Initial project setup". That's snapshot one: a project with documentation and nothing else. Then you add the actual calculator code, the validate-grade and calculate-average functions from last episode, in a separate file. You stage that, and you commit it with the message "Add grade calculation function". That's snapshot two. Notice what we did: two separate, focused commits, each capturing one complete idea, the setup and then the feature. The history now reads like a clear story, and either change can be understood or undone on its own. That is "commit small and often" in action.

NARRATOR: Now, the two traps. These are the version-control mistakes that lose marks in an exam and cause real pain on real teams, so I'm naming them explicitly. Trap one: the giant commit. This is when you work for hours across ten files, fixing bugs, adding features, renaming things, and then dump it all into a single commit with a message like "updates". That commit is worthless. If a bug appears, you can't tell which of the ten changes caused it, and you can't undo one piece without losing the rest. The fix is the discipline we just practised: small, focused commits, one logical change each. If you can't describe your commit in a short imperative sentence without using the word "and" three times, it's too big.

NARRATOR: Trap two is subtler and a classic exam "gotcha": adding a file to the ignore list after it's already been committed. Let me explain the ignore list first. There's a file called the git-ignore file, a dot-gitignore, where you list patterns for files Git should never track: things like Python's compiled cache folders, virtual environment folders, and editor settings. I've put a minimal Python git-ignore file in Listing two so you can see the typical patterns. You absolutely do not want those in your history; they're generated noise. But here's the trap. The ignore list only stops Git from tracking files it isn't already tracking. If you've already committed a file, adding it to the ignore list does nothing, Git keeps tracking it, because it's already under version control. To actually stop tracking it, you have to remove it from Git's tracking first, while keeping it on disk, using the git remove command with the cached option, and then commit that removal. I've put that exact fix in Listing three. The trap, and the exam answer, is this: ignore rules prevent tracking; they don't undo it. Add files to the ignore list before you ever commit them.

NARRATOR: Here's the answer. The three places are the working tree, the staging area, and the repository. NARRATOR: Feature one is the hosted, shared repository itself: a single authoritative copy in the cloud that an entire team pushes to and pulls from, so everyone's work converges in one place rather than scattering across laptops. Feature three is issue tracking: a built-in system for logging bugs and planning features, so the to-do list lives right next to the code. NARRATOR: Here's your memory hook for those benefits, because "describe two benefits of online code collaboration tools" is a four-mark question that has appeared and will appear again. QUESTION: Question one. "Outline the purpose of the staging area in Git." Three marks. Pause, answer, then play.

NARRATOR: Model answer: the staging area, or index, is an intermediate holding area between the working tree and the repository where a developer assembles exactly the changes they want in the next commit. Its purpose is to allow selective, focused commits: a developer can stage only the changes that form one logical unit of work while leaving unrelated or unfinished changes out, so that each commit in the history represents a single, complete idea. The marker wants the words "selective" or "focused" and the idea that it sits between the working tree and the repository.

QUESTION: Question two. "Describe two benefits of online code collaboration tools." Four marks. Pause, answer, then play.

NARRATOR: Model answer: first, parallel collaboration, multiple developers work simultaneously on separate branches and merge through pull requests without overwriting each other. Second, code review and accountability, pull requests let changes be reviewed and approved before entering the main codebase, while the commit history records who changed what and why. If you wrote CRAB in the margin first, you just pick any two of Collaboration, Review, Accountability, Backup and write the mechanism for each.

QUESTION: Question three. "A student has been committing all their work once a day in a single large commit with the message 'daily update'. Explain two problems this causes and recommend a better practice." Five marks. Pause, plan a full answer, then play.

NARRATOR: Model answer: the first problem is poor traceability, because many unrelated changes are bundled together, it's impossible to tell which change introduced a particular bug, making debugging far harder. The second problem is that the commits can't be selectively undone, reverting the commit to remove one bad change also removes all the good changes made that day, and the vague message "daily update" provides no useful documentation of what actually changed. The recommended practice is to make small, focused commits, one logical change per commit, each with a clear, imperative message describing what changed and why. This produces a readable history, isolates changes for easy debugging and reverting, and documents the project's evolution. A top answer explicitly names "commit small and often".

QUESTION: Question four. "Evaluate the prevalence and use of online code collaboration tools in modern software development." Six marks. This is the hard one, the actual dot-point verb. Pause, plan it, then play.

NARRATOR: Model answer: online code collaboration tools such as GitHub, GitLab and Bitbucket have become the de facto industry standard, used almost universally across both commercial software teams and open-source projects. Their prevalence is justified by the range of core development problems they solve simultaneously: they host a single authoritative repository that enables many developers to work in parallel without conflicts; they build code review directly into the workflow through pull requests, raising quality; they provide a complete, attributable history for accountability and debugging; and they integrate issue tracking and automated testing so that planning, coding and verification live in one place. A further driver of their dominance is the network effect, because the open-source ecosystem and the developer job market are built around these platforms, fluency with them is itself a professional requirement, which reinforces their universal adoption. On balance, their combination of collaboration, quality control, safety and ecosystem lock-in makes them not merely popular but essential infrastructure for modern software engineering. The marks here are for making a clear judgement, "essential infrastructure", not just "popular", and backing it with specific, named reasons.
