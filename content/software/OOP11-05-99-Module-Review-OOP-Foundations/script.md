NARRATOR: Let me do the proper spaced-repetition lap now, lesson by lesson, because some of these we haven't touched in a week and they need a jog. Lesson one: objects and classes. An object bundles data — its attributes, the nouns, its state — together with behaviour — its methods, the verbs, the actions. A class is the blueprint; it's written once and holds no actual data. An instance is a concrete object built from that class, and it holds its own real values. One class, many instances. The classic trap is saying "the bank-account class has a balance of a thousand dollars" — wrong. The class defines that there is a balance attribute; the instance holds the thousand. And calling a method is really message-passing: you send a message to an object, and the object acts on its own data and replies. The five-step dispatch behind that is our first mnemonic — L-B-P-E-R: Lookup the method on the class, Bind the receiver to self, Pass the parameters, Execute, Return. Lookup, Bind, Pass, Execute, Return.

NARRATOR: Lesson two: encapsulation. Two halves, and you need both — bundle the data with the methods that control it, and restrict direct access to that data. Bundling alone just describes an object; the restricting is what makes it encapsulation. We split the world into the public interface — the approved methods outside code is allowed to call, which should stay stable — and the internal state — the data nobody outside should touch directly. The interface is the buttons; the state is the wiring. And the reason we bother is held in our second mnemonic — I-C-F-S: Integrity, Consistency, Flexibility, Security. You encapsulate to protect the object's invariants — the conditions that must always be true, like a balance never going negative — by funnelling every change through a validating method. The trap: thinking a single underscore or a double underscore in Python gives you real privacy. It doesn't. Underscores are a polite request, not a locked door. Name-mangling is clash-avoidance, not security.

NARRATOR: Lesson three completed the four behaviours. Here's the master mnemonic for the whole module, and if you remember one thing from today, remember this one. Have a slice of A-PIE. A-PIE: Abstraction, Polymorphism, Inheritance, Encapsulation. Those are the four behaviours. Encapsulation we just did. Abstraction hides the complexity — you expose only the essentials through a simple interface. The one-liner to keep them apart: encapsulation hides the data, abstraction hides the complexity. Same instinct, different target. Then generalisation and inheritance, which people constantly confuse, and our mnemonic fixes it: generalise to model, inherit to reuse. Generalisation is the modelling act — on the whiteboard you notice that a car and a motorcycle are both vehicles, and you capture the shared idea. Inheritance is the implementation act — in code, a subclass actually reuses the parent's attributes and methods, calling super to run the parent's constructor, and can add or override. And polymorphism: one interface, many behaviours. One loop calls one method name, and each object runs its own version. In Python you don't even need a shared parent — that's duck typing, and the line is: duck typing, if it quacks, it'll do. If the object has the method, it works, whatever class it came from.

NARRATOR: Lesson four was the big step-back: comparing procedural programming with object-oriented. The whole contrast lives in one sentence, and it's worth writing on your exam paper verbatim. Procedural: data and functions live apart. OOP: data walks with its methods. That's it. Every trade-off — organisation, reuse, modularity, how you handle state — falls out of that one sentence. And the marquee trap from that lesson: do not crown OOP the universal winner. Markers penalise "OOP is always better." A simple one-shot tax calculation, a pure factorial, a linear data-cleaning pipeline — those are perfectly good procedural. OOP wins when you've got real entities with state that interact. The tell that you should reach for a class: a function with a giant parameter list. A giant parameter list is procedural crying out for a class — that's data that travels together, which is a class waiting to be born.

NARRATOR: Lesson five: modelling, three diagrams. The mnemonic does all the work — Class equals things, Chart equals jobs, DFD equals data. The class diagram shows the static structure: what classes exist, their attributes and methods, and how they relate. The structure chart shows functional decomposition: one big job broken top-down into a tree of smaller jobs — it's the picture of the top-down thinking you did in programming fundamentals. And the data flow diagram, the DFD, shows where data comes from, what transforms it, and where it ends up. Three high-value facts to keep. One, on a class diagram, a filled diamond means composition, and the hook is: filled diamond equals composition equals the part dies with the whole. Two, the DFD symbols: a process is a circle, an external entity is a closed rectangle, a data store is an open-ended rectangle. Three, and this is the marquee distinguish trap — a DFD is not a flowchart. A DFD shows where the data goes; a flowchart shows what the program does, in order. Data flow versus control flow.

NARRATOR: Lesson six: the design process — how you actually produce those diagrams. The pipeline is R-R-C-I: Requirements, Responsibilities, Collaborations, Implementation. And always say "iterative" — it loops, it's not a waterfall. Requirements split into functional, what it does, versus non-functional, how well it does it — response time, uptime, concurrency are the non-functional tells. Responsibilities use the heuristic nouns become classes, verbs become methods, and then you ask, in CRC style, who should be responsible for this? Each method lives where its data lives — that's encapsulation given a job. Collaborations are just which object sends which message to which — that's message-passing from lesson one, scaled up. And implementation comes last, by which point every method has an obvious home. We also did decomposition — top-down versus bottom-up, most real projects hybrid — and the one named design pattern in the syllabus, the facade. A facade is a tidy front desk over a messy back office. One simple front-of-house class hides a whole messy subsystem behind a clean interface. And the trap that loses marks: a facade hides complexity, it does not remove it. The subsystems still exist and still do all the work.

NARRATOR: And lesson seven closed the chapter: collaboration and version control. The spine sentence is — clear interfaces let teams work apart, then merge. Because each class is a module with a well-defined interface, and that interface is a contract — this is what you call, this is what you pass, this is what you get back — different people can own different classes and build in parallel. Stubs and mocks let you build against an interface before the real class even exists; when the real one lands, it honours the same interface and drops in unchanged — which is just polymorphism again. Then the four named practices, in the syllabus's own order: consistency, code commenting, version control, feedback. Consistency is shared style so you read a teammate's code as fluently as your own. Commenting — comment the why, not the what. Version control is Git: commits, branches, merges, and the rule one idea per commit. And feedback is code review through a pull request, where the hook is: comment the code, not the coder. When two branches change the same lines, you get a merge conflict — not an error, just the tool being careful and asking a human — and you resolve it: Talk, Edit, Strip the markers, Commit.

NARRATOR: Now the integrative story, because a review should anchor all this in something real you'll remember in the exam. This is the Mars Climate Orbiter, and it is the single best illustration of why an interface is a contract — it ties together encapsulation, the facade, and team collaboration in one expensive disaster. In nineteen ninety-eight, NASA launched a spacecraft to Mars to study its climate. It cost about a hundred and twenty-five million dollars. The mission was built by two teams. One team, at Lockheed Martin, wrote the software for the ground system that computed how much force the spacecraft's thrusters had produced. Another team, at NASA's Jet Propulsion Laboratory, wrote the navigation software that took those force figures and worked out where the spacecraft was and how to steer it. Two modules, two teams, exchanging numbers across an interface. Sound familiar? That's exactly the blog-app split from lesson seven — different developers owning different classes, talking through an interface. Listing 6 captures that interface-as-a-contract idea in code — a payment interface with a mock you build against and a real one that drops in unchanged — and the comment in it spells out the units lesson the Mars mission learned the hard way.

NARRATOR: Here's what went wrong. The Lockheed module produced its thruster figures in pound-force seconds — imperial units. The JPL navigation module expected those figures in newton-seconds — metric units. A pound-force is about four and a half newtons, so every number coming across that interface was off by a factor of roughly four and a half. And nobody had written the contract down. The interface — the promise of what gets passed and in what units — was never explicitly specified and agreed. Each team encapsulated its own work beautifully and assumed the other side spoke its units. For nine and a half months the spacecraft flew toward Mars accumulating a tiny, consistent navigation error. When it arrived in September nineteen ninety-nine, it dipped too low into the Martian atmosphere — about fifty-seven kilometres instead of the planned hundred and fifty or so — and it either burned up or skipped off into space. Either way, gone. A hundred and twenty-five million dollars, lost to an unstated interface contract.

NARRATOR: Now connect it to the chapter. This is lesson seven's point made unforgettable: clear interfaces let teams work apart, then merge — but only if the interface is actually specified. The encapsulation was fine; each module guarded its own internals. The problem was the public interface between them carried an unstated assumption — the units — and an interface with a hidden assumption is a time bomb. It's also the facade lesson in reverse: a facade works because the contract between the client and the front desk is clear and stable; here the contract was never agreed, so the two halves couldn't safely merge. And it's why, in lesson seven, we said a method signature and a docstring are the human-readable contract — if the docstring on that force value had said "returns impulse in newton-seconds," the bug is impossible. The whole disaster is one missing line of interface documentation. That's the story to tell in any exam answer about why interfaces and contracts matter in collaborative development. It's vivid, it's true, and it earns the mark.
