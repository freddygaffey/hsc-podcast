NARRATOR: Start with the signature. A method signature is the part of a method that the *outside world* sees and depends on. It's three things: the method's name, its parameters — including, ideally, what types they are — and its return type, or return value. Name, parameters, return. Say it as a memory hook: signature equals name plus parameters plus return, equals the promise. Write that down. Because the key word there is promise. The signature is a *contract*. It's a promise the method makes to every piece of code that calls it: "Call me this way, give me these inputs, and I will give you back this." Everything about *how* the method does its job — the loops, the branching, the helper calls — is hidden behind that promise. The caller doesn't know and doesn't care.

NARRATOR: You've actually met this idea three times already under different names. In the encapsulation episode it was the public interface versus the internal state — the buttons versus the wiring. In the design-process episode it was the facade — the front desk over the back office. And in the collaboration episode it was the interface as a contract that lets a team work apart and merge. A method signature is that same instinct, brought right down to a single method. The signature is the stable front; the body is the hidden internals. You can rewrite the body completely — make it ten times faster, swap the algorithm — and as long as the signature is unchanged, every caller still works. That's the whole point of designing the signature deliberately and first.

NARRATOR: So what makes a *good* signature, the kind a marker rewards? Three properties. First, clear: the purpose is obvious from the name and the parameters alone. A method called "calculate student grade average" tells you exactly what it does and what it returns. A method called "do stuff", or "process", or "method one", tells you nothing — and a vague name is a real marking pitfall, because it signals the method probably does several things. Second, focused: the parameters are exactly what the job needs, no more. If a method takes eight parameters, that's a smell — it's probably doing several jobs, and that data that travels together is begging to be a class, which is the symptom we named back in the procedural-versus-OOP episode. Third, consistent: similar operations follow similar patterns, so once you've learned one method in a class, you can predict the others.

QUESTION: Hang on — give me the quick version. What's the difference between a method's signature and its body, and why does it matter which one I design first?

NARRATOR: Good question. The signature is the name, the parameters and the return — the promise, the part the caller sees. The body is the implementation — the logic that fulfils the promise, the part the caller never sees. It matters which you design first because the signature is the contract every other piece of code depends on. If you nail the signatures first, all the connection points are fixed and agreed, and you can then fill in the bodies one at a time without breaking anything. If you write a body first and *then* discover the signature is wrong, you have to change the contract — and now every caller breaks. So you design the interface first, the insides last. Same order as R-R-C-I: implementation comes at the end.

NARRATOR: There's a famous, expensive illustration of a signature being a contract — and we've told the full story before, so just the one line here. The Mars Climate Orbiter: two teams' software exchanged values across an interface, one team working in pound-force-seconds, the other expecting newton-seconds, and nobody had written the units into the contract. The craft was lost. The lesson for us today is brutally simple: the interface contract that nobody writes down is the one that destroys the project. A method signature is you writing the contract down. The name says what it does, the parameters say what to pass, the return says what you get — and if the textbook had said "this returns newton-seconds" in the signature, there'd have been a spacecraft at Mars.

NARRATOR: Now the second piece: the mainline. The mainline is the top-level code that drives the program — in a procedural sense it's the main routine, and in an object-oriented program it's the orchestrating code, the part that creates the objects and sends them messages to actually get the work done. The syllabus phrase is "a clear and uncluttered mainline". And here's the rule that earns the mark: the mainline should *orchestrate*, not *implement*. It calls one-task subroutines in order; it does not do the work itself. The work lives down in the focused methods. The mainline just conducts.

NARRATOR: The memory hook — and it's the same one we coined last episode for the coordinator method — is: the mainline reads like a table of contents. Read it top to bottom and you should see the *shape* of the program: load the data, then process it, then display the results. Each of those is one call to one well-named method. You should be able to understand what the program does without reading a single line of the detail, exactly the way you understand a book from its contents page without reading the chapters. That's an uncluttered mainline, and Listing 2 in the supplementary materials is exactly that — a mainline whose three lines say "add the items, review the cart, finish the order", each one a single call. A *cluttered* mainline is the opposite: it's got the file-parsing logic and the validation loops and the printing all tangled together at the top level, so you have to read forty lines to work out that it loads, processes and displays. Listing 3 is that weak version, side by side for contrast, with the parsing loop and the validation and the pricing all jammed in at the top. If your mainline has loops and nested ifs doing real work, it's cluttered — extract that work into named methods and replace it with a call, the way Listing 2 does. And if you're rehearsing the exam pseudocode form, Listing 8 writes that same uncluttered mainline in NESA style — a main routine that just calls add-demo-items, review-cart and finish-order.

QUESTION: So is the uncluttered mainline just the coordinator method from last episode wearing a different hat?

NARRATOR: Essentially, yes — and noticing that connection is worth a mark, because it shows you see the single principle underneath. Last episode, inside a class, we extracted a long method into a short coordinator that called focused private helpers and read like a table of contents. The uncluttered mainline is that exact same shape, but at the *top level* of the whole program: a short orchestrator that calls one-task subroutines and reads like a table of contents. Same instinct, different scale. And it's the facade instinct again — a clean, simple front over the detailed work hidden behind it. One principle, showing up at the method level, the program level, the subsystem level, and the team level. When you can say "this is the same idea as cohesion and the facade, applied to the mainline", you're writing in the top band.

NARRATOR: That brings us to the dot-point phrase "one logical task per subroutine". A subroutine — a method, a function — should do exactly one logical job. This is the Single Responsibility Principle again, which you already know for methods: one method, one job. The reason it matters for *signatures* specifically is that one-task methods get clean signatures almost for free. A method that does one thing has an obvious name — the name *is* the thing it does — and a short, focused parameter list, because it only needs the inputs for that one job. A method that does five things can't be named clearly, because there's no single verb for "validate and price and update and record and email". The vague name is the symptom; the multiple responsibilities are the disease. So "one logical task per subroutine" and "a clear signature" are two views of the same quality.

NARRATOR: Now the headline tool of this whole episode: the stub. Here's the problem it solves. You've designed a class with, say, six methods. You want to check that the structure is right — that the methods connect properly, that the menu calls them in the right order, that the data flows between them — but you haven't written the hard logic yet. The real "calculate total" method needs pricing rules and tax and discounts; that's an afternoon's work. Do you have to write all six methods completely before you can run *anything*? No. You write stubs.

NARRATOR: A stub is a temporary, placeholder implementation of a method. It has the *real* signature — the correct name, the correct parameters, the correct return type — but the body is a stand-in. Instead of the real logic, a stub does one of two simple things. It either prints a message saying what it *would* do — something like printing "to-do: calculate the real total" — or it returns a dummy value of the right type: a zero, an empty list, a true or a false. That's it. The signature is real and final; the body is a placeholder. The memory hook is: stub first, fill later. You stub out every method with its real signature, get the whole thing running on placeholders, and then go back and fill in the real logic one method at a time.

NARRATOR: Let me make this concrete with a shopping cart, and this is Listing 1 in the supplementary materials if you want to read it after. Picture a shopping-cart class with four methods: add-item, remove-item, calculate-total, and checkout. We design all four signatures properly — real names, real parameters, real return types. Then we stub the bodies. Add-item might get a basic real body, because it's easy — just append the item to a list and print that it was added. But remove-item is harder, so we stub it: its body just prints "to-do: remove this product" and returns false. Calculate-total is harder still, so we stub it: it prints "to-do: calculate the real total" and returns a dummy zero. And checkout calls calculate-total, prints that it's processing the order for that total, and returns true. Now — and this is the magic — the whole cart *runs*. The menu works. You can add an item, ask to remove one, run a checkout, and watch the messages flow through end to end. The structure is proven before a single line of the hard pricing logic exists. If you want the exam-pseudocode version of a stubbed method, Listing 7 writes that calculate-total stub in NESA style — the real signature, a "to-do" displayed, and a dummy zero returned — so you can rehearse the exact form for a written answer.

QUESTION: Before I go on — here's a real exam question. What is a stub, and why would you use one? It's worth three marks. Pause the player, write your three-mark answer, then play.

NARRATOR: Right. For the three marks: a stub is a temporary, placeholder implementation of a method that keeps the method's real signature — its name, parameters and return type — but replaces the real logic with a simple stand-in, such as printing a "to-do" message or returning a dummy value of the correct type. That's the definition; that's mark one. Mark two, the first reason: stubs let you build and test your program *incrementally* — you can run and check the overall structure while some methods aren't finished yet, so you make progress instead of being blocked waiting for the hard parts. And mark three, the reason students forget, and the one that lifts the answer: because every stub has the real signature, the methods *connect* correctly, so you can test the *integration* between methods and classes — that they call each other properly and the data flows right — before any of the real logic exists. Define it, then give the two payoffs: incremental progress, and early integration testing. That last clause is the mark most people leave on the table.

NARRATOR: Let me hammer that integration point, because it's the heart of the dot-point and it links forward. Why is testing the *connections* early so valuable? Because the most painful, expensive bugs aren't usually inside one method — they're in the *gaps between* methods and classes, where one part expected something slightly different from what another part delivered. That's exactly the Mars Orbiter failure: each piece worked alone, but the *interface between them* was wrong. Stubs let you exercise those interfaces on day one. If method A is supposed to call method B with a product id and a quantity, a stub of B will happily receive that call and print what it got — and right there you find out if A is calling it wrong, days or weeks before B's real logic exists. You're catching interface and design problems at the cheapest possible moment. We'll do this properly when we get to integration testing in the testing episodes; for now, just bank the principle: stubs enable early integration testing.

NARRATOR: There's a direct line here back to two episodes ago, dependency injection, and to the collaboration episode's mocks. A stub and a mock are close cousins — both are stand-ins that honour the real interface so the surrounding code can run without the real thing. And remember the punchline from the collaboration episode: because the stand-in has the same signature as the real class, when the real class finally lands, it *drops in unchanged*. That's polymorphism — the P in A-PIE — one interface, many implementations. The stub is one implementation of the signature; the finished method is another; the calling code never knows the difference. So designing to a stub today is the same discipline as designing to an interface, which is exactly the habit the whole industry, and the Year 12 major project, runs on.

NARRATOR: Step two: write the signatures. The student class gets methods like add-grade, taking a subject and a score; get-average, returning a number; and get-grades-for-subject, taking a subject and returning a list. The gradebook class gets add-student, record-grade, get-class-average, and generate-report. Notice every one of those names is a clear verb phrase, every parameter list is focused, and you can tell from the signature alone what each one promises to return. NARRATOR: Step three: stub the bodies and run it. Some, like add-student, get a trivially real body — store the student in a dictionary keyed by student id. The hard ones, like get-class-average — which needs to gather every student's grades in a subject and average them — get stubbed: print "to-do: calculate the class average" and return a dummy zero point zero. Now you instantiate a gradebook, add a student called Alice, record a couple of grades, and call generate-report. It runs end to end. You've proven the objects connect — that recording a grade on the gradebook correctly reaches into the student object — long before the class-average maths exists. Then, and only then, you go back and replace each stub with real logic, one at a time, re-running after each. That's incremental development, and it's exactly how you'd build the classes for the Year 12 project.

NARRATOR: Let me show you the weak-versus-strong contrast directly, because the marker lives in that gap. Suppose the question is: how should you approach building this gradebook? A weak, band-four answer says: "Write all the methods, then run the program and fix the errors." That's the trap — writing full logic before you've validated the interface, then debugging a giant tangle where you can't tell whether the bug is in the maths or in how the objects connect. A strong answer says: "Plan the class structure first with a class diagram, write all the method signatures as clear contracts, then implement them incrementally using stubs — placeholder bodies that return dummy values — so the program runs and the integration between the student and gradebook objects can be tested before the complex logic is written; then replace each stub with its real implementation one at a time." Hear the difference? The strong answer names the artefacts — class diagram, signatures, stubs — and it names the payoff: integration tested before the logic exists. That's the language of the mark.

QUESTION: Let me throw the classic trap at you. Surely it's faster to just write the real code straight away? Why bother with stubs and dummy values that you're only going to throw away?

NARRATOR: It feels faster, and that's the trap. Writing everything at once means you can't run *anything* until the *last* method is done — so you can't test the structure, can't catch a design mistake, until you've sunk hours into logic that might be built on a broken interface. If the design is wrong, you find out late, and you rip up real work. Stubs flip that. You get a running program in minutes, you validate the interface and the integration immediately, and you discover design problems while they're cheap to fix. And the dummy values aren't wasted — the *signatures* you wrote are the real, final signatures; you only replace the bodies. So you don't throw away the stub's contract, just its placeholder insides. The slow part of programming isn't typing, it's getting the design wrong and finding out late. Stubs are how you find out early.

NARRATOR: Let me flag the three traps explicitly, because each is a place students lose marks. Trap one: writing the full logic before validating the interface — diving into the hard method body before you've confirmed the signatures and how things connect. The fix is the whole episode: signatures and stubs first. Trap two: vague signatures — a method called "process" or "do stuff", or a signature so unclear you can't tell what it returns. The fix is the clear-focused-consistent test, and the one-logical-task rule that gives a method an obvious name. Trap three, and it's the subtle one: forgetting that stubs enable early *integration* testing. If you say a stub "is just a placeholder so the code runs", that's only half the mark. The full answer is that stubs let you test the *connections between* methods and classes before the logic exists. Say "integration" and you bank the top mark.

QUESTION: Question one, two marks. List what a method signature comprises. Pause and answer.

NARRATOR: A method signature comprises three things: the method's name; its parameters, including their types; and its return type or return value. For the two marks, name all three — name, parameters, return. If you only say "the name and parameters", you've dropped the return and you've dropped a mark. QUESTION: Question two, three marks. What is a stub, and why would you use one? Pause and answer.

NARRATOR: A stub is a temporary, placeholder implementation of a method that keeps the method's real signature but replaces the real logic with a simple stand-in — printing a "to-do" message or returning a dummy value of the correct type. You use one for two reasons: first, to build and test your program incrementally, making progress while some methods are unfinished; and second — the high-value reason — because the stub has the real signature, you can test the integration between methods and classes, that they connect and the data flows correctly, before the real logic exists. QUESTION: Question three, three marks. Explain what is meant by "one logical task per subroutine", and why it is good design. Pause and answer.

NARRATOR: "One logical task per subroutine" means each method or function should do exactly one well-defined job — it's the Single Responsibility Principle applied to subroutines. It's good design for three reasons you can pick from: a single-task method has an obvious, clear name and a focused parameter list, so its signature is self-documenting; it's easier to test in isolation, because there's only one behaviour to check; and it's easier to reuse and to change, because the one job is localised. The mark-earning link is to name it as the Single Responsibility Principle and to connect it to a clear signature: one task gives one clear name.

QUESTION: Question four, four marks. Explain how stubs support incremental development and testing. Pause and answer.

NARRATOR: This is the integration-testing question dressed up, and it wants you to join the two ideas. Stubs support incremental development because you can write every method's real signature, give the hard ones placeholder bodies, and immediately run the whole program — so you make steady progress and validate the overall structure without waiting for every part to be finished, then replace stubs with real logic one method at a time. They support testing because, since each stub honours the real interface, the methods and classes *connect* exactly as they will in the finished system — so you can test the integration between components, catching interface and design mistakes at the cheapest possible moment, long before the complex logic is written. For full marks: incremental build on real signatures, plus early integration testing on real interfaces, and ideally the line that the placeholder later drops in unchanged because the signature never changed.
