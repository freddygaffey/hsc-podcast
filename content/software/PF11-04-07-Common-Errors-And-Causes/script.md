Let me take the three in turn, because each behaves completely differently — and that behaviour is how you classify it.

NARRATOR: First, syntax errors. A syntax error breaks Python's grammar rules, so the program won't run at all — Python refuses before it executes a single line. Likely causes: a missing colon after an if, a while, or a def; mismatched or missing brackets or quotes; or inconsistent indentation, which Python reports as an indentation error, a member of the same family. The good news, and a point worth making in an answer: syntax errors are the easiest to find, because Python points right at them. It reports the file, the line number, shows you the offending line, and prints a little caret — an up-arrow symbol — pointing at exactly where it got confused, then names the error type and gives a description. Listing 1 is the three-type reference; Listing 2 shows common syntax errors broken and fixed. To read a syntax error: go to the line number, look where the caret points, and check for the missing colon, bracket, or quote.

NARRATOR: Second, runtime errors — also called exceptions. A runtime error is different in kind: the code is grammatically valid, so it starts running, but it crashes partway through when it hits something it cannot do. The program was fine until that moment. The likely causes are a roll-call you should recognise by name: a zero-division error, from dividing by zero — like averaging an empty list, where the count is zero; an index error, from reading past the end of a list; a key error, from asking a dictionary for a key that isn't there; a type error, from combining incompatible types — remember adding the string "seventeen" to the number one from the data-types episode; a value error, from something like converting the text "abc" to a number; and a name error, from using a variable that was never assigned. When one of these fires, Python prints a traceback, and the trick to reading it is: read the last line. The last line names the exception type and gives a message; the line just above tells you where. Listing 3 demonstrates these exceptions and the two ways to handle them — guard against the condition before it happens, by checking the list isn't empty or the index is in range, or wrap the risky code in a try-and-except block to catch the exception gracefully.

QUESTION: Here's one to actually attempt. Pause the player. A function divides a total by the number of items to get an average, and it crashes when given an empty list. What type of error is it, and what's the cause? Work it out, then play.

NARRATOR: It's a runtime error — specifically a zero-division error. The cause: an empty list has a length of zero, so dividing the total by the count divides by zero, which Python cannot do, and it raises the exception mid-execution. The fix is to guard first — if the list is empty, return None or zero before dividing — or to catch the zero-division error with a try-and-except. The marks are for naming it a runtime error, identifying the zero-division cause from the empty list, and giving a guard or try-except fix. Note it ran fine for non-empty lists — runtime errors strike only when execution reaches the bad operation.

NARRATOR: Third, logic errors — and these are the dangerous ones. A logic error is code that is grammatically valid and runs to completion without crashing, but produces the wrong answer. No syntax error, no exception, no traceback — nothing. The program looks like it worked. The likely causes: an off-by-one error, like the range function starting at zero when you needed one — the factorial bug from the debugging episode; a wrong operator, like a greater-than where you needed greater-than-or-equal, which mishandles the boundary; or simply a wrong formula or condition. Listing 4 shows an average function with an off-by-one in the divisor: it runs perfectly, raises nothing, and quietly returns the wrong number. Because there's no message, Python can't help you — the only way to catch a logic error is testing and desk checking, which is exactly why the last two episodes mattered. This is the marquee trap, so say it out loud: code that runs without crashing is not proof that it's correct. A logic error runs silently.

NARRATOR: So the way to classify any error is to ask what it does. Did it refuse to run? Syntax error — check the grammar. Did it start, then crash with a traceback? Runtime error — read the last line for the exception. Did it run cleanly but give the wrong answer? Logic error — the silent one. QUESTION: Question one. Name the three types of programming error and state how each one reveals itself.

NARRATOR: A syntax error breaks the language's grammar, so the program won't run at all and Python reports it before execution. A runtime error occurs during execution, crashing the program with an exception and a traceback. A logic error doesn't crash — the program runs to completion but produces an incorrect result, with no error message. The hook is S-L-R, and the reveal for each — won't run, crashes, or runs-but-wrong — is the classifying test.

QUESTION: Question two, the stimulus classic. Classify each of these as a syntax, runtime, or logic error, and give a likely cause: first, an if-statement with no colon; second, reading the tenth item of a five-item list; third, a function that returns a person's age as one year too high. Pause the player, answer, then play.

NARRATOR: First, the missing colon is a syntax error — Python's grammar requires the colon, so the program won't run; the cause is the omitted colon. Second, reading the tenth item of a five-item list is a runtime error — an index error — because the index is out of range; it runs until it reaches that line, then crashes. Third, the age coming out one year too high is a logic error — the program runs and returns a value, but the value is wrong; a likely cause is an incorrect calculation, such as an off-by-one in the year arithmetic. The marks are the correct type plus a specific cause for each — and noticing the third is silent.

QUESTION: Question three. Distinguish between a runtime error and a logic error.

NARRATOR: A runtime error occurs during execution and crashes the program with an exception, so it is immediately visible — Python produces a traceback naming the error. A logic error does not crash: the program runs to completion and produces an incorrect result, with no error message at all. The distinguishing point is the symptom: a runtime error halts the program loudly; a logic error lets it finish silently with the wrong output. The mark is that contrast — crashes-with-a-message versus runs-silently-but-wrong.

QUESTION: Question four. Explain why logic errors are generally the hardest type of error to find.

NARRATOR: Logic errors are hardest to find because they produce no error message and no crash — the program runs to completion and appears to work, so nothing draws attention to the fault. Unlike a syntax error, which Python points to with a line number, or a runtime error, which produces a traceback, a logic error gives the programmer no automatic clue to its location. It can only be found by comparing the program's actual output to the expected output through careful testing and desk checking, which is why well-designed test data matters. The mark-earning point: the absence of any error message means logic errors must be hunted by testing, not reported by the interpreter.

QUESTION: Question five. A program tries to add the string "seventeen" to the number one and crashes. Identify the error type and the cause, and how you'd prevent it.

NARRATOR: It's a runtime error — a type error — because Python cannot add a string and a number together; the operation is invalid for those types and raises the exception during execution. The cause is combining incompatible data types, often because a value that should be a number is still a string, for instance straight from user input. To prevent it, convert the string to a number first — using the integer or float conversion — and validate that the conversion is possible before relying on it. The marks: runtime error, type error from incompatible types, and converting or validating the input as the fix. This is the data-types trap from earlier, now classified.
